# Executive summary

This is cycle 1 of the repeatable audit defined in [audits/instructions.md](../instructions.md),
run by an AI agent at commit `acc0471b1903` (main, clean). It is a complete manual source code
security audit of every security-critical module plus a re-run of the existing test suites,
dependency advisory scans and static invariant checks. It is **not** a penetration test, it had
no physical devices, no live model, no staging or production access, and no independent human
reviewer. Its findings are inputs to a human-reviewed cycle, not a release decision.

**Headline result.** The architecture's core invariants hold in the code: tokens never reach the
browser, signing goes only backend to Biatec OIDC, the MCP `signTransaction` tool is blocked, the
group ID is recomputed and bound at every signing step, and the model is gated server-side before
every tool call. The existing backend suite passes at the audited commit (1,483 tests). One
capability breaks the pattern: **liquidity groups returned by the builder sidecar are signed
without being decoded and checked** (BCHAT-001, High), where every other builder path checks
rekey, close-out, receiver, amount and app id. Two reviewers found it independently and the lead
confirmed it in the code. The same class of gap exists for transaction fees on swap, liquidity,
safe-creation and x402 groups (BCHAT-003).

**Counts.** 46 findings: 2 High, 7 Medium, 37 Low. 27 informational observations and one documented limitation are listed in
Appendix E. No Critical finding. No secret in the tracked tree. No cross-tenant data access path
was found.

| Severity | Open findings | Most important |
| --- | ---: | --- |
| Critical | 0 | |
| High | 2 | BCHAT-001 liquidity groups not verified; BCHAT-003 no fee ceiling on swap/liquidity/safe-create/x402 groups |
| Medium | 7 | BCHAT-002 cancel can race consent redemption; BCHAT-004/005 unauthenticated row creation and shared rate-limit bucket behind ingress; BCHAT-006 mock OIDC hands out device tokens; BCHAT-007/008/009 authenticator key binding, missing platform folders, iOS keychain backup |
| Low | 37 | see section "Detailed findings" |

**Release recommendation: No-go for the liquidity capability and conditional go for the rest,
pending a human-reviewed cycle.** Specifically:

1. Fix BCHAT-001 and BCHAT-003 before any release where `dex.addLiquidity`, `dex.removeLiquidity`
   or a swap can be signed against a real sidecar. Until then, disable those capabilities by
   configuration (the tool gate supports this).
2. Fix BCHAT-002 before release; it allows a "cancelled" transaction to be broadcast.
3. Configure trusted proxies in every overlay (BCHAT-005) and rate-limit the session endpoints
   (BCHAT-004) before public exposure.
4. The authenticator is not releasable as committed: the Android and iOS platform folders are not
   under version control (BCHAT-008), and the device key is not bound to biometric authentication
   in the keystore (BCHAT-007). These confirm, and sharpen, risk register entry RISK-003.
5. Schedule a human-reviewed cycle with physical devices, staging access and an independent
   reviewer (RISK-018). Every CVSS score below is an assessor estimate and must be re-scored.

**Decisions required from the sponsor:** accept or reject the no-go on liquidity; assign owners
to the 23 risk register entries; decide whether the mock OIDC image may be run on reachable hosts
until BCHAT-006 is fixed.

# Architecture and threat model

Assets: the user's OAuth tokens (backend vault only), the user's wallet (signing by Biatec OIDC
on phone consent), the evidence chain (signed, partially anchored), tenant configuration and
secrets, operator keys, the Bedrock quota and spend. Trust boundaries: host page to widget (not a
boundary, documented), browser to backend (cookie session, CSRF, CORS), backend to Biatec OIDC
(confidential client), backend to builder sidecar (shared secret, in-cluster), backend to Biatec
MCP, algod, indexer, market, x402 resource (allow-listed), model to backend (untrusted output,
server-side tool gate), phone to OIDC (device key, receipts).

Attackers modelled: anonymous internet user, other tenant, hostile host page, malicious model
output, poisoned KB/tool/chain content, compromised builder sidecar or its libraries, compromised
cluster neighbour, insider with deploy identity, stolen session or device. The code review
confirmed the controls listed under "Attack chains and effective controls" and found the gaps
listed as findings. The documented architecture matches the code with four deviations noted in
findings: liquidity verification (BCHAT-001), consent-resume gate skipping (BCHAT-011), the
vault's Dev provider default (BCHAT-012), and the widget's use of polling rather than
`postMessage` (which makes section 6.1's "postMessage origin check" item not applicable; an
improvement to the instructions, noted in Appendix G).

# Detailed findings

## BCHAT-001 Liquidity groups from the builder sidecar are signed without field-level verification

1. **ID, title, category, components:** BCHAT-001; financial integrity / builder boundary;
   `backend/Biatec.Chat.Tools/Dex/Liquidity/LiquidityBuilder.cs:110-145` at `acc0471b1903`,
   reached from `backend/Biatec.Chat.Api/Dex/Liquidity/LiquidityExecutors.cs:147-215` and
   signed by `backend/Biatec.Chat.Api/Chat/Confirm/ConfirmService.cs`.
2. **Status and confidence:** Open; confidence High; confirmed control gap (two reviewer
   instances independently, lead re-read the code and grepped for any rekey/close check on the
   path: none exists in Tools/Dex/Liquidity or Api/Dex/Liquidity, and ConfirmService has no
   generic pre-sign rekey check).
3. **Severity:** High, 7.1 estimate, CVSS-B AV:N/AC:L/AT:P/PR:N/UI:A/VC:N/VI:H/VA:N/SC:N/SI:N/SA:N.
   AT:P because the attacker must control the sidecar response; UI:A because the user presses
   Confirm and, above threshold, approves on the phone. CWE-345, CWE-20. ASVS 5.0 V11 business
   logic, spec section 7.2 "verify builders ... independently decode transactions".
4. **Prerequisites:** a compromised or buggy builder sidecar, a malicious release of
   `biatec-concentrated-liquidity-amm` (eight high advisories already sit in its transitive
   tree, BCHAT-046), or an in-cluster actor holding the sidecar shared secret (BCHAT-016).
   Affected population: every user of `dex.addLiquidity`/`dex.removeLiquidity`. Upstream
   assumption: whether Biatec OIDC's sign endpoint independently decodes and displays rekey or
   close fields on the phone is unknown (hypothesis H-TLS-4).
5. **Root cause and reproduction:** `BuildAsync` decodes the group, checks that every sender is
   the user, that the sidecar's *facts* name the same sender and pool and that the *facts'*
   amounts equal the request, then returns. It never inspects `RekeyTo`, `CloseRemainderTo`,
   `AssetCloseTo`, receivers, amounts, app ids, fee or genesis in the transactions. The card and
   canonical JSON are built from the facts, and the signed bytes are the transactions. Contrast
   `SwapGroupVerifier.cs:23-27`, `TransferStepBuilder.cs:109-120`, `SafeBuilder.cs:217`,
   `SafeProposalBuilder.cs:218`, `X402PayService.cs:112`.
   Test (backend unit test with the `IBuildersClient` fake used in `Tests/Dex/Liquidity`): for
   `clamm.liquidity.add` return a group `[pay(sender=user, receiver=attacker, amount=balance,
   closeRemainderTo=attacker), appl(noop, rekeyTo=attacker)]` with facts
   `{sender, pool:{appId:<requested>}, amountA, amountB}` equal to the request. Expected:
   `LiquidityBuildException`, no preview row. By code: a preview "Add X and Y to pool N" is
   persisted and Confirm signs it. Harness: TEST-008 (static, fails while open).
6. **Evidence:** EV-06 (code excerpt lines 110-145 captured by the lead; retained in transcript).
   Demonstrated: absence of the check. Potential: fund loss and account rekey.
7. **Impact:** unauthorized value movement bounded by the user's balances and OIDC consent
   thresholds; rekey gives persistent account control. Blast radius: all tenants with liquidity
   enabled. Loss estimate: not given (depends on balances; assumption-laden).

# Attack chains and effective controls

**AC-1 Compromised builder to fund loss (simulated, not executed).** Supply-chain compromise of
`biatec-concentrated-liquidity-amm` (BCHAT-046 shows its transitive tree is already stale) or
the sidecar pod (BCHAT-016 no NetworkPolicy) produces a liquidity group with `closeRemainderTo`
and `rekeyTo` set (BCHAT-001) and an inflated fee (BCHAT-003). Backend builds a plausible card,
user confirms, backend signs via OIDC. Stops that hold: OIDC's own decode and consent threshold
(unknown whether rekey is displayed), the user's phone approval above threshold. Stops that do
not exist: backend field-level verification on this path. Detection: evidence records the
signing outcome, not the hidden fields.

**AC-2 Hostile host page to a "cancelled" broadcast (simulated).** Host JS (documented
non-boundary) drives Confirm and, during the phone approval, fires Cancel at the right moment
(BCHAT-002). The user sees "cancelled"; the group lands. Stop that holds: the user must still
approve on the phone.

**AC-3 Anonymous resource exhaustion (simulated).** One host behind any CDN exhausts the shared
IP bucket (BCHAT-005) and floods `/session/probe` (BCHAT-004); operator API locks out
(BCHAT-005). No integrity impact.

**Effective controls verified in code (selection; full lists in the reviewer ledgers):**

- Tokens never leave the backend: only `SessionState` fields and an opaque `__Host-` cookie reach
  the browser (`Sessions/SessionEndpoints.cs:35-48,105-131`); the one documented exception is the
  `id_token_hint` in the RP-initiated logout redirect. No token or token-response body is logged
  anywhere (`AuthEndpoints.cs`, `Revocation.cs`, `TokenVault.cs:133,155`, `OidcClient.cs:41`).
- OIDC flow: confidential client, S256 PKCE, `resource` indicator, 256-bit state/nonce/verifier,
  state sealed and hashed, single-use, bound to session and tenant, RFC 9207 `iss` check, ID
  token validated with asymmetric algorithms only, fixed-time nonce compare, discovery endpoints
  forced onto the issuer origin (`OidcMetadata.cs:63-86`).
- Session: 256-bit CSPRNG cookie, SHA-256 prefix stored, 15 min idle / 8 h absolute, rotation
  in one transaction, loser of the race gets null.
- CORS exact-origin only, `null` and non-http(s) refused; CSRF needs custom header + allow-listed
  Origin + client key; tenant derived from `Host` only, unknown host 404; `X-Forwarded-For`
  honoured only from configured proxies with `ForwardLimit=1` (code correct; BCHAT-005 is the
  deployment).
- Signing: `WalletSigningClient.cs:51` posts only to `wallet/{network}/{address}/sign`; MCP
  client blocks `signTransaction` on every call (`McpTypes.cs:27`, `BiatecMcpClient.cs:67`);
  TEST-006 confirms no local signing primitive.
- Group binding: `AlgorandGroup.cs:32-36,55-57` recomputes the group ID with `grp` cleared and
  refuses relabelled groups; `SignedGroupVerifier.cs:33-62` compares every signed transaction
  byte for byte and re-hashes before submission; one sender per group.
- Field-level verification exists for transfers (sender, rekey, genesis id+hash, fee ceiling,
  wire-level close/aclose/asnd scan, receiver, amount), swaps (rekey/close/clawback/app
  lifecycle, exact funding transfer, model-chosen pool must be in the listing, slippage ceiling),
  safe creation and proposals (sender, rekey, app id, ABI canonical round-trip, fee ceilings,
  execute-on-propose refused, approval bound to payload version) and x402 (decoded transfer is
  the truth, re-encode equality catches hidden fields, SSRF allow-list, no redirects,
  connect-time DNS re-check).
- 600 s confirm gate with `>=`, rebuild = new ids and hashes, landed steps never rebuilt;
  atomic `Proposed -> Confirmed`, unique `(PreviewId, Seq)` and `AuthReqId`; caps reserved under
  `pg_advisory_xact_lock(sub, tenant)`; `Submitted` persisted before broadcast with
  `CancellationToken.None` and lazy reconciliation; `consent_not_enforced` refusal when OIDC
  signs without a challenge; caps a hard stop when `OidcHonoursRequireConsent` is false.
- Model: tool gate before every executor regardless of the model's tool list
  (`ConversationOrchestrator.cs:180-184`), strict JSON schemas (`additionalProperties:false`,
  depth 16, regex timeout), 8-round loop cap, tool results and host context wrapped as
  `<untrusted_data>` with closing-tag neutralisation, guardrail fails closed when unreachable,
  `maxTokens` always set, model ids restricted to `eu.` Claude 4.x, region pinned.
- Evidence: RFC 8785 canonicalizer rejecting unsafe integers and duplicate keys; 32-byte salt per
  entry; chain ordered under an advisory lock with a unique `(ConversationId, Seq)`; ES256 only;
  evidence key store refuses to start outside Development without `Secret`/`Kms`; DB holds public
  keys only; export scoped to tenant and subject with 404-shaped denial.
- Vault: AES-256-GCM, fresh data key and 96-bit nonce per seal, session id as AAD, version and
  length checks, zeroing; KMS encryption context bound; single-flight refresh across replicas
  with a Redis owner lock and Lua write-if-locked.
- Admin: operator keys as SHA-256 hashes, constant-time comparison over all entries, 32-char
  minimum, 404 while unconfigured; policy patch refuses unknown members; KB upload strict UTF-8,
  size and count limits under a global lock; onboarding has no SSRF surface, host normalised,
  challenge HMAC bucketed; every admin change commits with its signed evidence or not at all.
- Widget: no `v-html`/`innerHTML`/`eval`; markdown parsed to data and rendered as text nodes;
  links http(s) only via `new URL` with `noopener noreferrer`; no storage of any token; confirm
  needs Review opened + checkbox + 600 s remaining, sends the hash of the shown step, double
  submit locked; host API exposes no programmatic confirm.
- Consent protocol: strict JCS, strict base64url, no algorithm agility (`alg` const ES256),
  attestation binds subject, device kid and thumbprint, the eight signed members are exactly the
  schema, consumption only after verification, request object never carries the binding code,
  push payload is only the `auth_req_id`.
- Delivery: `permissions: contents: read` in every workflow, `id-token: write` only on publish,
  no `pull_request_target`, no expression injection (untrusted values via `env:`), promotion
  never rebuilds and asserts digest equality, secrets validated and never printed, kubeconfig
  deleted `if: always()`, no IAM users or keys, Roles Anywhere trust policy bound to anchor ARN
  and CN list with 1 h sessions, role policy limited to three `eu.` Claude profiles, signing
  helper SHA-256 verified in the image, pods non-root with seccomp and all capabilities dropped,
  NetworkPolicies on PostgreSQL and Redis, cert-manager TLS, mock OIDC not deployed, demo image
  refuses credential-shaped bundle content, strict CSP.
