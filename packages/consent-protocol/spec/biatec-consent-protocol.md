# Biatec Consent Protocol, version 1.2

Status: draft. This document is the integrator-facing specification. `PRODUCT-DESCRIPTION.md` ("Biatec Authenticator And The Biatec Consent Protocol") is the product source of truth and wins on any conflict. Version 1.2 adds **relying parties**: any organisation (a bank, a broker, an internal system) can use the authenticator to confirm payments, logins and other actions, without Biatec vouching for it ([14. Relying parties](#14-relying-parties)), with the requests of sections 3.3 to 3.6, the verification of section 8.4 and 8.5 and the text rules of [15. Text rules](#15-text-rules); [16. Changes from 1.1](#16-changes-from-11) lists what changed. Version 1.1 stays the version of `biatec_transaction` and `biatec_limits_change` receipts: the envelope `version` is `"1.1"` for them and `"1.2"` for the three new types. Version 1.1 replaced 1.0 (the mock Biatec OIDC, the widget's backend and the authenticator of this repository move to the newer versions in their own tasks; the schemas and verifiers accept all of them meanwhile); [13. Changes from 1.0](#13-changes-from-10) lists what changed then.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Overview

The Biatec Consent Protocol lets a user approve or deny one precisely described action on a trusted, device-bound surface (the Biatec Authenticator) while the action is requested from somewhere else (the Biatec Chat widget, a bank app, a website). It is a profile over existing standards, not a new protocol:

| Need | Standard |
| --- | --- |
| Push an approval to a device that did not start the flow | OpenID Connect CIBA (push and poll modes) |
| Describe exactly what is approved | OAuth 2.0 Rich Authorization Requests, RFC 9396 (`authorization_details`) |
| Bind approval to amount and payee | PSD2 dynamic linking, carried by `authorization_details`; CIBA `binding_message` for an optional purpose text |
| Step up only when needed | OAuth 2.0 Step-up Authentication Challenge, RFC 9470 |
| Hardening | FAPI 2.0 Security Profile, FAPI-CIBA: PKCE, exact redirect URIs, short lifetimes, `requested_expiry` default 300 s |
| Canonical signed bytes | JSON Canonicalization Scheme, RFC 8785 |
| Device keys | Two hardware-backed P-256 keys per device (an approval key bound to biometrics and a presence key), attested at enrollment |
| Client identity | A fingerprint of the `client_id` and, when proven, the client's domain; the user decides on their own phone whether to trust it |
| Consent record | Kantara Consent Receipt field layout |

Roles:

- **Client**: the requesting application (Biatec Chat backend, a bank, a fintech).
- **Biatec OIDC**: the authorization server. It decodes the transaction group, values it, opens the request, generates the binding code, stores the request and verifies and consumes receipts. It vouches for no client and for no application.
- **Authenticator**: the mobile app holding the device keys.
- **User**: sees the card on the authenticator and the binding code on the requesting surface. All trust is the user's: the threshold, which services are linked and which applications are trusted are set on the user's own phone.
- **Relying party**: a client that is an organisation asking for confirmation of its own actions, not a wallet application. It registers itself, is linked by the user on the phone and can then send payment, login and action requests ([14. Relying parties](#14-relying-parties)). Biatec OIDC vouches for no relying party.

Machine-readable definitions live in `schemas/` (JSON Schema 2020-12) and signed examples in `vectors/`. Everything in this document that is normative about a wire object is expressed by a schema.

## 2. The request model

A consent request at Biatec OIDC is always the same object, whichever entry point opened it (`schemas/consent-request.schema.json`):

- `authorization_details`: exactly one typed object, decoded by Biatec OIDC (section 3).
- A **binding code** generated by Biatec OIDC, returned only to the client (section 7).
- An optional client-supplied `binding_message`.
- The client identity: `fingerprint`, `domain_proven`, `domain` when proven, and `linked` (section 6).
- `requested_expiry` (default and maximum 300 seconds) and the derived `expiry`.
- The **bound hash** (`group_hash`, `request_hash` or, for the relying-party types of protocol 1.2, `details_hash`) the consent is tied to.
- The reporting `origin` and the pairwise `sub` of the requesting client.

Client-supplied amounts or payees are never accepted as the thing being consented to; the group (or canonical limits body) is.

## 3. Authorization details types

`authorization_details` is an array of exactly one object (`schemas/authorization-details.schema.json`), of one of the types below: the two wallet types of protocol 1.1 (3.1, 3.2) or, from protocol 1.2, the three relying-party types (3.3 to 3.5, branch `#/$defs/v1_2`). A receipt or request of a wallet type has version 1.1, one of a relying-party type version 1.2; the two never mix (the schemas and every verifier refuse a mixture, and `version` is unsigned, so the shape decides).

### 3.1 `biatec_transaction`

Describes one signing call (`schemas/authorization-details-transaction.schema.json`). Biatec OIDC decodes every field from the unsigned group itself:

- `network`, `group_hash`, `sender` and `origin`.
- `transfers`: every payment and asset transfer the sender sends out, in group order, at most 16, each with `receiver`, `asset`, `amount` and, when it could be priced, `fiat_value`. Transfers of other senders are not listed.
- `applications`: every application the group calls, at most 16, each with its `id` and `trusted`, which is true only when the user trusted that application for this client on their own phone. There is no operator list of applications.
- `value_known`: false when any transfer could not be priced or any application is not trusted. Then there is no top-level `fiat_value` and the card says "Value unknown" in the warning style. When true, the top-level `fiat_value` is the total in EUR of the priced transfers. The top-level `fiat_value` is present exactly when `value_known` is true.

A renderer MUST show every transfer and every application and MUST NOT summarize. A group that sends value somewhere `transfers` cannot name is not described and is not consentable in this version: a payment with a close-to address, an asset transfer with a close-to or clawback address, a rekey, and any transaction type other than payment, asset transfer and application call. Biatec OIDC refuses such a group for a client under consent enforcement (`403 consent_unsupported_operation`), so no receipt ever covers one. Amounts are decimal strings, never JSON numbers, so canonicalization loses no precision. `origin` is part of the signed object, as the client reported it: the receipt proves which origin the user saw on the card, not that the site is who it says it is. The card shows it labelled as reported by the client, and only a proven domain says who the client is.

The `group_hash` is the Algorand group ID recomputed from the handed transactions (base32, 52 characters; for one ungrouped transaction its transaction id), or for Bitcoin the SHA-256 intent hash derived from a PSBT carrying prevout data (lowercase hex). The signing endpoint MUST refuse a request whose recomputed hash differs from the consented one.

### 3.2 `biatec_limits_change`

Describes a change of spending limits (`schemas/authorization-details-limits-change.schema.json`). It carries no `origin`: for this type the request's `origin` is recorded by Biatec OIDC but is not part of what the device signs. It has `current_limits`, `requested_limits` and `request_hash`, the lowercase hex SHA-256 of the RFC 8785 canonical request body of `PUT /wallet/limits`. The vectors include a worked example: the body `{"per_day_eur":"5000","per_transaction_eur":"2000"}` hashes to the `request_hash` in `vectors/receipts.json`.

### 3.3 `biatec_payment`

A payment the relying party asks the user to confirm (`schemas/authorization-details-payment.schema.json`). Biatec does not execute it: the relying party (a bank) does, after it has the user's signed approval. The members are exactly:

- `type`: `biatec_payment`.
- `instructed_amount`: `{ amount, currency }`. `amount` is a decimal string with at most two decimals and greater than zero (`^(0|[1-9][0-9]{0,14})(\.[0-9]{1,2})?$`, never a JSON number); `currency` is three upper-case letters (ISO 4217).
- `creditor_name`: 1 to 70 characters.
- `creditor_account`: either `{ iban }` or `{ identification, scheme }`. The IBAN is in electronic form (upper case, no spaces) and its ISO 7064 mod-97-10 check digits MUST be right (`isValidIban` in `scripts/lib.mjs`; the country-specific lengths are not checked). `identification` is 1 to 34 characters and `scheme` 1 to 20 characters (for example `BBAN` or `SORTCODE`).
- `remittance` (optional): 1 to 140 characters.
- `execution_date` (optional): an ISO 8601 calendar date `YYYY-MM-DD` that exists.
- `origin` (optional): added by Biatec OIDC when it has one (section 3.6), never sent by the relying party.

Every string member is text a relying party supplied and is untrusted: it obeys the text rules of [15. Text rules](#15-text-rules) (relying-party profile), a violation is refused and never stripped. The card shows each member in a field the app draws itself, the creditor's name and account marked as written by the relying party, together with who is asking (section 6).

```json schema=authorization-details-payment
{
  "type": "biatec_payment",
  "instructed_amount": {
    "amount": "1250.00",
    "currency": "EUR"
  },
  "creditor_name": "Muster Energie GmbH",
  "creditor_account": {
    "iban": "DE89370400440532013000"
  },
  "remittance": "Invoice 2026-0042",
  "execution_date": "2026-10-20",
  "origin": "https://netbanking.bank.example"
}
```

### 3.4 `biatec_login`

Access to the relying party's own service, for example internet banking (`schemas/authorization-details-login.schema.json`): `type` `biatec_login`, an optional `context` with any of `ip`, `location` and `user_agent` (each 1 to 80 characters, at least one present, text rules of section 15) and an optional `origin` as in 3.3. The context is what the relying party reports about the session that asks; the card shows it as reported by the relying party.

```json schema=authorization-details-login
{
  "type": "biatec_login",
  "context": {
    "ip": "203.0.113.42",
    "location": "Bratislava, Slovakia",
    "user_agent": "Firefox 133 on Windows 11"
  },
  "origin": "https://netbanking.bank.example"
}
```

### 3.5 `biatec_action`

Any other action (`schemas/authorization-details-action.schema.json`): `type` `biatec_action`, a `title` of 1 to 60 characters, 1 to 8 `lines` of `{ label, value }` (label 1 to 30, value 1 to 80 characters) and an optional `origin` as in 3.3. The app renders the title and every line as plain text in fields it draws itself and shows nothing the relying party did not list.

```json schema=authorization-details-action
{
  "type": "biatec_action",
  "title": "Add payee",
  "lines": [
    {
      "label": "Payee",
      "value": "Muster Energie GmbH"
    },
    {
      "label": "Account",
      "value": "DE89 3704 0044 0532 0130 00"
    },
    {
      "label": "Daily limit",
      "value": "5 000 EUR"
    }
  ]
}
```

### 3.6 `details_hash`

For the three relying-party types the bound hash is the `details_hash`: the base64url encoding without padding (43 characters) of the SHA-256 digest of the RFC 8785 canonical form of the `authorization_details` **object** (the one element, not the array) exactly as the relying party sent it, plus the `origin` member that Biatec OIDC added when it had an origin. Biatec OIDC never rewrites, completes or removes a member of the relying party's object, and a request that carries an unknown member or an `origin` of the relying party's own is refused (`400 invalid_authorization_details`).

- The device computes the hash itself from the object it renders and signs, and never copies it from the request. A verifier computes it again from the object in the receipt (`detailsHash(details)` in `scripts/lib.mjs`) and compares it with the signed `details_hash`.
- The request's `bound_hash`, the signed receipt's `details_hash` and the elevated token's `consent_hash` carry the same value. `group_hash` stays the bound hash of `biatec_transaction` and is a member of that type's details; a signed object has `details_hash` for the three new types and never for a wallet type, so exactly one of `group_hash` and `details_hash` binds a receipt.
- The relying party knows the object it sent and the origin it reported, so it recomputes the hash without asking anyone (section 8.5).

Worked example, the first vector of `vectors/receipts-1.2.json` (`payment-approve`). Biatec OIDC added the origin the request came from to the object the bank sent:

```
sent by the relying party   {"creditor_account":{"iban":"DE89370400440532013000"},"creditor_name":"Muster Energie GmbH","execution_date":"2026-10-20","instructed_amount":{"amount":"1250.00","currency":"EUR"},"remittance":"Invoice 2026-0042","type":"biatec_payment"}
stored (origin added)       {"creditor_account":{"iban":"DE89370400440532013000"},"creditor_name":"Muster Energie GmbH","execution_date":"2026-10-20","instructed_amount":{"amount":"1250.00","currency":"EUR"},"origin":"https://netbanking.bank.example","remittance":"Invoice 2026-0042","type":"biatec_payment"}
SHA-256 (hex)               dc3d46b119895d9d9a465a649a877d48d41148b589b318b575f815dd769917b7
details_hash (base64url)    3D1GsRmJXZ2aRlpkmod9SNQRSLWJsxi1dfgV3XaZF7c
```

The origin is part of the hashed object: the same payment without it hashes to `b2PVUKD24wUOKSiIlgXGGUi5aGY0xDrOEbTynZ7A-HA`. One character of the creditor IBAN changed (`DE89370400440532013001` instead of `DE89370400440532013000`) gives `7GT9fJfJrRbKOcU278OAD0xH25t7eMzkLTbZkPnwlbk`, and the altered IBAN also fails its check digits; `vectors/receipts-1.2.json` contains a receipt signed over such an altered payment next to the original hash (`payment-approve-iban-altered-REFUSED`) that every verifier MUST refuse.

## 4. Step-up entry

The client calls a wallet endpoint (`POST /wallet/{network}/{address}/sign` or `PUT /wallet/limits`) with an ordinary token. The CIBA request inherits that token's scopes and audience, so the elevated token carries the same `sign` or `manage-limits` scope and resource and can be presented straight back to the wallet endpoint. Biatec OIDC decides consent is needed (value above the user's threshold, an unknown value, a client the user has not linked yet or that registered less than 24 hours ago, the client sent `requireConsent: true`, or the user set "always ask" for this client), opens the request itself and answers with an RFC 9470 challenge:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="biatec:consent"
Content-Type: application/json
```

```json schema=stepup-challenge
{
  "error": "insufficient_user_authentication",
  "error_description": "Phone approval is required for this group.",
  "acr_values": "biatec:consent",
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "expires_in": 300,
  "interval": 2,
  "binding_code": "483920"
}
```

The client shows the binding code on its surface, polls the token endpoint (or receives the push-mode callback), then retries the wallet endpoint with the elevated token and the same unsigned group:

```http
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:openid:params:grant-type:ciba&auth_req_id=ciba_8257c10231dd9b46e2f877484cf0b2a3&resource=https%3A%2F%2Fapi.biatec.io
```

The token response carries the access token (and never a refresh or ID token; the schema forbids both) (`acr` = `biatec:consent`, bound to the group hash, 300 seconds) and the signed receipt in `consent_receipt` (`schemas/token-response.schema.json`). A step-up receipt signs an empty `binding_message`, because no client text exists.

## 5. Direct entry

A client that already built the group and wants the consent in hand before calling the wallet endpoint (for example to drive its own progress UI) calls the CIBA backchannel authentication endpoint with the exact unsigned group (or the canonical limits request body) plus an optional `binding_message`. Biatec OIDC decodes the group and builds `authorization_details` exactly as in the step-up entry. A request that carries `authorization_details` is invalid.

```http
POST /connect/ciba
Content-Type: application/json
```

```json schema=backchannel-authentication-request
{
  "scope": "sign",
  "resource": "https://api.biatec.io",
  "login_hint": "user@example.com",
  "network": "algorand-mainnet",
  "address": "YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE",
  "unsigned_group": ["gqNzaWfEQ...base64 unsigned transaction..."],
  "binding_message": "Invoice 2026-0042",
  "requested_expiry": 300,
  "origin": "https://bank.example"
}
```

```json schema=backchannel-authentication-response
{
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "expires_in": 300,
  "interval": 2,
  "binding_code": "120934"
}
```

(The wire encoding of the endpoint follows CIBA, form-encoded; JSON is shown for readability and is what the schema validates.) The client then displays the binding code, obtains the token as in section 4 and presents it to the wallet endpoint, which checks the hash as usual.

`binding_message` is rendered on the card, under the decoded facts and visibly attributed to the client, only for a client whose domain is proven. For any other client it is not rendered and therefore signed as the empty string; the raw text is kept only in the unsigned request log. A client without a proven domain therefore has no free-text channel to the trusted surface.

### 5.1 One model, two entries

Both entries produce the same request object, the same receipt schema, the same canonical form and the same signing rules. Receipts differ only in field values (`binding_message`, `client_fingerprint`, the detail fields). In `vectors/receipts.json`, `stepup-*` and `direct-*` vectors validate against identical schemas.

The client retrieves the receipt in the CIBA token response (`consent_receipt`) and again at `GET /consent/receipts/{auth_req_id}`, only as the client the request belongs to: the one that opened it (direct entry) or the one whose token was challenged (step-up entry).

**Who is asking.** Biatec OIDC vouches for no client. The `client` object has exactly:

- `fingerprint`: 16 lowercase hex characters, the first eight bytes (64 bits) of the SHA-256 of the `client_id`, shown to the user as `xxxx-xxxx-xxxx-xxxx`. The fingerprint is for the user's eyes: a client is linked and trusted by its full `client_id` at Biatec OIDC, never by this value alone. Matching a chosen client's fingerprint takes about 2^64 hashes, which is out of reach of casual attackers and within reach of very large clusters, so the user must still compare the proven domain, which an impostor cannot have.
- `domain_proven` and `domain`: true, and the ASCII (A-label) host, when the client proved control of that domain by serving `/.well-known/biatec-client.json` that lists its `client_id`; otherwise false and no `domain`.
- `linked`: whether this user already linked this client on their phone.

A renderer shows the proven domain, or "Unproven application" in the warning style with the fingerprint, and the user's own label for the service when they set one beside it. It never shows a name or a logo taken from the operator or from the client.

## 7. The binding code

Biatec OIDC generates a six digit binding code (`schemas/binding-code.schema.json`) and returns it only to the client. The authenticator does not display it; the user types the code shown on the requesting surface into the authenticator to approve. The user has three attempts in total within the request's validity. The third wrong code produces a denial recorded as `code_failed`; an explicit Deny produces a denial recorded as `deny`. Only explicit denies count toward the denial counter of section 11. The code the user entered is part of the signed receipt.

## 8. The signed receipt

The device signs the RFC 8785 canonical form of exactly this object (`schemas/consent-receipt-signed.schema.json`):

```
{ authorization_details, auth_req_id, client_fingerprint, binding_code, decision, expiry, sub, binding_message }
```

and, for an `approve` only, a ninth member `remember` (below).

- `client_fingerprint` is the fingerprint of section 6.
- `decision` is `approve`, `deny` or `code_failed`.
- `expiry` is Unix time in seconds.
- `binding_message` is the text as rendered, or the empty string if none was rendered.
- `auth_req_id` is the single-use nonce.
- `sub` is the pairwise subject of the requesting client, so the client can match it against its own session and nothing linkable across clients is signed. The device does not compare it with its own subject. The attestation of the receipt is minted by Biatec OIDC for this subject when the receipt is stored.
- `remember` is `{ "applications": [<application ids>] }`: the applications of this request the user chose to trust for this client. Each id MUST be an application of the request's `authorization_details` that the card offered to trust (its `trusted` is false) and the request's application ids are unambiguous (a verifier checks it against the stored request; the user can only trust what the card offered); it is refused on `deny` and `code_failed`. One biometric prompt covers the approval and the trust.

Signing procedure:

1. Build the object above from the request fetched in section 6 and the code the user typed.
2. Canonicalize it with RFC 8785. All amounts are strings; integers MUST be at most 2^53 - 1.
3. Sign the UTF-8 bytes with ES256 (ECDSA P-256, SHA-256) using the **approval key** for `approve`; `deny` and `code_failed` may use either key. The signature is the 64-byte IEEE P1363 `r || s` form, base64url without padding; verifiers MUST reject non-canonical encodings.

The receipt envelope (`schemas/consent-receipt.schema.json`) adds `version` (`"1.1"`, or `"1.2"` for a relying-party receipt), `alg`, `signature`, `issued_at` (informational, unsigned) and `device`: the key ID, the informational `key_use`, the device public key as a JWK, and the **attestation**, a compact ES256 JWS signed by a Biatec OIDC JWKS key whose payload binds `sub`, `device_kid`, `device_jwk_thumbprint` (RFC 7638 thumbprint of the device public key) and `biatec_key_use`, which is `approve` or `presence`.

Worked example, the first vector in `vectors/receipts.json` (canonical bytes, one line):


### 8.1 Offline verification

Anyone with the Biatec OIDC JWKS verifies a receipt without further lookups:

1. Validate the receipt against the schema.
2. Verify the attestation JWS with the JWKS key named by its `kid`.
3. Check that the attestation header `typ` is `biatec-device-attestation+jwt`, that its signing key is an EC P-256 signature key of the Biatec OIDC JWKS, that its `iss` is the expected issuer, that its `exp` is in the future (verifiers use a trusted clock), and that its `sub` equals `signed.sub`, `device_kid` equals `device.kid` and `device_jwk_thumbprint` equals the thumbprint of `device.public_key`. For version 1.1 the attestation MUST carry `biatec_key_use` (`approve` or `presence`), `device.key_use` MUST equal it, and an `approve` receipt MUST carry the use `approve`: a receipt that approves but is signed by a presence key is refused however valid its signatures are (`vectors/receipts.json` contains such a vector, named `...-REFUSED`).
4. Canonicalize `signed` (RFC 8785) and verify `signature` over its UTF-8 bytes with `device.public_key`.
5. For authorization, compare every signed member (`authorization_details`, `auth_req_id`, `client_fingerprint`, `binding_message`, `expiry`, `sub`) and the bound hash with the stored request the verifier is waiting on, never with data the receipt supplies. Additionally require `decision` = `approve` and that `binding_code` equals, in constant time, the code Biatec OIDC issued for this `auth_req_id` (number matching, rule 2), compare the `signed.authorization_details` hash fields with the group or body presented, check `expiry`, and mark `auth_req_id` spent only when the signing call actually proceeds (rule 5); a verification that is followed by a failed signing call leaves the consent unspent. A verifier MUST NOT treat a `deny` or `code_failed` receipt, or an expired one, as consent. Verification helpers return a boolean and never throw on malformed input.

`version` is not part of the signed object, so no rule may depend on it alone: the signed object's members must agree with it (`client_fingerprint` for 1.1, the 1.0 client member for 1.0), an attested `biatec_key_use` is honoured whatever `version` says (a device with a key use can never approve with a presence key by relabelling the receipt `"1"`), and the stored request, not the receipt, decides which version applies (`verifyApproval` refuses a 1.1 request answered by a 1.0 receipt and the other way round). A 1.1 receipt is authorized only for a device the caller holds as active (`opts.deviceActive === true`; the attestation of a pending device is valid too).

A relying party that pinned the device's public keys when the user linked it can verify the device signature itself and treat the attestation as a second check.

Reference implementations: `scripts/lib.mjs` (JavaScript; `verifyReceipt` covers steps 2-4 and `verifyApproval` step 5, which also matches the receipt against the stored request) and `backend/Biatec.Chat.Tests/Canonical/ConsentProtocolVectorTests.cs` (.NET, using the backend `JsonCanonicalizer`). Both verify every vector signature, honour the `expected` verdict of every vector including the refused ones, and enforce the key-use rule; the .NET test also verifies the attestation.

### 8.2 Statements signed by the approval key of an active device

Two more objects are signed with the **approval key** of an **active** device, canonicalized with RFC 8785 exactly like a receipt, and carried with the device block and its attestation (`schemas/device-signed.schema.json`). `verifyReceipt` establishes that a receipt is authentic and says nothing about whether the device is active; authorization (`verifyApproval`, with `opts.deviceActive`) is where that is decided. Verification of these statements is the receipt's: signature over `JCS(signed)` by `device.public_key`, the attestation (which binds the device key and, for a settings change, `signed.sub`), the attested `biatec_key_use` MUST be `approve` (a presence key is refused), the key named inside the statement MUST be the key that signed, and `issued_at` MUST be within 300 seconds of the verifier's clock. A settings change keys its per-client changes by `client_id` (1 to 200 printable characters), lists each application at most once, and does not add and remove the same application in one change; the verifier and the schema agree on all three. The nonce is used once per device. A device approval carries no subject of its own, so the verifier says whose approval it accepts: the approver's attestation MUST be for the subject (account) of the device being enrolled, and Biatec OIDC checks that both devices belong to the same account; an active device of another account cannot approve. The approver MUST be an active device (an inactive device, including the one being enrolled, cannot approve) and is never one of the keys being enrolled; application id 0 is an application creation: it is never trusted, never in a trusted list and never in `remember`; the nonce of every statement and of the enrollment challenge MUST be 16 to 128 characters of the base64url alphabet (so the pairing code input has one reading) and is accepted once per device, so a verifier needs the set of nonces it already accepted, MUST add a nonce to that set when it accepts the statement, and MUST keep each nonce until 300 seconds after the statement's own `issued_at` plus the clock skew it tolerates (a statement issued up to 300 seconds ahead stays valid for up to 600 seconds after it was accepted, so keeping a nonce 300 seconds from acceptance is not enough). Checking the set and adding to it is ONE atomic operation (an insert that fails if the nonce is present, such as `SET NX` in Redis); two concurrent requests with the same statement must not both pass. `verifyDeviceSigned` in `scripts/lib.mjs` implements it (`expect.sub`, `expect.approval`).

**Settings change** (`schemas/settings-change-signed.schema.json`). A change that loosens protection (raising a threshold, turning a protection off, trusting an application, lifting a pause) needs this statement; tightening needs none. Biatec OIDC classifies the change itself. The threshold belongs to the user: the schema has no ceiling, and `0` asks for everything.

```json schema=settings-change-signed
{
  "type": "biatec_settings_change",
  "sub": "pw_a9e3c0417b5d2f86",
  "kid": "device-test-key-1",
  "nonce": "n-7eb064c2a94489ba608c95cf3aaf54",
  "issued_at": 1792425630,
  "change": {
    "threshold_eur": "5000",
    "clients": {
      "bank-example-client": { "trusted_applications_add": [{ "network": "algorand-mainnet", "app_id": 1234567 }] }
    }
  }
}
```

A user's own text (`label`, at most 40 code points) is Unicode NFC, not blank and without padding or runs of spaces, without control characters, bidirectional controls (U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F, U+061C), zero-width characters (U+200B to U+200D, U+2060, U+FEFF), line breaks, other white space, format characters, filler or invisible characters (soft hyphen, Hangul fillers, invisible operators, variation selectors, tag characters), bare or stacked (more than three) combining marks; ZWNJ and ZWJ are allowed after a letter, mark, symbol or digit and before a letter, symbol or digit (never before a mark or a selector) and U+FE0F right after a symbol, a digit, '#' or '*' (the keycap bases) (never at an end, next to white space or several in a row), so Persian and Indic text and emoji sequences can be labels; the character classes are those of Unicode 16, and a verifier whose Unicode tables are older than Unicode 16 may refuse a character newer than its tables (the verdict on such a character is implementation-defined, so a label with a very new emoji may be refused by an older runtime), so implementations should use Unicode 16 or later; look-alike letters of another script are not detected, which is why a label is shown beside the proven domain or fingerprint and never instead of it; a violation is refused, never stripped (`isDisplaySafe` in `scripts/lib.mjs`; `verifyDeviceSigned` applies it to every label, refuses unknown members, a pause without its `origin` and an `unlink` combined with anything else).

**Approval of a new device** (`schemas/device-approval-signed.schema.json`). A device that enrolls is active at once only when this statement from an existing active device covers its two keys and the enrollment nonce and carries the pairing code the user compared on both phones (or a recovery code is used). Naming a `kid` proves nothing.

### 8.3 Enrollment: the proof and the pairing code

The enrollment nonce is consumed once by the server when it accepts the proof; the same value then appears as the `nonce` of the approver's `biatec_device_approval`, which is tracked in the approver's own set of used statement nonces, so the two are separate namespaces. A new device sends, in `POST /devices`, an **enrollment proof**: a compact JWS (`schemas/device-enroll-proof.schema.json` describes its decoded header and payload) with `typ` `biatec-device-enroll+jwt`, signed with ES256 by the new **approval** key, which it carries as the header `jwk`. The payload is `{ kid, presence_kid, presence_jwk_thumbprint, nonce, iat }`: it names the approval key, names the presence key by its RFC 7638 thumbprint, and carries the nonce of the server's challenge. The device also sends a `presence_proof`: a second compact JWS, `typ` `biatec-device-enroll-presence+jwt`, over the SAME payload, signed by the presence key, which it carries as its header `jwk`; without it a key named only by its thumbprint would not have proven possession (anyone's public key can be named). The server checks the signature under the header `jwk`, the nonce, that the thumbprint is that of the presence public key the request also carries and the `presence_proof` verifies under that key, and `iat` within 300 seconds. `verifyEnrollmentProof` in `scripts/lib.mjs` implements it.

The **pairing code** is a human check, not a secret: it lets the user confirm that the phone they are holding and the new device they are enrolling are looking at the same enrollment (it is not meant to resist someone who controls the new device, who can pick its keys freely; that is what the 24 hour delay, the notices and the requirement that an ACTIVE device signs are for). It is the six digit number both phones show: the first four bytes of `SHA-256(new_approval_jwk_thumbprint + "." + new_presence_jwk_thumbprint + "." + nonce)` read as a big-endian unsigned integer, modulo 10^6, zero padded to six digits. Worked example (`vectors/device-signed.json`, `pairing_code`):

```
input   cpXj3K7c4_bBd9lXxKoO8aZPwTwuPMGzwnYgg3rG_jY.hOlyodNi_jjK_piu5kSIQkvt2q5zwnCUtO8iVYQtwlw.enroll-nonce-53bcbb91525547bf679e9d4f
sha256  5969c03c8789e9dfc7c532ebd67bdd77dc384b9bd84399d68bdccb06bee32c28
uint32  1500102716   (0x5969c03c)
code    102716       (1500102716 mod 1000000)
```

### 8.4 Verification of relying-party receipts (attestation mode)

For a receipt of version `"1.2"` the steps of section 8.1 apply with these additions (`verifyReceipt` covers them, `verifyApproval` adds the stored request):

1. The signed object has exactly the nine members of section 8, `authorization_details` has exactly one object of a relying-party type that satisfies its schema, the text rules of [15. Text rules](#15-text-rules) hold for every string, the IBAN check digits and the amount and date rules of section 3.3 hold, `binding_message` is the empty string and `decision` and `binding_code` have the shapes of the schema (an explicit deny may carry an empty code).
2. `details_hash` equals, compared in constant time, the hash of section 3.6 computed from `authorization_details[0]`: it is never accepted because it is there. A receipt whose hash differs is refused however valid its signatures are.
3. An `approve` MUST be signed by an approval key (attested `biatec_key_use` `approve`); a payment, a login or an action approved with a presence key is refused. `deny` and `code_failed` accept either key. There is no other way to approve: this is the same rule as for wallet receipts, and the relying-party types have no application trust and so no `remember`.
4. `version` is not signed: a receipt whose details are of a relying-party type and whose `version` is not `"1.2"`, or the reverse, is refused, and so is a `version` `"1.2"` receipt without `details_hash` or with `group_hash` or `remember` anywhere.
5. For authorization, `verifyApproval` additionally requires that the stored request is a direct request of a linked client (`entry` `direct`, `client.linked` true), that the signed `authorization_details` equal the stored ones, that `bound_hash` equals the signed `details_hash`, that the request's `origin` is the origin inside the details (both absent, or equal) and the number matching, expiry, single-use and active-device rules of section 8.1.

### 8.5 Verification with a pinned device key (no attestation)

A relying party that pinned the device's public keys when the user linked it (section 14.3) can verify a receipt of its own request with those keys alone and without Biatec OIDC's JWKS, its attestation or any request to a Biatec server. This mode is defined for version `"1.2"` receipts only: `verifyReceiptPinned(receipt, pinned, expectedDetails, opts)` in `scripts/lib.mjs`. The relying party passes the object it sent (`expectedDetails`), never the details of the receipt. It returns true only when all of these hold:

1. The signed object is well formed as in 8.4 step 1 (the text rules apply to what the user was shown, not only to what the party meant to send).
2. `details_hash` is the hash of the signed details, computed by the verifier (8.4 step 2).
3. The signed details equal `expectedDetails` member for member (compared as canonical forms), except `origin`: Biatec OIDC added it. The origin is **explicit**: the party passes `opts.origin`, the origin it reported (a string) or `null` when it reported none, and the signed details must carry exactly that (an `origin` that is absent from `opts` is refused, so is an `expectedDetails.origin` that differs from it). The verifier never accepts "whatever the server added".
4. The signature over the canonical form of the signed object verifies under a pinned key. Each pin says whether it is an approval or a presence key; an `approve` is accepted only under an approval pin (a presence key never approves), `deny` and `code_failed` under either. The receipt's own `device` block is not consulted: a pinned key is the only trust anchor.
5. The party's own values, all REQUIRED (they are what ties the receipt to the request the party opened, and the party knows every one of them): `opts.auth_req_id` (the id it got when it opened the request), `opts.sub` (the subject it used as `login_hint`), `opts.clientFingerprint` (`clientFingerprint(client_id)`), `opts.bindingCode` (the code it displayed; compared in constant time for an `approve`) and `opts.consumed` (a Set of the ids it already acted on: an id in it is refused). The function never adds to the set: **the caller records `auth_req_id` after it got true, atomically with acting on it** (before the payment is executed), so a replay of the same receipt is refused. Optional: `opts.decision` (the decision the caller requires) and, for an approval, `opts.now` (default the current time; an approval must not be expired; `opts.checkExpiry === false` re-verifies an archived receipt, with a fresh `consumed`).

True means the receipt is authentic and is about what the party sent; the party then reads `signed.decision`. The attestation, when the party also checks it, is a second check: a party that trusts Biatec OIDC's key may additionally run the steps of 8.4.

## 10. Third-party integration

1. Self-register with RFC 7591 Dynamic Client Registration, declaring `backchannel_token_delivery_mode` and the `authorization_details_types` used, and a `client_uri`. Capabilities needing the `manage-limits` scope stay reserved for operator-allowlisted clients.
2. Prove the domain: serve `/.well-known/biatec-client.json` with the `client_id` listed. Without it the user sees the client as "Unproven application" with its fingerprint.
3. Use the direct entry (section 5) or handle the step-up challenge (section 4). In both cases display the returned binding code, poll or receive the token, and present it to the wallet endpoint.

The user links the client on their phone the first time they approve a request of it; every request of a client that is not linked asks the phone, whatever the value.

A relying party (an organisation that asks the user to confirm its own payments, logins and actions) follows [14. Relying parties](#14-relying-parties) instead: it registers with `private_key_jwt`, is linked by the user, and verifies receipts with the keys it pinned.

### 11.1 Requester identity and cooling-off

- **Rule 3.** Biatec OIDC vouches for no client. The authenticator shows a client's proven domain, or "Unproven application" with a short fingerprint of its `client_id` in a warning style, and nothing else about it. The user's own label for a service is shown beside it, never instead of it. The user's policy may block clients without a proven domain entirely. A user trusts an application by ticking it on the approval card, which signs it into the approve receipt (`remember`); there is no operator list.
- **Rule 4.** For a user with an active enrolled device, every client that registered less than 24 hours ago, and the first request of any client the user has not linked yet, requires phone approval regardless of value, as if the threshold were zero. Approving that first request links the client. An enrolled but still inactive device counts as no active device. For a user with no active device, Biatec OIDC instead applies a reduced per-client daily cap (default 100 EUR) during the client's first 24 hours and the user's first day with the client.

### 11.2 Validity and consumption

- **Rule 5.** A consent is valid for 300 seconds by default, bound to one group hash, and authorizes exactly one signing call. It is spent only when Biatec OIDC actually signs; a call failing the hash check, the spending limits or any other validation leaves it unspent. The signing endpoint signs for one sender address per call, so an action needing two senders is two groups, two signing calls and, if each needs it, two consents. A Bitcoin transaction in version 1 spends from one address; a transfer needing several addresses is split into one transaction per address, each with its own group hash. Biatec OIDC rejects a signing request whose group hash differs from the consented hash.

### 11.3 Device keys, enrollment and recovery

- **Rule 6.** The authenticator holds two hardware-backed key pairs and an enrollment identifier, and no wallet keys, cloud-storage tokens or long-lived OAuth tokens. The **approval key** is created so that the operating system itself requires a strong biometric for every signature and invalidates it when the biometrics change; it signs `approve` receipts, settings changes and approvals of new devices. The **presence key** is usable while the device is unlocked; it signs device proofs on every HTTP call, `deny` and `code_failed` receipts. Each key has its own `kid` and its own attestation with `biatec_key_use` set to `approve` or `presence`. The keys are generated in hardware and attested at enrollment; the attestation is presented again when receipts are posted.
- **Rule 7.** Enrollment starts with a fresh full Biatec OIDC login inside the authenticator, including the identity provider's multi-factor step. The device is active at once only when an already active device signed a device approval (section 8.2) after the user compared the pairing code on both phones, or a recovery code is used. Otherwise (first device or lost-device recovery) it is enrolled but inactive for 24 hours; every other device and the user's email address receive a cancel link, and during that period a user with no other active device cannot complete any action needing phone approval. A recovery code, generated and shown once only after a device has become active, activates a later device immediately.
- **Rule 8.** A user without an active enrolled device can use every below-threshold capability (subject to the reduced caps of rule 4) but cannot complete an action needing phone approval. The default threshold is not lowered for such users.

### 11.4 Denial, pending limits and pause

- **Rule 10.** A denial produces a signed denial receipt (`decision` = `deny`) and immediately cancels the pending action in the requesting surface. Denials never auto-block a client. Biatec OIDC allows at most three pending requests per client per user per origin (origin is reported by the client with each request), rate-limits new requests as an anti-spam measure only (default 60 per hour per client per user, no per-second burst limit), and after three explicit denials in a day the authenticator offers a one-tap "pause this client on this site for 24 hours", scoped to the reporting origin and liftable from the linked-services screen. `code_failed` denials do not count toward the three.

### 11.5 Limits

- **Rule 11.** Authenticator approval never bypasses spending limits; it is an additional requirement. Biatec OIDC's per-user limits cover the user's own addresses only; funds inside a Biatec Safe are governed by the safe's on-chain signer-group limits plus the consent threshold applied to each approval.

## 12. Threshold, loosening and tightening

The threshold is the user's. A new account starts at 1000 EUR: any single action valued above the user's threshold, or whose value is unknown, requires authenticator approval. The user can set any threshold on their phone, including 0 (ask for everything), and per-client thresholds; there is no ceiling unless a deployment sets one. Any change that loosens protection (raising a threshold, turning "always ask" off, lifting a pause, trusting an application) is itself a statement signed by the approval key of an active device (section 8.2, or `biatec_limits_change` for spending limits); tightening applies immediately. The threshold and the user's per-client settings are stored and enforced by Biatec OIDC at the signing endpoint. A client may ask for more consent (`requireConsent: true`) but never less.

## 13. Changes from 1.0

Version 1.1 is additive where it can be and replaces 1.0 as the only version implementations produce. No production receipt of 1.0 exists. Schemas keep a 1.0 branch so that 1.0 receipts, requests and details keep validating; `vectors/receipts-1.0.json` is that frozen set.

1. **Whole-group details.** `biatec_transaction` lists every outgoing transfer (`transfers`) and every application (`applications`) instead of one summary line; the single-transfer members (`receiver`, `asset`, `amount`, `application_id`) are 1.0 only.
2. **Unknown value.** `value_known` says when the value could not be priced or an application is not trusted; the total `fiat_value` is present exactly when it is true.
3. **Signed origin.** `origin` (as the client reported it) is a member of the details, so a receipt proves which origin the user saw.
4. **`group_hash`** is the Algorand group id recomputed from the handed transactions (for one ungrouped transaction its transaction id), base32, 52 characters; the `sha256:` form that appeared in `docs/required-changes-biatec-oidc.md` is dropped.
5. **Subject.** `signed.sub` is the pairwise subject of the requesting client; the attestation is minted for that subject when the receipt is stored; the device does not compare it with its own.
6. **Two keys.** An approval key (biometric-bound) and a presence key, each with its own attestation carrying `biatec_key_use`. Verification step 3 gains the key-use rule: an `approve` receipt MUST carry `approve`. Device proofs and `deny` / `code_failed` receipts may use the presence key. The envelope carries `version` `"1.1"` and `device.key_use`.
7. **New signed objects.** `biatec_settings_change`, `biatec_device_approval` and the enrollment proof (sections 8.2 and 8.3), with schemas and vectors, and the pairing code definition with a worked example.
8. **The client is not vouched for.** The request's `client` object is `{ fingerprint, domain_proven, domain?, linked }`; the 1.0 members that asserted an operator-vouched name, a verified flag or a federation entity id are 1.0 only. The signed object names the client by `client_fingerprint` instead of the 1.0 entity member. The fingerprint is 16 lowercase hex characters (shown `xxxx-xxxx-xxxx-xxxx`). `binding_message` is rendered only when the domain is proven.
9. **User-held trust.** `remember` in an approve receipt trusts applications for a client; the user sets the threshold (no ceiling), links clients, and trusts applications on their own phone (rules 3, 4 and section 12). There is no operator list of clients, applications or test-network prices.
10. **Device channel.** The authenticator learns of a request from a hint over Biatec OIDC's own device channel (or a platform push); no third-party push relay is part of the protocol.

## 14. Relying parties

Biatec Authenticator is a universal authenticator: any organisation can adopt it as its confirmation app for payments and for access to its internet banking. Biatec vouches for nobody. The organisation proves its domain, the user links it on the phone, and the organisation can verify every approval against the device key it saw at linking. The trust claim is exactly this: after it pinned a device key the party does not depend on Biatec OIDC for what a receipt for that key says; for WHICH keys are the user's at link time it does (14.1, 14.6). The server side is specified by Biatec OIDC (issue 38 of the Biatec OIDC repository); this chapter is the contract between it, the authenticator and the relying party. `docs/relying-party-protocol.md` points here.

### 14.1 Trust model

Four statements hold and nothing in this chapter may weaken one:

1. **Biatec OIDC vouches for no relying party.** The phone shows the domain the party proved (section 6) or "Unproven application" with the fingerprint, and the user decides. No name, logo or badge comes from the operator or from the party.
2. **A relying party reaches a user's phone only after that user linked it on the phone.** Linking is a statement signed by the approval key (14.3). A request for a subject that is not linked is refused (`400 unknown_user_id`); no request of a relying party opens before that, whatever its content.
3. **What the user approves is exactly the `authorization_details` the relying party sent.** The card shows them in fields the app renders itself (plain text, never markup, links or images), the strings marked as written by the relying party, and the device signs their hash (section 3.6). Server-side thresholds, application trust and first-use rules do not apply to these requests: they always go to the phone.
4. **The receipt is signed by the device.** Biatec OIDC adds an attestation, but a relying party that pinned a device key verifies the device signature itself (8.5): after pinning, the operator cannot alter or forge the content of a receipt for that key, and a receipt signed by another key is detected. The limit: the pinned keys come from the server's own answer at link time, so the party trusts the operator for which keys are the user's at that moment (14.3 step 7, 14.6).

A relying party is never given a wallet capability: it can never obtain `sign`, `manage-limits`, `enroll-device` or any wallet scope, and the access token it redeems for a request has scope `openid` only, `acr` `biatec:consent` and a `consent_hash` (the `details_hash`) and is refused by every endpoint of Biatec OIDC (the signing endpoint, userinfo, the device endpoints). What the party needs is the receipt.

### 14.2 Registration

A relying party registers itself with RFC 7591 Dynamic Client Registration as a confidential client:

- `token_endpoint_auth_method` `private_key_jwt`, with `jwks` (inline; at most 4 keys; EC P-256 or RSA of 2048 bits or more; no private members) or `jwks_uri` (https; fetched like the well-known file below and cached for one hour). No client secret is ever issued.
- `grant_types` containing only `urn:openid:params:grant-type:ciba`; no redirect URIs.
- `client_uri`: required, an absolute https URL with a host name (not an IP address), as for every client.

Client authentication follows RFC 7523: the assertion's `iss` and `sub` are the `client_id`, `aud` is the token endpoint or the issuer, `exp` is at most 5 minutes ahead, the `jti` is single use (an assertion replayed within its lifetime is refused) and the algorithms are `ES256` and `PS256` only (`none` and HMAC are refused). Such a client can use only the CIBA endpoint and grant, the link endpoints (14.3) and receipt retrieval; every other endpoint answers `401` or `403`.

The party proves its domain by serving `https://<host of client_uri>/.well-known/biatec-client.json` with the body `{ "client_ids": ["<client_id>"] }` (at most 50 entries). Biatec OIDC fetches it with a hardened fetcher and re-checks it daily. Without it the user sees the party as "Unproven application" with its fingerprint, `domain` in the link statement is `null`, and the user decides on that basis. Registration is rate limited per source address.

### 14.3 Linking

Linking is how the user establishes trust, and it is the only way a relying party reaches a phone.

1. **The party starts a link** inside its own authenticated session with `POST /consent/links` (client authentication), body `{ "user_label"?: string }` (at most 40 characters, text rules of section 15: what the party calls this user, for example a masked name). The answer is `201` (`schemas/link-created.schema.json`) with the `link_id`, the `link_uri`, a six digit `binding_code`, `expires_in` (300) and `interval` (2).
2. **The link code** is the `link_uri`, shown as a QR code: `biatec-authenticator://link?iss=<issuer>&id=<link_id>&s=<link_secret>`. `iss` is the percent-encoded issuer of the Biatec OIDC the party registered with, `id` the `link_id` and `s` the 32 random bytes of the link secret as base64url (43 characters, stored hashed by the server). The query has exactly these three members in this order. **The app refuses a link code whose `iss` is not the server it is enrolled with**, before it sends the secret anywhere. The six digit `binding_code` is shown next to the QR code and typed on the phone (the binding-code rules of section 7: three attempts).
3. **The device fetches the request** with `GET /consent/links/{id}`, header `X-Link-Secret`, device authentication of an **active** device (`schemas/link-request.schema.json`): the `client` (fingerprint, `domain_proven`, `domain` when proven), the `user_label` (shown as reported by the service), a `nonce` and `expires_at`.
4. **The user decides** on the phone: the card shows the proven domain, or "Unproven application" with the fingerprint, and the label as written by the service. Approving needs the binding code and the approval key (biometrics). The device signs the `biatec_link` statement (`schemas/link-signed.schema.json`) and posts it with `POST /consent/links/{id}/receipt` as `{ "signed", "signature" }`, again with the header `X-Link-Secret` (**required**: a missing or wrong secret is `404`, as for the fetch).
5. **The statement** is `{ type: "biatec_link", link_id, client_fingerprint, domain (string or null), decision: "approve" | "deny", binding_code, nonce, issued_at, kid }`, signed (ES256, IEEE P1363, base64url) over its RFC 8785 canonical form by the **approval key** for `approve` (either key for `deny`, which carries an empty `binding_code` when no code was typed). `domain` is the proven domain the server showed the device, or `null`: signing it makes the user's decision about that domain, and the server and a verifier refuse a statement whose domain, fingerprint, link id, nonce or code differ from what was shown and issued, whose `issued_at` is not within 300 seconds of their clock, or that is used a second time.
6. **The party polls** `GET /consent/links/{id}` (only the client that created it; polling faster than `interval` answers `slow_down`; `schemas/link-status.schema.json`): `status` `pending`, `linked`, `denied` or `expired`. When `linked` it carries the pairwise `subject` (the `login_hint` of every later request), the `devices` (the `kid`, `key_use` and public JWK of the approval and presence key of each active device of the account) and the `approval` (`signed`, `signature`, `attestation`). When `denied` it carries the `approval` of the denial.
7. **The party verifies and pins.** With `verifyLinkPinned(approval, devices, expect)` the party checks that the statement is the user's: the signature under the device named by `signed.kid` (an approval needs that device's `key_use` to be `approve`), the link id, its own fingerprint, the domain it expects, the nonce, the code it showed and the time. The party passes the answer's `approval` with `alg: "ES256"` (the answer names none) and a `consumed` Set of link ids it already acted on (the caller records `link_id` after true). On success it pins the `devices` of the answer (14.6). The limit, stated exactly: the `devices` list comes from the same server answer as the link approval, so at link time the party trusts Biatec OIDC for WHICH keys it pins (an operator that lied could present keys of its own). Once pinned, the operator cannot alter or forge the content of a receipt for that key, and a receipt signed by any other key is detected and refused. The party does not need the user to confirm the key out of band; it can reduce the exposure by pinning at the first link only, treating every later change of the list as a decision of its own policy (14.6), and keeping the receipts it checked. `verifyLink(envelope, jwks, opts, expect)` is the same check with the attestation, which Biatec OIDC runs at `POST /consent/links/{id}/receipt` and a party may run as a second check.
8. **Unlinking.** The party removes its own link with `DELETE /consent/links/subject/{subject}`; the user removes a link on the phone at any time (tightening, no statement needed). Requests of the party that were still open when the link went are closed with a distinguishable outcome: the token endpoint answers `400 access_denied` with `reason: "unlinked"` (a deny by the user has none, a third wrong code has `reason: "code_failed"`) and there is no receipt (14.4).

Worked example, the first vector of `vectors/link.json` (`link-approve-domain-proven`). What the party gets from `POST /consent/links`:

### 14.4 Direct requests

A linked relying party opens a request with the CIBA backchannel authentication endpoint (`POST /connect/ciba`, client authentication with its `private_key_jwt`, `schemas/backchannel-authentication-request.schema.json`): `scope` `openid`, `login_hint` the linked `subject`, `authorization_details` with exactly one object of the types of sections 3.3 to 3.5 (without `origin`), optionally `origin` (the origin of the party's session, which Biatec OIDC records inside the details as the party reported it) and `requested_expiry`. There is no `binding_message`.

```json schema=backchannel-authentication-request
{
  "scope": "openid",
  "login_hint": "pw_5e2b9d0c71a84f36",
  "authorization_details": [
    {
      "type": "biatec_payment",
      "instructed_amount": {
        "amount": "1250.00",
        "currency": "EUR"
      },
      "creditor_name": "Muster Energie GmbH",
      "creditor_account": {
        "iban": "DE89370400440532013000"
      },
      "remittance": "Invoice 2026-0042",
      "execution_date": "2026-10-20"
    }
  ],
  "origin": "https://netbanking.bank.example",
  "requested_expiry": 300
}
```

- Unknown members, a schema violation, an IBAN with wrong check digits, a text-rule violation or an `origin` the party put inside the object are refused with `400 invalid_authorization_details`; nothing is stripped or corrected. An unlinked or unknown `login_hint` is `400 unknown_user_id`, for a party the user unlinked as well, and for a subject that never existed (the answer does not say which).
- The request always goes to the phone: the threshold, trusted applications and first-use rules do not apply. The pause of a client on a site, "block unproven clients", the open-request cap (at most five pending requests per user and client) and the rate limit (60 requests per minute per client) do, and a user with no active device cannot be asked (`403 consent_unavailable`).
- The answer is that of section 5 (`auth_req_id`, `expires_in`, `interval`, `binding_code`). The party displays the binding code inside its own session and the user types it on the phone, as for every request (rule 2).
- The party polls the token endpoint as in section 4. The token it redeems has scope `openid` only and is useless anywhere. The receipt is returned in `consent_receipt` of the token response and at `GET /consent/receipts/{auth_req_id}`, only to the party the request belongs to. A request closed because the link was removed (by the party or on the phone) ends with `400 access_denied` and `reason: "unlinked"` and has no receipt: the party must not treat it as a denial by the user, and executes nothing.

### 14.5 Receipt verification with a pinned device key

The party verifies the receipt it got, without trusting Biatec OIDC for its content (the keys it pinned decide, 14.1 statement 4), as described in section 8.5: `verifyReceiptPinned(receipt, pinned, expectedDetails, opts)` with the keys it pinned at linking, the object it sent, and its own ids. Only then does it act: a payment is executed, a login completed, an action carried out when `signed.decision` is `approve`; a `deny` and a `code_failed` are results too, and nothing is executed. The party passes the origin it reported (or `null`) explicitly (8.5). Verifying the attestation as well is optional. The party also stores the receipt: it is the user's signed consent to exactly that payment.

### 14.6 A new device and a pinned key

A pinned key belongs to the devices the account had when the party looked. When the user adds a phone, its receipts are signed by a key the party has not pinned: `verifyReceiptPinned` refuses them, correctly, because nothing yet says the new key is the user's. The party asks `GET /consent/links/subject/{subject}/devices` (client authentication), which lists the current approval and presence keys of the account's active devices (`devices` of `schemas/link-status.schema.json`), and decides by its own policy:

- **Accept the new keys**, trusting Biatec OIDC's statement that they belong to this account (the attestation of the receipt says the same). A party that does so trusts the operator for the keys, though never for the content of a receipt.
- **Ask the user to link again**, in the party's own authenticated session, with a link statement from the new phone: the new phone's approval key then signs the user's decision about the party itself. (The key of that phone still reaches the party in the server's answer, so the trust in the operator for which keys are the user's is the same as at the first link; what the party gains is a statement of the user, signed on the new phone, about this party.)

A party removes pins that no longer appear in the list (a phone the user removed or lost) and refuses receipts signed by them. The conformance vector `payment-approve-new-device-unpinned` is a valid receipt that pinned verification refuses until the party decides.

## 15. Text rules

One normative section for every string a relying party supplies (`creditor_name`, `creditor_account.identification`, `creditor_account.scheme`, `remittance`, the `context` members of a login, the `title`, `label` and `value` of an action, the `user_label` of a link) and for the user's own text (the `label` of a settings change, section 8.2). Everything in this chapter is an input rule: a violation is **refused, never stripped, normalized or truncated**, by the server that receives the string and again by the device that renders it, because the device does not trust the server. A string that would be accepted on one reading and refused on another is refused.

1. **Normalization.** Unicode NFC.
2. **Length.** Counted in code points (not UTF-16 units, not bytes): at least 1 and at most the maximum of the member. An optional member is absent, never empty.
3. **No control characters** (general category Cc: U+0000 to U+001F and U+007F to U+009F, which includes the tab).
4. **No bidirectional controls**: U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F and U+061C.
5. **No zero-width characters**: U+200B to U+200D, U+2060 and U+FEFF.
6. **No line breaks**: U+000A, U+000D, U+0085, U+2028 and U+2029.
7. **The rest of the strict set** (`isDisplaySafe`): no other format character (Cf) or private-use character, no white space other than a plain space, no leading or trailing space, no run of spaces, no blank text, no filler or invisible character (soft hyphen, Hangul fillers, invisible operators, variation selectors, tag characters), no combining mark without a base character or in a stack of more than three, and no lone surrogate.

Two profiles share these rules and differ in one point. The **relying-party profile** (`isRelyingPartyText(text, max)`) has no exception: ZWNJ, ZWJ and the emoji selector U+FE0F are refused like the other zero-width and invisible characters, because no payee, title or login context depends on them and the party is untrusted. The **label profile** (`isDisplaySafe(text, max)`, the user's own text) allows ZWNJ and ZWJ after a letter, mark, symbol or digit and before a letter, symbol or digit (never in a run, at an end or next to white space) and U+FE0F right after a symbol, a digit, `#` or `*`, so Persian and Indic text and emoji sequences can be labels; the character classes are those of Unicode 16, and a verifier whose Unicode tables are older may refuse a character newer than its tables. A string the relying-party profile accepts, the label profile accepts as well.

Rules 1 to 6 are the **core**: every implementation MUST apply at least these (Biatec OIDC at the server, the .NET reference test in this repository); the device and every receipt verifier apply all seven rules. A string only the core accepts can be opened as a request and then be refused on the phone, which is safe, never the reverse. `vectors/text-rules.json` lists accepted and refused strings with the profile, the limit and the reason; the vectors with `core: true` are decided by rules 1 to 6 alone. Rule 5 (and rule 7's refusal of the emoji selector) is the relying-party profile's: the label profile allows ZWNJ and ZWJ (U+200C, U+200D) in context and U+FE0F after a symbol, a digit, `#` or `*`, as `isDisplaySafe` does, and refuses the rest of U+200B to U+200D, U+2060 and U+FEFF. So a vector is `core: true` only when BOTH profiles refuse (or accept) it by rules 1 to 6 alone, and every `core` vector today is a relying-party vector without a joiner or selector; the joiner cases are never `core`.

Look-alike letters of another script are not detected, so a relying party's text is always shown as written by the relying party, beside the proven domain or the fingerprint and never instead of them, in plain text, with no markup, link or image interpreted.

## 16. Changes from 1.1

Version 1.2 is additive: nothing of 1.1 changes, `biatec_transaction` and `biatec_limits_change` stay at envelope `version` `"1.1"`, and a verifier that knows only 1.1 refuses a 1.2 receipt as it refuses any unknown version.

1. **Relying parties.** Any organisation can register as a `private_key_jwt` client, be linked by the user on the phone and send payment, login and action requests (chapter 14, `docs/relying-party-protocol.md`). Biatec OIDC vouches for none.
2. **Three request types.** `biatec_payment`, `biatec_login` and `biatec_action` (sections 3.3 to 3.5, schemas `authorization-details-payment|login|action`). Amounts are decimal strings of at most two decimals; the IBAN's check digits are validated.
3. **`details_hash`** (section 3.6): the SHA-256 of the canonical details object, base64url, computed by the device from what it renders; the bound hash and `consent_hash` of these requests. A 1.2 receipt's signed object has it as a ninth member, never `remember`, and an empty `binding_message`; the envelope `version` is `"1.2"` (`schemas/consent-receipt-signed.schema.json#/$defs/v1_2`).
4. **Pinned verification** (section 8.5): `verifyReceiptPinned` verifies a receipt with the keys a relying party pinned at linking and no attestation; an `approve` always needs an approval key (8.4).
5. **Linking.** The `biatec_link` statement (14.3, `schemas/link-signed.schema.json`, `link-request`, `link-created`, `link-status`), the link code `biatec-authenticator://link?iss=<issuer>&id=<link_id>&s=<link_secret>` and the rule that the app refuses an issuer other than its own server. `device-signed.schema.json` accepts the statement as a third device-signed object.
6. **Direct requests of relying parties.** `scope` `openid` and an `authorization_details` object in the backchannel authentication request (`schemas/backchannel-authentication-request.schema.json`); the requests always go to the phone and the token they redeem is useless at every endpoint.
7. **Text rules** (chapter 15): one normative section for every string a relying party supplies and for the user's own text; `isDisplaySafe` gains the relying-party profile (`isRelyingPartyText`).
8. **Request origin.** The request's `origin` is required for wallet types and optional for relying-party types (present exactly when the server had one).
9. **New vectors.** `vectors/receipts-1.2.json`, `vectors/link.json` and `vectors/text-rules.json`; the 1.0 and 1.1 vectors are unchanged.
