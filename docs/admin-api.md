# Admin API (operators)

PRODUCT-DESCRIPTION.md, Chat Backend Responsibilities: *"Expose health, metrics, and an admin API for policy and
knowledge-base management."* This page documents the tenant policy part (T-086) and knowledge-base management
(T-096, [Knowledge base](#knowledge-base)), operator identities and the admin evidence chain (T-097,
[Admin evidence chain](#admin-evidence-chain)), and how operator tenant approval is authenticated and recorded (T-098,
[Operator tenant approval](#post-onboardingoperatortenants-operator-tenant-approval)).

Code: `backend/Biatec.Chat.Api/Admin/`. Tests: `backend/Biatec.Chat.Tests/Admin/`. Operator tenant approval:
`backend/Biatec.Chat.Api/Onboarding/`, tests in `backend/Biatec.Chat.Tests/Onboarding/`.

## Authentication

- The API is for Biatec Chat operators only. Every operator has an **own named bearer key**, so every admin request
  and change is attributed to a named operator:

  | Setting | Value |
  |---|---|
  | `Admin:Operators:<name>:KeyHash` (env `Admin__Operators__<name>__KeyHash`) | hex SHA-256 (64 characters, any case) of that operator's key |

  Only the hash is configured. The key itself is generated by (or for) the operator, at least 32 random characters
  (for example `openssl rand -base64 32`), handed over out of band and never written to configuration, the repo, the
  database or a log. The hash is computed as `printf %s "$KEY" | sha256sum`. Because the hash is unsalted, a key must be
  random, not a password. The hash is not a secret in the strict sense, but treat it like one and inject it from the
  secret store too. No IAM user or access key is involved.
- `<name>`: 1-64 letters, digits, `.`, `_` or `-` (starting and ending with a letter or digit), case-insensitive, and
  not `legacy`. Two operators may not share a key. A malformed entry stops the start (options validation), with one
  error per broken entry naming it and the rule (for example `Admin:Operators:carol:KeyHash is the same as
  Admin:Operators:alice:KeyHash`), so an operator is never silently locked out. The hashes are decoded once at start.
- A presented key shorter than 32 characters is never accepted, for named and legacy keys alike.
- **Legacy shared key (deprecated).** The single `Onboarding:OperatorKey` (at least 32 characters, env
  `Onboarding__OperatorKey`, from a secret) is still accepted, so existing scripts keep working. Requests with it are
  attributed to the operator `legacy` (evidence `operatorAuth: "legacy-shared-key"`), and the first use per process
  logs a deprecation warning. Give each operator a named key and then unset it.
- While neither a named key nor a legacy key is configured every admin route answers `404`: the API does not exist.
- A missing or wrong `Authorization: Bearer <key>` gets `401` and a warning log line with method, path and remote IP
  (never the presented value). The presented key's SHA-256 is compared with every configured hash in constant time, with
  no early exit. Authentication runs before the request body is read, so an unauthenticated request never reaches the
  JSON parser (it gets `401`, or `404` without a key, never `400`).
- The check is shared with the operator onboarding route (`OperatorAuth` in `backend/Biatec.Chat.Api/Onboarding/`),
  which therefore accepts the named keys too, also authenticates before reading its body, and records each approval in
  the admin evidence chain.
- Biatec OIDC has no operator claim or group yet; named keys are the fallback. The intended OIDC-based alternative is
  recorded in [required-changes-biatec-oidc.md, row 23](required-changes-biatec-oidc.md#23-operator-identity-claim-for-the-admin-api-t-097).
- Requests go to any registered tenant host (the tenant middleware resolves every request by `Host`), for example
  `https://chat.biatec.io`. The operator acts on any tenant by id; the host used for the call does not scope it.

### Browser and CSRF posture

The routes sit under `/onboarding/operator/`, which already is the operator surface, so they share its posture:

- No cookie or other ambient credential is used, so there is nothing for a cross-site request to borrow; the CSRF
  guard is not needed and does not apply (`OriginPolicy.IsPublic`).
- `Authorization` is not in the CORS allowed headers, and the operator prefix never gets the `/public` wildcard, so a
  page in a browser cannot send the bearer cross-origin.
- The admin routes have their own rate-limit policy `operator` (per remote IP, `Admin:RateLimitPermits`, default 60,
  per `Admin:RateLimitWindowSeconds`, default 60), counted apart from public onboarding. The onboarding body limit
  (`Onboarding:MaxBodyBytes`) applies. A PATCH body must be `application/json` (else `415`).

## Endpoints

### `GET /onboarding/operator/tenants`

All tenants' policy: `{ "tenants": [ <policy>, ... ] }`.

### `GET /onboarding/operator/tenants/{tenantId}`

One tenant's policy, or `404`.

The policy view is policy only. It never contains `clientSecretRef`, `oidcClientId`, tokens or any secret:

```json
{
  "tenantId": "chat.example-bank.com",
  "host": "chat.example-bank.com",
  "softCapEurPerHour": 1500,
  "effectiveSoftCapEurPerHour": 1500,
  "consentThresholdCeilingEur": 1000,
  "trustAnchorVerified": false,
  "limitsUpdateEnabled": false,
  "x402Enabled": false,
  "bedrockUsdPerWindow": null,
  "safeApprovalCaps": { "approvalsPerHour": 5, "approvalEurPerHour": 2000, "executionsPerHour": 10 },
  "defaultModel": null
}
```

`effectiveSoftCapEurPerHour` is what signing applies (`SoftCapPolicy.EffectiveCapEur`). `bedrockUsdPerWindow: null`
means the deployment default `Budget:TenantUsdPerWindow`. `safeApprovalCaps` shows effective values (stored value or
platform default).

### `PATCH /onboarding/operator/tenants/{tenantId}/policy`

Changes policy fields. Every field is optional; a field that is missing or `null` is left unchanged. `reason` is
required (1-200 characters, no control characters) and goes into the audit log.

```json
{
  "softCapEurPerHour": 3000,
  "trustAnchorVerified": true,
  "limitsUpdateEnabled": true,
  "x402Enabled": false,
  "bedrockUsdPerWindow": 10,
  "safeApprovalCaps": { "approvalsPerHour": 3, "approvalEurPerHour": 1000, "executionsPerHour": 10 },
  "defaultModel": "eu.anthropic.claude-sonnet-4-5-20250929-v1:0",
  "reason": "ticket 42: bank pilot, federation chain checked"
}
```

Answer: `200 { "tenant": <policy>, "changes": ["softCapEurPerHour: 1500 -> 3000", ...] }`, `400 { "error": ... }`
for a refused change (nothing is written), `404` for an unknown tenant.

Rules, enforced server-side:

| Field | Rule |
|---|---|
| any field not listed here | `400`. Identity and secret fields (`host`, `allowedOrigins`, `clientKeys`, `oidcClientId`, `clientSecretRef`, `redirectUri`) are set only by onboarding and cannot be changed here. |
| `softCapEurPerHour` | The same save rule as onboarding (`SoftCapPolicy.ValidateOnSave`, with `byOperator: true`): at least `consentThresholdCeilingEur` (the floor), and above the platform default (1500 EUR) only while `trustAnchorVerified` is true. At most 1 000 000. |
| `trustAnchorVerified` | The operator's attestation that the tenant's OIDC client chains to a recognized trust anchor (no automatic federation check exists yet). Clearing it while the soft cap is above the default is refused: lower the cap in the same or an earlier request. |
| `limitsUpdateEnabled`, `x402Enabled` | Booleans. `x402Enabled` still needs the deployment switch `X402:Enabled`. |
| `bedrockUsdPerWindow` | 0 to 10 000; written to `bedrockBudgets.usdPerWindow`, other keys of that JSON are kept. |
| `safeApprovalCaps.*` | Counts 0 to 10 000, EUR 0 to 1 000 000; merged into the stored JSON. |
| `defaultModel` | An `eu.anthropic.claude-(haiku\|sonnet\|opus)-4-*` inference profile id (Claude 5 isn't available on this account); `""` clears it. Stored now; takes effect once T-085 ships (the runtime does not read it yet). |
| `consentThresholdCeilingEur` | Read-only here: it is the deployment's ceiling, not a per-tenant knob. |

The soft-cap save rule runs when the patch changes `softCapEurPerHour` or `trustAnchorVerified`. A patch of other
fields is never blocked by a stored row that predates the rule, so switching a feature off (for example
`x402Enabled: false`) always works.

Numeric fields are compared as numbers: a value equal to the current effective one (stored value, legacy
`safeApprovalCaps.perHour`, or default) is no change and is not written. The audit line shows the effective old value.

Concurrent changes to one tenant are serialized (a PostgreSQL advisory lock), so two operators never overwrite each
other's read-modify-write.

Request handling reads tenant policy (including the gates `x402Enabled`, `limitsUpdateEnabled`, the soft cap and the
safe caps) from the cached tenant row in `DbTenantStore`. A successful change evicts that row on the replica that
handled it, so it applies there at once. Other replicas pick it up when their entry expires: the cache TTL is 10
seconds, so a gate switched off is off everywhere within 10 seconds.

### `POST /onboarding/operator/tenants` (operator tenant approval)

The operator fallback of tenant onboarding (T-045; flow in [integration-widget.md](integration-widget.md) and
[required-changes-biatec-oidc.md](required-changes-biatec-oidc.md)): after the self-service route answered
`202 pending-operator-approval`, an operator adds the static OIDC client, stores its secret and approves the tenant.
It uses the onboarding rate-limit policy, not `operator`.

- Authentication runs before the body is read, exactly as on the admin routes: no or a wrong bearer gets `401` (with
  the `Operator: rejected unauthenticated ...` log line), `404` while no operator key is configured, whatever the body.
  Only then must the body be `application/json` (else `415`) and parseable (else `400`).
- Body: `{ "request": { host, signInPageUrl, allowedOrigins, clientKeys }, "oidcClientId", "clientSecretRef": "secret://…",
  "reason"? }`. `reason` is optional; when sent it must be 1-200 characters without control characters (else `400`).
  The DNS proofs are re-checked; answers are as before (`201`, `400`, `409`, `422`, `502`).
- A created tenant commits together with its admin chain entry `tenant_approve`, or not at all (a failing append rolls
  the tenant back and the request fails with `500`). Refused approvals are not recorded.
- Log line on success (category `Biatec.Chat.Api.Onboarding.OnboardingService`): `Onboarding: operator {Operator} from
  {RemoteIp} approved tenant {Host}. Reason: {Reason}`.

```bash
curl -sS -X POST https://chat.biatec.io/onboarding/operator/tenants \
  -H "Authorization: Bearer $OPERATOR_KEY" -H 'Content-Type: application/json' \
  -d '{"request": {"host": "chat.example-bank.com"}, "oidcClientId": "static-client",
       "clientSecretRef": "secret://tenants/chat.example-bank.com/oidc-client-secret", "reason": "ticket 7"}'
```

## Knowledge base

`kb.search` serves the seed pages under `Kb:Path` (the `docs/kb/*.md` files shipped in the image) overlaid with pages
operators upload here. Uploaded pages live in the PostgreSQL table `KbPages` (migration `KbPages`), so every replica
serves the same set; no AWS resource is involved. An uploaded page replaces the seed page with the same id; deleting
it brings the seed page back (a seed page cannot be hidden from here).

Uploaded pages are untrusted data, exactly like seed pages: they reach the model only as a `kb.search` tool result
(wrapped in `<untrusted_data source="tool.kb.search">`, excerpt at most 600 characters), never in the system prompt.

Each replica holds an immutable page snapshot and swaps it atomically on reload. Replicas converge in two ways:

- the replica that handles an upload or delete reloads at once;
- every replica polls the table every `Kb:RefreshSeconds` (default 30; `0` turns polling off) and reloads when the
  set of page ids and SHA-256 hashes changed (the poll reads ids and hashes only, not bodies). If the database cannot
  be read, the replica keeps the pages it serves (at start: the seed only) and logs one warning per outage, with the
  PostgreSQL SQL state and message (for example `42P01 relation "KbPages" does not exist`: the migration is not
  applied).

Seed page ids are file names without `.md`. Two seed files with the same name in different subdirectories collide:
the first in ordinal path order is served and each other one is skipped with a warning.

Settings (section `Kb`): `Path` (seed directory, default `kb/` next to the binary), `MaxPageBytes` (default 16384),
`MaxPages` (uploaded pages, default 200), `RefreshSeconds` (default 30).

### `GET /onboarding/operator/kb/pages`

```json
{
  "uploaded": [ { "id": "zebra-staking", "contentType": "text/markdown", "sizeBytes": 87, "sha256": "…", "updatedAt": "2026-10-20T10:00:00+00:00" } ],
  "served": [ { "id": "what-is-biatec", "title": "What is Biatec", "source": "seed" }, { "id": "zebra-staking", "title": "Zebra staking", "source": "upload" } ]
}
```

`uploaded` is the shared table (no bodies); `served` is what this replica serves right now, from its own snapshot,
with `source` `seed` or `upload` as served. Until its next refresh a replica can serve less than `uploaded` shows.

### `PUT /onboarding/operator/kb/pages/{pageId}`

Creates or replaces a page. The raw request body is the page; the audit reason goes in the header `X-Admin-Reason`
(required, 1-200 characters, no control characters). Answer: `201` created, `200` replaced or unchanged (same
content), with `{ "page": <uploaded page>, "change": "created|replaced|unchanged", "served": <count>, "reloaded":
true|false, "note": null|"..." }`. An unchanged upload does not reload. If the change is committed but this replica
then cannot reload, the request still succeeds and is audited, with `reloaded: false` and the note "Stored; this
replica will pick it up on the next refresh."

| Check | Refusal |
|---|---|
| `pageId`: 1-64 characters, lower-case letters, digits and inner hyphens (it is the id the model cites) | `400` |
| `X-Admin-Reason` missing or invalid | `400` |
| `Content-Type` `text/markdown` (or `text/x-markdown`) or `text/plain`; a charset other than UTF-8 is refused | `415` |
| Valid UTF-8, no control characters other than tab and line breaks (no binary) | `415` |
| At most `Kb:MaxPageBytes` bytes (also for a chunked body without a length); the `/onboarding` body limit of 32 KiB applies as well | `413` |
| Not empty or whitespace only | `400` |
| A new id while `Kb:MaxPages` pages are stored | `400` |

The title is the first `# heading`, else the id. Writes are serialized with a PostgreSQL advisory lock.

### `DELETE /onboarding/operator/kb/pages/{pageId}`

Removes an uploaded page (`X-Admin-Reason` required). `200 { "deleted": id, "served": <count>, "reloaded": ..., "note": ... }` (as for an upload), or `404`.
Deletes take the same advisory lock as uploads.

### `POST /onboarding/operator/kb/reload`

Re-reads the seed directory (`Kb:Path`) and the uploaded pages on the replica that handles it, for example after a
mounted seed volume changed: `200 { "served": <count>, "partial": false }`. `X-Admin-Reason` is optional here; when
sent it must be valid (else `400`) and is recorded. Uploaded pages reach other replicas by
polling. If the database cannot be read, the new seed is still served together with the last uploaded pages read,
and the answer is `503 { "served": <count>, "partial": true, "error": "... <SQL state and message>" }`, audited as
`reloaded the knowledge base partially`.

```bash
curl -sS -X PUT https://chat.biatec.io/onboarding/operator/kb/pages/zebra-staking \
  -H "Authorization: Bearer $OPERATOR_KEY" -H 'Content-Type: text/markdown' \
  -H 'X-Admin-Reason: ticket 42: new staking page' --data-binary @zebra-staking.md
```

## Audit

Every call writes a structured log line naming the operator (category `Biatec.Chat.Api.Admin.TenantPolicyService`):

- read: `Admin: operator {Operator} from {RemoteIp} read tenant policy {TenantId} (found: ...)`, and the same for the list;
- change: `Admin: operator {Operator} from {RemoteIp} changed tenant policy {TenantId}: {Changes}. Reason: {Reason}`,
  with each changed field as `name: old -> new`;
- refusal: `Admin: refused tenant policy change {TenantId} by operator {Operator} from {RemoteIp}: {Error}. Reason: {Reason}`;
- knowledge base (category `Biatec.Chat.Api.Admin.KbAdminService`): `uploaded kb page {PageId} ({Change}, {Bytes}
  bytes, sha256 {Sha256}); serving {Served} pages. Reason: {Reason}`, `deleted kb page {PageId}; ... Reason: {Reason}`,
  `reloaded the knowledge base; serving {Served} pages. Reason: {Reason}`, `listed kb pages`, and refusals as `refused
  kb page change {PageId} by operator {Operator} from {RemoteIp}: {Error}. Reason: {Reason}`. Lines carry the page id,
  size and hash, never its content;
- rejected authentication (category `Biatec.Chat.Api.Operator`, shared with operator onboarding): `Operator: rejected
  unauthenticated {Method} {Path} from {RemoteIp}`; first use of the legacy key: a deprecation warning.

Lines carry policy values only, never the bearer key, a key hash, `clientSecretRef` or another secret. Caller-supplied
text (tenant id in a path, reason) has control characters removed or refused, so a request cannot forge log lines.
Every committed change is also in the signed admin evidence chain below.

## Admin evidence chain

Every committed admin change is appended to one signed, hash-chained evidence chain, with the same `IEvidenceLog`,
encodings (RFC 8785, SHA-256, ES256) and signing keys (published at `/.well-known/evidence-jwks.json`) as conversation
chains. Its chain id is the fixed `00000000-0000-0000-0000-00000000ad01` (`AdminEvidence.ChainId`); conversation ids are
random version-4 GUIDs, and no conversation row has this id, so no chat session can read it.

| Action | When recorded | `target` | `before` / `after` |
|---|---|---|---|
| `tenant_policy_update` | A PATCH that changes at least one field, in the same transaction as the change | `tenant:<id>` | Each changed field as invariant text (`"1500"`, `"true"`, `"(default)"`, `"(none)"`) |
| `kb_page_upload` | A created or replaced page (not an unchanged one), in the same transaction | `kb-page:<id>` | `{contentType, sizeBytes, sha256}`; `before` is `null` for a new page |
| `kb_page_delete` | A deleted page, in the same transaction | `kb-page:<id>` | `before` the page's `{contentType, sizeBytes, sha256}`, `after` `null` |
| `kb_reload` | After the reload ran (it stores nothing) | `kb` | `after` `{served, partial}` |
| `tenant_approve` | An operator tenant approval that created the tenant, in the same transaction | `tenant:<id>` | `before` `null`; `after` `{host, oidcClientId, redirectUri, signInPageUrl, allowedOrigins, consentThresholdCeilingEur, softCapEurPerHour, trustAnchorVerified}` (amounts as invariant text); never `clientSecretRef` |

Each entry has kind `admin_change` and the payload
`{ "operator", "operatorAuth": "named-key"|"legacy-shared-key", "action", "target", "reason", "before", "after" }`. It
never holds a key, a key hash, a secret or page content (a page is recorded by its SHA-256, size and type). Refused
requests and no-op changes are not recorded (they are in the log).

Tenant approvals, policy and knowledge-base changes commit together with their entry or not at all: if the entry cannot be appended
(for example the signing key store fails) the change is rolled back and the request fails with `500`. A reload has
already taken effect when it is recorded, so its entry is best-effort: if it cannot be appended, the request still
answers as described and an error line `the kb reload by operator ... is not in the admin evidence chain` is logged.
It is appended without the request's cancellation token, so a client that disconnects after the reload ran still
leaves its record.

### `GET /onboarding/operator/evidence`

Operator bearer required; `Cache-Control: no-store`. Query `fromSeq` (default 1) and `limit` (default 200, clamped to
1-1000); a non-integer value is `400` (checked after authentication). Returns one page of the chain as a signed
**evidence bundle in the conversation export format** (`biatec-evidence-bundle` v1, built by `EvidenceBundleBuilder`,
with `jwksUrl` from `Evidence:PublicBaseUrl` or the request host; its `conversationId` is the chain id), plus the
server's verdict:

```json
{
  "chainId": "00000000-0000-0000-0000-00000000ad01",
  "fromSeq": 1,
  "limit": 200,
  "nextFromSeq": null,
  "verification": { "valid": true, "throughSeq": 2, "failedSeq": null, "error": null },
  "bundle": { "format": "biatec-evidence-bundle", "version": 1, "conversationId": "00000000-0000-0000-0000-00000000ad01",
    "exportedAt": "…", "kid": "…", "jwksUrl": "https://chat.biatec.io/.well-known/evidence-jwks.json", "keys": [ … ],
    "entries": [ { "seq": 1, "kind": "admin_change", "payload": { "operator": "alice", "operatorAuth": "named-key",
      "action": "tenant_policy_update", "target": "tenant:chat.example-bank.com", "reason": "ticket 42",
      "before": { "x402Enabled": "false" }, "after": { "x402Enabled": "true" } },
      "salt": "…", "payloadHash": "…", "prevHash": "000…0", "entryHash": "…", "anchorRef": null, "kid": "…",
      "signedAt": "2026-10-20T10:00:00.000Z", "signature": "…" } ],
    "signature": "…" }
}
```

How paging stays verifiable (the simplest correct option): the server reads, in one query, every entry from seq 1 to
the end of the requested page and verifies that snapshot from genesis, so `verification` covers seq 1 to
`throughSeq` and matches exactly the entries returned (no second read). The page itself is the entries from `fromSeq`;
`nextFromSeq` is the next page's start, or `null` at the end. A page's first `prevHash` equals the previous page's last
`entryHash`, so pages concatenate into the full chain. A bundle starting at seq 1 (the default, or every page when the
chain fits in 1000 entries) is checked by the offline verifier as is (`jq .bundle > admin-evidence.json`); the offline
verifier expects a chain from seq 1, so for later pages concatenate the entries first. A request for a late page
costs a read of the whole prefix; admin changes are rare, so that is accepted rather than caching a verdict.

**Retention.** The admin chain holds operator names, reasons and tenant policy values, not end-user personal data, so
it is exempt from the payload window (`Retention:Payloads`, 90 days): its payloads and salts are kept, so who did what
stays readable. It keeps the record window (`Retention:Records`, 7 years): once its newest entry is past it, the
retention job deletes the chain like any orphan chain. The anchoring job anchors this chain's head like any other.

## Example

```bash
# Each operator keeps their own key; only its SHA-256 is configured as Admin__Operators__<name>__KeyHash.
export OPERATOR_KEY="$(kubectl get secret biatec-chat-operator-alice -o jsonpath='{.data.key}' | base64 -d)"
curl -sS https://chat.biatec.io/onboarding/operator/tenants/chat.example-bank.com \
  -H "Authorization: Bearer $OPERATOR_KEY"
curl -sS -X PATCH https://chat.biatec.io/onboarding/operator/tenants/chat.example-bank.com/policy \
  -H "Authorization: Bearer $OPERATOR_KEY" -H 'Content-Type: application/json' \
  -d '{"x402Enabled": true, "reason": "ticket 42"}'
```

## Not covered

- A dedicated `/admin` prefix, and operator sign-in through Biatec OIDC (an operator claim or group; row 23 of
  required-changes-biatec-oidc.md). Named keys are the fallback until then.
- A UI.
