# Biatec Consent Protocol, version 1.1

Status: draft. This document is the integrator-facing specification. `PRODUCT-DESCRIPTION.md` ("Biatec Authenticator And The Biatec Consent Protocol") is the product source of truth and wins on any conflict. Version 1.1 replaces 1.0 as the only version new implementations produce (the mock Biatec OIDC, the widget's backend and the authenticator of this repository still produce 1.0 and move to 1.1 in their own tasks; the schemas and verifiers accept both meanwhile); [13. Changes from 1.0](#13-changes-from-10) lists what changed.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Overview

The Biatec Consent Protocol lets a user approve or deny one precisely described action on a trusted, device-bound surface (the Biatec Authenticator) while the action is requested from somewhere else (the Biatec Chat widget, a bank app, a website). It is a profile over existing standards, not a new protocol:

| Need | Standard |
| --- | --- |
| Push an approval to a device that did not start the flow | OpenID Connect CIBA (push and poll modes) |
| Describe exactly what is approved | OAuth 2.0 Rich Authorization Requests, RFC 9396 (`authorization_details`) |
| Bind approval to amount and payee | PSD2 dynamic linking, carried by `authorization_details`; CIBA `binding_message` for an optional purpose text |
| Step up only when needed | OAuth 2.0 Step-up Authentication Challenge, RFC 9470 |
| Hardening | FAPI 2.0 Security Profile, FAPI-CIBA: PKCE, exact redirect URIs, short lifetimes, `requested_expiry` default 300 s |
| Canonical signed bytes | JSON Canonicalization Scheme, RFC 8785 |
| Device keys | Two hardware-backed P-256 keys per device (an approval key bound to biometrics and a presence key), attested at enrollment |
| Client identity | A fingerprint of the `client_id` and, when proven, the client's domain; the user decides on their own phone whether to trust it |
| Consent record | Kantara Consent Receipt field layout |

Roles:

- **Client**: the requesting application (Biatec Chat backend, a bank, a fintech).
- **Biatec OIDC**: the authorization server. It decodes the transaction group, values it, opens the request, generates the binding code, stores the request and verifies and consumes receipts. It vouches for no client and for no application.
- **Authenticator**: the mobile app holding the device keys.
- **User**: sees the card on the authenticator and the binding code on the requesting surface. All trust is the user's: the threshold, which services are linked and which applications are trusted are set on the user's own phone.

Machine-readable definitions live in `schemas/` (JSON Schema 2020-12) and signed examples in `vectors/`. Everything in this document that is normative about a wire object is expressed by a schema.

## 2. The request model

A consent request at Biatec OIDC is always the same object, whichever entry point opened it (`schemas/consent-request.schema.json`):

- `authorization_details`: exactly one typed object, decoded by Biatec OIDC (section 3).
- A **binding code** generated by Biatec OIDC, returned only to the client (section 7).
- An optional client-supplied `binding_message`.
- The client identity: `fingerprint`, `domain_proven`, `domain` when proven, and `linked` (section 6).
- `requested_expiry` (default and maximum 300 seconds) and the derived `expiry`.
- The **bound hash** (`group_hash` or `request_hash`) the consent is tied to.
- The reporting `origin` and the pairwise `sub` of the requesting client.

Client-supplied amounts or payees are never accepted as the thing being consented to; the group (or canonical limits body) is.

## 3. Authorization details types

`authorization_details` is an array of exactly one object (`schemas/authorization-details.schema.json`), of one of the two types below.

### 3.1 `biatec_transaction`

Describes one signing call (`schemas/authorization-details-transaction.schema.json`). Biatec OIDC decodes every field from the unsigned group itself:

- `network`, `group_hash`, `sender` and `origin`.
- `transfers`: every payment and asset transfer the sender sends out, in group order, at most 16, each with `receiver`, `asset`, `amount` and, when it could be priced, `fiat_value`. Transfers of other senders are not listed.
- `applications`: every application the group calls, at most 16, each with its `id` and `trusted`, which is true only when the user trusted that application for this client on their own phone. There is no operator list of applications.
- `value_known`: false when any transfer could not be priced or any application is not trusted. Then there is no top-level `fiat_value` and the card says "Value unknown" in the warning style. When true, the top-level `fiat_value` is the total in EUR of the priced transfers. The top-level `fiat_value` is present exactly when `value_known` is true.

A renderer MUST show every transfer and every application and MUST NOT summarize. A group that sends value somewhere `transfers` cannot name is not described and is not consentable in this version: a payment with a close-to address, an asset transfer with a close-to or clawback address, a rekey, and any transaction type other than payment, asset transfer and application call. Biatec OIDC refuses such a group for a client under consent enforcement (`403 consent_unsupported_operation`), so no receipt ever covers one. Amounts are decimal strings, never JSON numbers, so canonicalization loses no precision. `origin` is part of the signed object, as the client reported it: the receipt proves which origin the user saw on the card, not that the site is who it says it is. The card shows it labelled as reported by the client, and only a proven domain says who the client is.

The `group_hash` is the Algorand group ID recomputed from the handed transactions (base32, 52 characters; for one ungrouped transaction its transaction id), or for Bitcoin the SHA-256 intent hash derived from a PSBT carrying prevout data (lowercase hex). The signing endpoint MUST refuse a request whose recomputed hash differs from the consented one.

### 3.2 `biatec_limits_change`

Describes a change of spending limits (`schemas/authorization-details-limits-change.schema.json`). It carries no `origin`: for this type the request's `origin` is recorded by Biatec OIDC but is not part of what the device signs. It has `current_limits`, `requested_limits` and `request_hash`, the lowercase hex SHA-256 of the RFC 8785 canonical request body of `PUT /wallet/limits`. The vectors include a worked example: the body `{"per_day_eur":"5000","per_transaction_eur":"2000"}` hashes to the `request_hash` in `vectors/receipts.json`.

## 4. Step-up entry

The client calls a wallet endpoint (`POST /wallet/{network}/{address}/sign` or `PUT /wallet/limits`) with an ordinary token. The CIBA request inherits that token's scopes and audience, so the elevated token carries the same `sign` or `manage-limits` scope and resource and can be presented straight back to the wallet endpoint. Biatec OIDC decides consent is needed (value above the user's threshold, an unknown value, a client the user has not linked yet or that registered less than 24 hours ago, the client sent `requireConsent: true`, or the user set "always ask" for this client), opens the request itself and answers with an RFC 9470 challenge:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="biatec:consent"
Content-Type: application/json
```

```json schema=stepup-challenge
{
  "error": "insufficient_user_authentication",
  "error_description": "Phone approval is required for this group.",
  "acr_values": "biatec:consent",
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "expires_in": 300,
  "interval": 2,
  "binding_code": "483920"
}
```

The client shows the binding code on its surface, polls the token endpoint (or receives the push-mode callback), then retries the wallet endpoint with the elevated token and the same unsigned group:

```http
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:openid:params:grant-type:ciba&auth_req_id=ciba_8257c10231dd9b46e2f877484cf0b2a3&resource=https%3A%2F%2Fapi.biatec.io
```

The token response carries the access token (and never a refresh or ID token; the schema forbids both) (`acr` = `biatec:consent`, bound to the group hash, 300 seconds) and the signed receipt in `consent_receipt` (`schemas/token-response.schema.json`). A step-up receipt signs an empty `binding_message`, because no client text exists.

## 5. Direct entry

A client that already built the group and wants the consent in hand before calling the wallet endpoint (for example to drive its own progress UI) calls the CIBA backchannel authentication endpoint with the exact unsigned group (or the canonical limits request body) plus an optional `binding_message`. Biatec OIDC decodes the group and builds `authorization_details` exactly as in the step-up entry. A request that carries `authorization_details` is invalid.

```http
POST /connect/ciba
Content-Type: application/json
```

```json schema=backchannel-authentication-request
{
  "scope": "sign",
  "resource": "https://api.biatec.io",
  "login_hint": "user@example.com",
  "network": "algorand-mainnet",
  "address": "YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE",
  "unsigned_group": ["gqNzaWfEQ...base64 unsigned transaction..."],
  "binding_message": "Invoice 2026-0042",
  "requested_expiry": 300,
  "origin": "https://bank.example"
}
```

```json schema=backchannel-authentication-response
{
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "expires_in": 300,
  "interval": 2,
  "binding_code": "120934"
}
```

(The wire encoding of the endpoint follows CIBA, form-encoded; JSON is shown for readability and is what the schema validates.) The client then displays the binding code, obtains the token as in section 4 and presents it to the wallet endpoint, which checks the hash as usual.

`binding_message` is rendered on the card, under the decoded facts and visibly attributed to the client, only for a client whose domain is proven. For any other client it is not rendered and therefore signed as the empty string; the raw text is kept only in the unsigned request log. A client without a proven domain therefore has no free-text channel to the trusted surface.

### 5.1 One model, two entries

Both entries produce the same request object, the same receipt schema, the same canonical form and the same signing rules. Receipts differ only in field values (`binding_message`, `client_fingerprint`, the detail fields). In `vectors/receipts.json`, `stepup-*` and `direct-*` vectors validate against identical schemas.

The client retrieves the receipt in the CIBA token response (`consent_receipt`) and again at `GET /consent/receipts/{auth_req_id}`, only as the client the request belongs to: the one that opened it (direct entry) or the one whose token was challenged (step-up entry).

## 6. The authenticator's request object

The authenticator learns of a request as a hint over its device channel (or a push) that carries only the `auth_req_id`. It then fetches the request over an authenticated channel using its device key. The response is the consent request object (`schemas/consent-request.schema.json`) and never contains the binding code:

```json schema=consent-request
{
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "entry": "step-up",
  "authorization_details": [
    {
      "type": "biatec_transaction",
      "network": "algorand-mainnet",
      "group_hash": "BJPMYYUBSMQWYXMEBZT2ZHFZTWCIJAFAIMUZEGOJZKJPRBKU5KNA",
      "sender": "YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE",
      "transfers": [
        {
          "receiver": "WSNJGAWN52IJMHAEFZIOPCS3IXSHS4C46QDNSKWDEWQ3E6M4HUNLYTHJXE",
          "asset": { "id": "31566704", "symbol": "USDC", "decimals": 6 },
          "amount": "5000.000000",
          "fiat_value": { "amount": "4612.50", "currency": "EUR" }
        }
      ],
      "applications": [],
      "value_known": true,
      "fiat_value": { "amount": "4612.50", "currency": "EUR" },
      "origin": "https://app.biatec.io"
    }
  ],
  "client": {
    "fingerprint": "68dcf7ce89a943b0",
    "domain_proven": true,
    "domain": "chat.biatec.io",
    "linked": true
  },
  "binding_message": "",
  "requested_expiry": 300,
  "expiry": 1792425900,
  "bound_hash": "BJPMYYUBSMQWYXMEBZT2ZHFZTWCIJAFAIMUZEGOJZKJPRBKU5KNA",
  "origin": "https://app.biatec.io",
  "sub": "pw_7c1f0a52e9b34d68"
}
```

**Who is asking.** Biatec OIDC vouches for no client. The `client` object has exactly:

- `fingerprint`: 16 lowercase hex characters, the first eight bytes (64 bits) of the SHA-256 of the `client_id`, shown to the user as `xxxx-xxxx-xxxx-xxxx`. The fingerprint is for the user's eyes: a client is linked and trusted by its full `client_id` at Biatec OIDC, never by this value alone. Matching a chosen client's fingerprint takes about 2^64 hashes, which is out of reach of casual attackers and within reach of very large clusters, so the user must still compare the proven domain, which an impostor cannot have.
- `domain_proven` and `domain`: true, and the ASCII (A-label) host, when the client proved control of that domain by serving `/.well-known/biatec-client.json` that lists its `client_id`; otherwise false and no `domain`.
- `linked`: whether this user already linked this client on their phone.

A renderer shows the proven domain, or "Unproven application" in the warning style with the fingerprint, and the user's own label for the service when they set one beside it. It never shows a name or a logo taken from the operator or from the client.

## 7. The binding code

Biatec OIDC generates a six digit binding code (`schemas/binding-code.schema.json`) and returns it only to the client. The authenticator does not display it; the user types the code shown on the requesting surface into the authenticator to approve. The user has three attempts in total within the request's validity. The third wrong code produces a denial recorded as `code_failed`; an explicit Deny produces a denial recorded as `deny`. Only explicit denies count toward the denial counter of section 11. The code the user entered is part of the signed receipt.

## 8. The signed receipt

The device signs the RFC 8785 canonical form of exactly this object (`schemas/consent-receipt-signed.schema.json`):

```
{ authorization_details, auth_req_id, client_fingerprint, binding_code, decision, expiry, sub, binding_message }
```

and, for an `approve` only, a ninth member `remember` (below).

- `client_fingerprint` is the fingerprint of section 6.
- `decision` is `approve`, `deny` or `code_failed`.
- `expiry` is Unix time in seconds.
- `binding_message` is the text as rendered, or the empty string if none was rendered.
- `auth_req_id` is the single-use nonce.
- `sub` is the pairwise subject of the requesting client, so the client can match it against its own session and nothing linkable across clients is signed. The device does not compare it with its own subject. The attestation of the receipt is minted by Biatec OIDC for this subject when the receipt is stored.
- `remember` is `{ "applications": [<application ids>] }`: the applications of this request the user chose to trust for this client. Each id MUST be an application of the request's `authorization_details` that the card offered to trust (its `trusted` is false) and the request's application ids are unambiguous (a verifier checks it against the stored request; the user can only trust what the card offered); it is refused on `deny` and `code_failed`. One biometric prompt covers the approval and the trust.

Signing procedure:

1. Build the object above from the request fetched in section 6 and the code the user typed.
2. Canonicalize it with RFC 8785. All amounts are strings; integers MUST be at most 2^53 - 1.
3. Sign the UTF-8 bytes with ES256 (ECDSA P-256, SHA-256) using the **approval key** for `approve`; `deny` and `code_failed` may use either key. The signature is the 64-byte IEEE P1363 `r || s` form, base64url without padding; verifiers MUST reject non-canonical encodings.

The receipt envelope (`schemas/consent-receipt.schema.json`) adds `version` (`"1.1"`), `alg`, `signature`, `issued_at` (informational, unsigned) and `device`: the key ID, the informational `key_use`, the device public key as a JWK, and the **attestation**, a compact ES256 JWS signed by a Biatec OIDC JWKS key whose payload binds `sub`, `device_kid`, `device_jwk_thumbprint` (RFC 7638 thumbprint of the device public key) and `biatec_key_use`, which is `approve` or `presence`.

Worked example, the first vector in `vectors/receipts.json` (canonical bytes, one line):

```
{"auth_req_id":"ciba_8257c10231dd9b46e2f877484cf0b2a3","authorization_details":[{"applications":[],"fiat_value":{"amount":"4612.50","currency":"EUR"},"group_hash":"BJPMYYUBSMQWYXMEBZT2ZHFZTWCIJAFAIMUZEGOJZKJPRBKU5KNA","network":"algorand-mainnet","origin":"https://app.biatec.io","sender":"YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE","transfers":[{"amount":"5000.000000","asset":{"decimals":6,"id":"31566704","symbol":"USDC"},"fiat_value":{"amount":"4612.50","currency":"EUR"},"receiver":"WSNJGAWN52IJMHAEFZIOPCS3IXSHS4C46QDNSKWDEWQ3E6M4HUNLYTHJXE"}],"type":"biatec_transaction","value_known":true}],"binding_code":"483920","binding_message":"","client_fingerprint":"68dcf7ce89a943b0","decision":"approve","expiry":1792425900,"sub":"pw_7c1f0a52e9b34d68"}
```

### 8.1 Offline verification

Anyone with the Biatec OIDC JWKS verifies a receipt without further lookups:

1. Validate the receipt against the schema.
2. Verify the attestation JWS with the JWKS key named by its `kid`.
3. Check that the attestation header `typ` is `biatec-device-attestation+jwt`, that its signing key is an EC P-256 signature key of the Biatec OIDC JWKS, that its `iss` is the expected issuer, that its `exp` is in the future (verifiers use a trusted clock), and that its `sub` equals `signed.sub`, `device_kid` equals `device.kid` and `device_jwk_thumbprint` equals the thumbprint of `device.public_key`. For version 1.1 the attestation MUST carry `biatec_key_use` (`approve` or `presence`), `device.key_use` MUST equal it, and an `approve` receipt MUST carry the use `approve`: a receipt that approves but is signed by a presence key is refused however valid its signatures are (`vectors/receipts.json` contains such a vector, named `...-REFUSED`).
4. Canonicalize `signed` (RFC 8785) and verify `signature` over its UTF-8 bytes with `device.public_key`.
5. For authorization, compare every signed member (`authorization_details`, `auth_req_id`, `client_fingerprint`, `binding_message`, `expiry`, `sub`) and the bound hash with the stored request the verifier is waiting on, never with data the receipt supplies. Additionally require `decision` = `approve` and that `binding_code` equals, in constant time, the code Biatec OIDC issued for this `auth_req_id` (number matching, rule 2), compare the `signed.authorization_details` hash fields with the group or body presented, check `expiry`, and mark `auth_req_id` spent only when the signing call actually proceeds (rule 5); a verification that is followed by a failed signing call leaves the consent unspent. A verifier MUST NOT treat a `deny` or `code_failed` receipt, or an expired one, as consent. Verification helpers return a boolean and never throw on malformed input.

`version` is not part of the signed object, so no rule may depend on it alone: the signed object's members must agree with it (`client_fingerprint` for 1.1, the 1.0 client member for 1.0), an attested `biatec_key_use` is honoured whatever `version` says (a device with a key use can never approve with a presence key by relabelling the receipt `"1"`), and the stored request, not the receipt, decides which version applies (`verifyApproval` refuses a 1.1 request answered by a 1.0 receipt and the other way round). A 1.1 receipt is authorized only for a device the caller holds as active (`opts.deviceActive === true`; the attestation of a pending device is valid too).

A relying party that pinned the device's public keys when the user linked it can verify the device signature itself and treat the attestation as a second check.

Reference implementations: `scripts/lib.mjs` (JavaScript; `verifyReceipt` covers steps 2-4 and `verifyApproval` step 5, which also matches the receipt against the stored request) and `backend/Biatec.Chat.Tests/Canonical/ConsentProtocolVectorTests.cs` (.NET, using the backend `JsonCanonicalizer`). Both verify every vector signature, honour the `expected` verdict of every vector including the refused ones, and enforce the key-use rule; the .NET test also verifies the attestation.

### 8.2 Statements signed by the approval key of an active device

Two more objects are signed with the **approval key** of an **active** device, canonicalized with RFC 8785 exactly like a receipt, and carried with the device block and its attestation (`schemas/device-signed.schema.json`). `verifyReceipt` establishes that a receipt is authentic and says nothing about whether the device is active; authorization (`verifyApproval`, with `opts.deviceActive`) is where that is decided. Verification of these statements is the receipt's: signature over `JCS(signed)` by `device.public_key`, the attestation (which binds the device key and, for a settings change, `signed.sub`), the attested `biatec_key_use` MUST be `approve` (a presence key is refused), the key named inside the statement MUST be the key that signed, and `issued_at` MUST be within 300 seconds of the verifier's clock. A settings change keys its per-client changes by `client_id` (1 to 200 printable characters), lists each application at most once, and does not add and remove the same application in one change; the verifier and the schema agree on all three. The nonce is used once per device. A device approval carries no subject of its own, so the verifier says whose approval it accepts: the approver's attestation MUST be for the subject (account) of the device being enrolled, and Biatec OIDC checks that both devices belong to the same account; an active device of another account cannot approve. The approver MUST be an active device (an inactive device, including the one being enrolled, cannot approve) and is never one of the keys being enrolled; the nonce of every statement and of the enrollment challenge MUST be 16 to 128 characters of the base64url alphabet (so the pairing code input has one reading) and is accepted once per device, so a verifier needs the set of nonces it already accepted, MUST add a nonce to that set when it accepts the statement, and MUST keep each nonce at least as long as the 300 second window plus the clock skew it tolerates. Checking the set and adding to it is ONE atomic operation (an insert that fails if the nonce is present, such as `SET NX` in Redis); two concurrent requests with the same statement must not both pass. `verifyDeviceSigned` in `scripts/lib.mjs` implements it (`expect.sub`, `expect.approval`).

**Settings change** (`schemas/settings-change-signed.schema.json`). A change that loosens protection (raising a threshold, turning a protection off, trusting an application, lifting a pause) needs this statement; tightening needs none. Biatec OIDC classifies the change itself. The threshold belongs to the user: the schema has no ceiling, and `0` asks for everything.

```json schema=settings-change-signed
{
  "type": "biatec_settings_change",
  "sub": "pw_a9e3c0417b5d2f86",
  "kid": "device-test-key-1",
  "nonce": "n-7eb064c2a94489ba608c95cf3aaf54",
  "issued_at": 1792425630,
  "change": {
    "threshold_eur": "5000",
    "clients": {
      "bank-example-client": { "trusted_applications_add": [{ "network": "algorand-mainnet", "app_id": 1234567 }] }
    }
  }
}
```

A user's own text (`label`, at most 40 code points) is Unicode NFC, not blank and without padding or runs of spaces, without control characters, bidirectional controls (U+202A to U+202E, U+2066 to U+2069, U+200E, U+200F, U+061C), zero-width characters (U+200B to U+200D, U+2060, U+FEFF), line breaks, other white space, format characters, filler or invisible characters (soft hyphen, Hangul fillers, invisible operators, variation selectors, tag characters), bare or stacked (more than three) combining marks; ZWNJ and ZWJ are allowed between two letters, marks, symbols or digits and U+FE0F right after a symbol or digit (never at an end, next to white space or several in a row), so Persian and Indic text and emoji sequences can be labels; the character classes are those of Unicode 16, and a verifier on an older version may refuse a character newer than its tables, so implementations should use Unicode 16 or later; look-alike letters of another script are not detected, which is why a label is shown beside the proven domain or fingerprint and never instead of it; a violation is refused, never stripped (`isDisplaySafe` in `scripts/lib.mjs`; `verifyDeviceSigned` applies it to every label, refuses unknown members, a pause without its `origin` and an `unlink` combined with anything else).

**Approval of a new device** (`schemas/device-approval-signed.schema.json`). A device that enrolls is active at once only when this statement from an existing active device covers its two keys and the enrollment nonce and carries the pairing code the user compared on both phones (or a recovery code is used). Naming a `kid` proves nothing.

```json schema=device-approval-signed
{
  "type": "biatec_device_approval",
  "approver_kid": "device-test-key-1",
  "new_kid": "new-approval-test-key-1",
  "new_approval_jwk_thumbprint": "cpXj3K7c4_bBd9lXxKoO8aZPwTwuPMGzwnYgg3rG_jY",
  "new_presence_jwk_thumbprint": "hOlyodNi_jjK_piu5kSIQkvt2q5zwnCUtO8iVYQtwlw",
  "pairing_code": "102716",
  "nonce": "enroll-nonce-53bcbb91525547bf679e9d4f",
  "issued_at": 1792425640
}
```

### 8.3 Enrollment: the proof and the pairing code

The enrollment nonce is consumed once by the server when it accepts the proof; the same value then appears as the `nonce` of the approver's `biatec_device_approval`, which is tracked in the approver's own set of used statement nonces, so the two are separate namespaces. A new device sends, in `POST /devices`, an **enrollment proof**: a compact JWS (`schemas/device-enroll-proof.schema.json` describes its decoded header and payload) with `typ` `biatec-device-enroll+jwt`, signed with ES256 by the new **approval** key, which it carries as the header `jwk`. The payload is `{ kid, presence_kid, presence_jwk_thumbprint, nonce, iat }`: it names the approval key, names the presence key by its RFC 7638 thumbprint, and carries the nonce of the server's challenge. The device also sends a `presence_proof`: a second compact JWS, `typ` `biatec-device-enroll-presence+jwt`, over the SAME payload, signed by the presence key, which it carries as its header `jwk`; without it a key named only by its thumbprint would not have proven possession (anyone's public key can be named). The server checks the signature under the header `jwk`, the nonce, that the thumbprint is that of the presence public key the request also carries and the `presence_proof` verifies under that key, and `iat` within 300 seconds. `verifyEnrollmentProof` in `scripts/lib.mjs` implements it.

The **pairing code** is a human check, not a secret: it lets the user confirm that the phone they are holding and the new device they are enrolling are looking at the same enrollment (it is not meant to resist someone who controls the new device, who can pick its keys freely; that is what the 24 hour delay, the notices and the requirement that an ACTIVE device signs are for). It is the six digit number both phones show: the first four bytes of `SHA-256(new_approval_jwk_thumbprint + "." + new_presence_jwk_thumbprint + "." + nonce)` read as a big-endian unsigned integer, modulo 10^6, zero padded to six digits. Worked example (`vectors/device-signed.json`, `pairing_code`):


## 10. Third-party integration

1. Self-register with RFC 7591 Dynamic Client Registration, declaring `backchannel_token_delivery_mode` and the `authorization_details_types` used, and a `client_uri`. Capabilities needing the `manage-limits` scope stay reserved for operator-allowlisted clients.
2. Prove the domain: serve `/.well-known/biatec-client.json` with the `client_id` listed. Without it the user sees the client as "Unproven application" with its fingerprint.
3. Use the direct entry (section 5) or handle the step-up challenge (section 4). In both cases display the returned binding code, poll or receive the token, and present it to the wallet endpoint.

The user links the client on their phone the first time they approve a request of it; every request of a client that is not linked asks the phone, whatever the value.

### 11.1 Requester identity and cooling-off

- **Rule 3.** Biatec OIDC vouches for no client. The authenticator shows a client's proven domain, or "Unproven application" with a short fingerprint of its `client_id` in a warning style, and nothing else about it. The user's own label for a service is shown beside it, never instead of it. The user's policy may block clients without a proven domain entirely. A user trusts an application by ticking it on the approval card, which signs it into the approve receipt (`remember`); there is no operator list.
- **Rule 4.** For a user with an active enrolled device, every client that registered less than 24 hours ago, and the first request of any client the user has not linked yet, requires phone approval regardless of value, as if the threshold were zero. Approving that first request links the client. An enrolled but still inactive device counts as no active device. For a user with no active device, Biatec OIDC instead applies a reduced per-client daily cap (default 100 EUR) during the client's first 24 hours and the user's first day with the client.

### 11.2 Validity and consumption

- **Rule 5.** A consent is valid for 300 seconds by default, bound to one group hash, and authorizes exactly one signing call. It is spent only when Biatec OIDC actually signs; a call failing the hash check, the spending limits or any other validation leaves it unspent. The signing endpoint signs for one sender address per call, so an action needing two senders is two groups, two signing calls and, if each needs it, two consents. A Bitcoin transaction in version 1 spends from one address; a transfer needing several addresses is split into one transaction per address, each with its own group hash. Biatec OIDC rejects a signing request whose group hash differs from the consented hash.

### 11.3 Device keys, enrollment and recovery

- **Rule 6.** The authenticator holds two hardware-backed key pairs and an enrollment identifier, and no wallet keys, cloud-storage tokens or long-lived OAuth tokens. The **approval key** is created so that the operating system itself requires a strong biometric for every signature and invalidates it when the biometrics change; it signs `approve` receipts, settings changes and approvals of new devices. The **presence key** is usable while the device is unlocked; it signs device proofs on every HTTP call, `deny` and `code_failed` receipts. Each key has its own `kid` and its own attestation with `biatec_key_use` set to `approve` or `presence`. The keys are generated in hardware and attested at enrollment; the attestation is presented again when receipts are posted.
- **Rule 7.** Enrollment starts with a fresh full Biatec OIDC login inside the authenticator, including the identity provider's multi-factor step. The device is active at once only when an already active device signed a device approval (section 8.2) after the user compared the pairing code on both phones, or a recovery code is used. Otherwise (first device or lost-device recovery) it is enrolled but inactive for 24 hours; every other device and the user's email address receive a cancel link, and during that period a user with no other active device cannot complete any action needing phone approval. A recovery code, generated and shown once only after a device has become active, activates a later device immediately.
- **Rule 8.** A user without an active enrolled device can use every below-threshold capability (subject to the reduced caps of rule 4) but cannot complete an action needing phone approval. The default threshold is not lowered for such users.

### 11.4 Denial, pending limits and pause

- **Rule 10.** A denial produces a signed denial receipt (`decision` = `deny`) and immediately cancels the pending action in the requesting surface. Denials never auto-block a client. Biatec OIDC allows at most three pending requests per client per user per origin (origin is reported by the client with each request), rate-limits new requests as an anti-spam measure only (default 60 per hour per client per user, no per-second burst limit), and after three explicit denials in a day the authenticator offers a one-tap "pause this client on this site for 24 hours", scoped to the reporting origin and liftable from the linked-services screen. `code_failed` denials do not count toward the three.

### 11.5 Limits

- **Rule 11.** Authenticator approval never bypasses spending limits; it is an additional requirement. Biatec OIDC's per-user limits cover the user's own addresses only; funds inside a Biatec Safe are governed by the safe's on-chain signer-group limits plus the consent threshold applied to each approval.

## 12. Threshold, loosening and tightening

The threshold is the user's. A new account starts at 1000 EUR: any single action valued above the user's threshold, or whose value is unknown, requires authenticator approval. The user can set any threshold on their phone, including 0 (ask for everything), and per-client thresholds; there is no ceiling unless a deployment sets one. Any change that loosens protection (raising a threshold, turning "always ask" off, lifting a pause, trusting an application) is itself a statement signed by the approval key of an active device (section 8.2, or `biatec_limits_change` for spending limits); tightening applies immediately. The threshold and the user's per-client settings are stored and enforced by Biatec OIDC at the signing endpoint. A client may ask for more consent (`requireConsent: true`) but never less.

## 13. Changes from 1.0

Version 1.1 is additive where it can be and replaces 1.0 as the only version implementations produce. No production receipt of 1.0 exists. Schemas keep a 1.0 branch so that 1.0 receipts, requests and details keep validating; `vectors/receipts-1.0.json` is that frozen set.

1. **Whole-group details.** `biatec_transaction` lists every outgoing transfer (`transfers`) and every application (`applications`) instead of one summary line; the single-transfer members (`receiver`, `asset`, `amount`, `application_id`) are 1.0 only.
2. **Unknown value.** `value_known` says when the value could not be priced or an application is not trusted; the total `fiat_value` is present exactly when it is true.
3. **Signed origin.** `origin` (as the client reported it) is a member of the details, so a receipt proves which origin the user saw.
4. **`group_hash`** is the Algorand group id recomputed from the handed transactions (for one ungrouped transaction its transaction id), base32, 52 characters; the `sha256:` form that appeared in `docs/required-changes-biatec-oidc.md` is dropped.
5. **Subject.** `signed.sub` is the pairwise subject of the requesting client; the attestation is minted for that subject when the receipt is stored; the device does not compare it with its own.
6. **Two keys.** An approval key (biometric-bound) and a presence key, each with its own attestation carrying `biatec_key_use`. Verification step 3 gains the key-use rule: an `approve` receipt MUST carry `approve`. Device proofs and `deny` / `code_failed` receipts may use the presence key. The envelope carries `version` `"1.1"` and `device.key_use`.
7. **New signed objects.** `biatec_settings_change`, `biatec_device_approval` and the enrollment proof (sections 8.2 and 8.3), with schemas and vectors, and the pairing code definition with a worked example.
8. **The client is not vouched for.** The request's `client` object is `{ fingerprint, domain_proven, domain?, linked }`; the 1.0 members that asserted an operator-vouched name, a verified flag or a federation entity id are 1.0 only. The signed object names the client by `client_fingerprint` instead of the 1.0 entity member. The fingerprint is 16 lowercase hex characters (shown `xxxx-xxxx-xxxx-xxxx`). `binding_message` is rendered only when the domain is proven.
9. **User-held trust.** `remember` in an approve receipt trusts applications for a client; the user sets the threshold (no ceiling), links clients, and trusts applications on their own phone (rules 3, 4 and section 12). There is no operator list of clients, applications or test-network prices.
10. **Device channel.** The authenticator learns of a request from a hint over Biatec OIDC's own device channel (or a platform push); no third-party push relay is part of the protocol.
