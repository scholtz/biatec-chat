# biatec_authenticator

Biatec Authenticator (Flutter): device enrollment with a hardware key, consent approvals with signed receipts, push
notifications, and device, trusted-client and security settings screens. It runs against the mock Biatec OIDC
(`packages/consent-protocol/mock-oidc`); real Biatec OIDC has no consent or device APIs yet
([docs/required-changes-biatec-oidc.md](../../docs/required-changes-biatec-oidc.md)).

## Platform folders

`android/` and `ios/` are committed (generated by `flutter create --platforms=android,ios --project-name biatec_authenticator --org io.biatec .`,
then hardened; BCHAT-008). The application id and bundle identifier are `io.biatec.authenticator`. What is set, and kept by
`test/platform_hardening_test.dart`:

- **Android:** no backup or device transfer (`allowBackup="false"`, `data_extraction_rules.xml`), no cleartext traffic (the debug manifest alone allows
  it, for the local mock), `MainActivity` (the launcher) is the only component of the app's own manifest, the window is `FLAG_SECURE`, `KeystorePlugin`
  is registered in `MainActivity`, release builds are minified and signed with your own key (below). Libraries add three receivers when the manifests
  merge (Firebase messaging twice, protected by `com.google.android.c2dm.permission.SEND`; the AndroidX profile installer, protected by
  `android.permission.DUMP`); review the merged manifest (`build/app/intermediates/merged_manifests/release/`) on each release.
- **iOS:** App Transport Security at its default (no exceptions), no URL schemes, a Face ID usage string, `KeystorePlugin` (Secure Enclave) registered in
  `AppDelegate`, and `ScreenCover` hides the content from the app switcher and while the screen is recorded or mirrored.
- **Push on iOS is not enabled yet:** the Push Notifications capability (a `Runner.entitlements` with `aps-environment`, per build configuration) needs the Apple
  developer account, and `GoogleService-Info.plist` / `android/app/google-services.json` are not committed; until then approval pushes do not arrive.
  The deployment target is iOS 15 (Firebase iOS SDK 12); `UIBackgroundModes` `remote-notification` is added together with the capability.
- **Not verified:** the Kotlin plugin compiles (`flutter build apk --debug` and `--release` were run), but nothing was run on a device or an emulator.
  The Swift files (`KeystorePlugin.swift`, `ScreenCover.swift`, `AppDelegate.swift`) and the Xcode project edits were written without Xcode: build them
  on a Mac before the first iOS release.

### Release build

The release build never uses the debug key. Create a keystore once, keep it out of the repository, and describe it in `android/key.properties`
(git-ignored):

    storeFile=/absolute/path/to/upload-keystore.jks   (or relative to android/)
    storePassword=...
    keyAlias=...
    keyPassword=...

    flutter build apk --release --dart-define=OIDC_BASE_URL=https://oidc.example

Without `key.properties` the release build fails with `SigningConfig "release" is missing required property "storeFile"`. A release build also
needs `OIDC_BASE_URL` (https only; there is no mock default).

The `windows/` folder is checked in. Build it with `flutter build windows` (needs Visual Studio with the "Desktop
development with C++" workload and Windows Developer Mode for plugin symlinks). `windows/CMakeLists.txt` defines
`_SILENCE_EXPERIMENTAL_COROUTINE_DEPRECATION_WARNINGS` because `local_auth_windows` fails on MSVC 14.51+ without it.

A Windows build without `OIDC_BASE_URL` (a bare `flutter build windows`) defaults to `https://stage.oidc.biatec.io`;
`./build-windows.ps1` passes the same URL explicitly via `--dart-define-from-file=config/local.json`. Put `nuget.exe` on `PATH` to silence the
`Nuget.exe not found` message from `local_auth_windows`.

### Platform hardening (T-227)

What the committed project files enforce, each with a test in `test/platform_hardening_test.dart` that fails on a regression:

| Setting | Android | iOS |
| --- | --- | --- |
| No backup or transfer | `allowBackup=false`, `fullBackupContent=false`, data extraction rules exclude every domain | app folders marked excluded from backup at launch; keychain items `_this_device` |
| No screenshots or recording | `FLAG_SECURE` set before the first view; recents screenshot off (Android 13+) | cover view when the app is inactive (so the app switcher shows no content) and while the screen is recorded or mirrored. iOS has no way to block a screenshot of the app in front, so a screenshot there is not prevented |
| Overlay and tapjacking | other apps' overlay windows hidden (Android 12+, `HIDE_OVERLAY_WINDOWS`); on Android 11 and older a touch through another app's overlay is dropped, which also disables a full-screen filter app's taps while it runs | - |
| No custom keyboard | - | `shouldAllowExtensionPointIdentifier` refuses keyboard extensions |
| Release build | not debuggable, R8 minify and shrink, every `android.util.Log` call removed (and none in the app's own Kotlin) | - |
| Privacy | cleartext off (pinned network config: T-229) | `PrivacyInfo.xcprivacy`: no tracking; push token declared |

CI builds the release APK with `--obfuscate --split-debug-info=build/symbols`, signed with a throwaway key that exists only for that job, runs the hardening test against the merged release manifest, and keeps the symbols of that build for 7 days as the `authenticator-debug-symbols` artifact. The repository and its artifacts are public, so the artifact is `symbols.tar.gz.gpg`, encrypted (OpenPGP, AES-256) with the `AUTHENTICATOR_SYMBOLS_PASSPHRASE` repository secret (decrypt with `gpg -d symbols.tar.gz.gpg | tar -xz`). Without that secret (a fork, or before it is set) no symbols are published. Those symbols fit only that CI build: a shipped release is built with its own `--obfuscate --split-debug-info=<dir>`, and that directory must be archived privately with the release to read its crash traces.

To check by hand on a device: open the app and try a screenshot (it must fail or show a black image), look at the recents list (blank), `adb backup -f x.ab io.biatec.authenticator` (must produce an empty archive), and `adb shell run-as io.biatec.authenticator ls` (must be refused on a release build).

Not verified on a device: none of this has been run on a phone; the Swift changes were written without Xcode.

### Backup and restore (T-226)

The Codes tab has a backup action (and the "fingerprints changed" screen a restore action). A backup is one file, `biatec-authenticator-backup-YYYYMMDD.biatecbackup`, offered through the system share sheet and read through the system file picker; nothing goes to a server. Both directions first ask for a fresh biometric.

File layout (`lib/totp/backup/backup_format.dart`): `"BTBK"`, version, KDF id, Argon2id memory (KiB), iterations, lanes, a 16-byte random salt, a 12-byte random nonce, then AES-256-GCM of the accounts as JSON padded to a multiple of 4 KiB (the size hides the account count). The header is the associated data, so any changed byte fails authentication. The key is Argon2id (RFC 9106, `pointycastle`) of the passphrase. The floor is 64 MiB, 3 passes, 4 lanes; a file made below it is refused as a downgrade, and one above the ceilings (1 GiB, 12 passes, 16 lanes) or the size and count limits (4 MiB, 1000 accounts) is refused without running the derivation. Every failure (wrong passphrase, damaged or foreign file) gives the same message, after the same work, so a failure does not say which. Each account in a file goes through the same validation as a scanned QR code.

The passphrase needs at least 12 characters and an estimated 50 bits, is typed twice, and is never stored, logged or kept after use. It cannot be recovered: the screen says so. Restoring adds the accounts that are not already there (duplicates are counted and skipped) after showing them. After the phone's biometrics changed the old vault cannot be opened; restoring then replaces it with a new vault holding the file's accounts and returns to the lock screen. `test/codes/backup_screen_test.dart` also checks that only the vault and the backup code read a saved seed.

## Config

The Biatec OIDC base URL comes from `--dart-define=OIDC_BASE_URL=...` and defaults to the mock OIDC
(`http://10.0.2.2:5080/mock-oidc`, the host machine as seen from the Android emulator).

    flutter run --dart-define=OIDC_BASE_URL=https://oidc.example

The default does not match where the mock actually listens: `pnpm --filter mock-oidc start` serves
`http://127.0.0.1:8089` (`PORT`, `HOST` override it) with no `/mock-oidc` path. From the Android emulator pass
`--dart-define=OIDC_BASE_URL=http://10.0.2.2:8089` (with `adb reverse tcp:8089 tcp:8089` you can instead pass `http://127.0.0.1:8089` and keep the mock on loopback; `HOST=0.0.0.0` exposes it on every interface, and with `MOCK_TEST_HELPERS=1` anyone who reaches it can approve consent as a seeded user). An explicit URL that is not the
default counts as a real Biatec OIDC, so the settings screens are off unless `--dart-define=CONSENT_SETTINGS_API=true`
(see T-084 below).

**URL rules (BCHAT-029).** The URL must be `https`. Plain `http` is accepted only for the built-in mock URL (debug builds) and, in a debug build (not release, not profile), for `localhost`, `127.0.0.1`, `::1` and `10.0.2.2`; credentials, a query or a fragment in the URL are refused. A URL that breaks a rule stops the app at launch with a `ConfigException` that says which. Certificate pinning is not done.

## Enrollment and device key (T-051)

- `lib/keys/device_key_store.dart`: `DeviceKeyStore` is the hardware key (no export method, only `sign`).
  `PlatformDeviceKeyStore` calls the method channel `io.biatec.authenticator/keystore` (`generate`, `load`, `sign`,
  `delete`, each with an `alias`; `generate`/`load` return `{x, y}` base64url P-256). The native side is in
  `android/app/src/main/kotlin/io/biatec/authenticator/KeystorePlugin.kt` (Android Keystore, StrongBox with fallback to the TEE; registered in
  `MainActivity.configureFlutterEngine`) and `ios/Runner/KeystorePlugin.swift` (Secure Enclave, `kSecAttrTokenIDSecureEnclave`; registered in
  `AppDelegate`).
- Key security level (BCHAT-032): `generate` and `load` also return `securityLevel`: `strongbox`, `tee`, `hardware` (Android below API 31, where the platform
  only says "inside secure hardware"), `secure_enclave` (iOS, read from the key's token attribute), `software` or `unknown`. The Android plugin deletes a key that
  ended up in software and answers `insecure_key`; `EnrollmentController.enroll` refuses `software` and `unknown` too (fail closed, also for an older plugin that
  says nothing), and the enrollment screen shows "Key protection: ...". The Kotlin side is compiled, the Swift side is not.
- `lib/enrollment/`: `EnrollmentController` state machine (`notEnrolled`, `generatingKey`, `enrolling`, `inactive`,
  `activeRecoveryPending`, `active`, `failed`), `OidcEnrollmentClient` (`POST /devices`), secure-storage record, and
  the enrollment and recovery-code screen. Attestation is stubbed by the mock (not sent).
- The mock `POST /devices` takes a `login-*` bearer token (`login-alice` is prefilled against the mock) and
  returns `active_at` in epoch seconds. The kid is a random per-install alias (`biatec-authenticator-<hex>`),
  persisted before the key is created and used as both keystore alias and kid, because the server rejects a kid it
  has already seen.
- Recovery code (rule 7): never part of the enrollment response and never stored on the device. Once the device is
  active the app calls `POST /devices/recovery-code` (`Authorization: Device <token>`, refused with 403 while
  inactive), holds the code in memory while it is shown, and confirms with `POST /devices/recovery-code/ack`. These
  two calls are a fallback implemented in the mock; the needed change is in
  `docs/required-changes-biatec-oidc.md` section 4.
- Known gap: the Kotlin plugin has been compiled (Android debug and release builds) but, like the Swift one, NOT run
  on a device or emulator. "Key is non-exportable on device" and the emulator enrollment run are therefore
  unverified and the task is partial until someone runs them (the iOS simulator has no Secure Enclave; use a device).
- Contract test against the real mock: start `MOCK_TEST_HELPERS=1 pnpm --filter mock-oidc start` (the `/mock/*` helpers and the seeded device tokens exist only with that flag), then
  `flutter test --dart-define=MOCK_OIDC_URL=http://127.0.0.1:8089 test/enrollment/mock_oidc_contract_test.dart`
  (skipped otherwise).

## Approvals and receipts (T-052)

- `lib/approvals/`: `ApprovalClient` (`GET /devices/requests`, `GET /consent/requests/{id}`,
  `POST /consent/requests/{id}/receipt`, all `Authorization: Device <token>`), `ApprovalController` (one request),
  the card, the pending list (polls every 5 s, and refreshes at once on a push) and the local history (secure storage, last
  100 decisions with their full receipts).
- The card is rendered only from the fetched consent request. The receipt signs `authorization_details` exactly as
  fetched, canonicalized with `jcs.dart` (RFC 8785, checked against `packages/consent-protocol/vectors`), with ES256
  by the device key, and carries the enrollment attestation (now kept in the enrollment record; a record saved before
  this change has none and must re-enroll).
- Approve: six-digit binding code, biometric check (`local_auth`, biometric only, fails closed), then a fresh fetch
  of the request. If that fetch fails the device is offline and nothing is signed; if the request differs from the
  card, the new one is shown and nothing is signed. Biatec OIDC counts the three attempts; after the third wrong
  code the app signs and posts a `code_failed` receipt.
- Deny is signed too, needs neither code nor biometric check, and signs the last typed code or the empty string.
- Unverified clients: warning banner with fingerprint only; their `binding_message` is never rendered or signed.
- `local_auth` needs `FlutterFragmentActivity` as the Android `MainActivity` and `NSFaceIDUsageDescription` in the
  iOS `Info.plist` once the platform folders exist.
- Contract test against the real mock (it verifies signature and attestation with its JWKS): start the mock, then
  `flutter test --dart-define=MOCK_OIDC_URL=http://127.0.0.1:8089 test/approvals/mock_oidc_approval_contract_test.dart`.
  On Node older than 22.18 start it with `node --experimental-strip-types src/server.ts`.

## Push notifications (T-053)

- `lib/push/`: `PushController` keeps the push token registered at Biatec OIDC (`PUT /devices/push`,
  `Authorization: Device <token>`) on start, on token rotation, on app resume and on navigation, re-sent at most every 10 minutes; a tapped
  notification opens the approval screen for its `auth_req_id` (not a second time if it is already open), and a push
  received in the foreground refreshes the pending list and shows an in-app "New approval request" notice. The payload is read only for `auth_req_id` (`push_payload.dart`); the request itself is always
  fetched from Biatec OIDC, so a forged or altered push can at most open a request the device's user really has.
- FCM through `firebase_messaging` (`FcmPushTransport`, token = the Firebase Installation ID from `register()`).
  Push is off unless all four Firebase options are passed, so nothing per deployment is committed:

      flutter run --dart-define=FIREBASE_API_KEY=... --dart-define=FIREBASE_APP_ID=... \
        --dart-define=FIREBASE_SENDER_ID=... --dart-define=FIREBASE_PROJECT_ID=...

  Without them the app polls exactly as before. Android also needs the Google services Gradle setup and iOS the
  push capability once the platform folders exist.
- The mock never calls FCM; it records what it would send. Every new request queues one message per active device
  with a token, data `{ "auth_req_id": "..." }` only (`GET /mock/push-outbox?kid=...`). Contract test:
  `flutter test --dart-define=MOCK_OIDC_URL=http://127.0.0.1:8089 test/push/mock_oidc_push_contract_test.dart`.

## Devices, trusted clients and security settings (T-084)

- `lib/devices/`, `lib/clients/`, `lib/settings/`: the screens (the Settings tab is `lib/settings/settings_screen.dart`), one `SettingsController` (`lib/security/settings_controller.dart`)
  and `SettingsClient` (`GET /devices`, `POST /devices/{kid}/cancel`, `GET` and `PUT /devices/settings`, all with
  `Authorization: Device <token>`).
- Tightening (lower a threshold, turn a requirement on) applies at once. Loosening (raise a threshold, turn biometric, blocking or
  always-ask off, lift a client pause) first passes the biometric check, then the device key signs a `biatec_settings_change`
  (`isLoosening` decides). Biatec OIDC verifies it; an inactive device cannot loosen.
- Biatec OIDC has none of these APIs yet (`docs/required-changes-biatec-oidc.md` rows 21 and 22, fallback none). `AppConfig.settingsApi` is on
  for the mock URL and off otherwise; override with `--dart-define=CONSENT_SETTINGS_API=true`. When off, the screens say "Not available yet".
- Tests: `flutter test test/settings` (scripted OIDC); `test/settings/mock_oidc_settings_contract_test.dart` runs against a started mock
  (`MOCK_OIDC_URL`, fresh mock). The mock's side is tested by `pnpm --filter mock-oidc test`.
- `flutter analyze` and `flutter test` run in CI (see "Checks"); the contract test needs a started mock and is skipped there.

## Navigation structure (T-219)

A bottom navigation bar (a side rail when the window is short or wide) holds the five top-level destinations, in this order. Each has its own
navigator, so back goes up inside a tab first, then to Codes, and only then leaves the app (`lib/shell/`).

| Tab | Root screen | What is inside |
| --- | --- | --- |
| Codes | `lib/codes/` | Two-factor codes (T-224). |
| Approvals | `lib/approvals/pending_screen.dart` | Open requests, opening a request card, the result. |
| History | `lib/approvals/history_screen.dart` | Past decisions by day, a receipt for each. |
| Devices | `lib/devices/devices_screen.dart` | Enrolled devices, cancelling a pending enrollment. |
| Settings | `lib/settings/settings_screen.dart` | Security (biometric, threshold, blocked clients, a row that opens Trusted clients), Appearance (system, light, dark), About (version, Biatec OIDC server with mock or stage marking, device key protection, open-source notices). |

- Trusted clients (`lib/clients/`) is not a tab: it opens inside the Settings tab, so back returns to Settings and the bar stays.
- The Security group needs the consent settings from Biatec OIDC. While they load, or when they are not available or offline, it says so
  (with a retry) and Appearance and About stay usable.
- The theme choice is `ThemeController` (`lib/settings/theme_controller.dart`): it applies at once and is saved in the device-bound secure storage.
- The app version in About is `appVersion` in `lib/settings/app_info.dart`; a test keeps it equal to `version` in `pubspec.yaml`.
- Accessibility: `test/a11y/all_screens_test.dart` opens every tab at 320x568, in light and dark, at text scale 1 and 3, and checks that nothing
  overflows, that every control is at least 48 dp, and that every control has a label. The screen tests (`test/settings`, `test/approvals`,
  `test/shell`) cover the states of each screen the same way. A state is never shown by colour alone: it always has an icon and words.

## Biometric lock (T-222)

- `lib/lock/lock_controller.dart`: `LockController` (locked, unlocking, unlocked, noBiometric, biometricsChanged, compromised). The only way to
  `unlocked` is `unlock()` with a `BiometricOutcome.success`; there is no PIN, no fallback and no debug switch. A process start is a locked state.
- `lib/shell/app_lock_gate.dart`: builds the shell only while unlocked, so while locked the widget tree holds a lock screen and no secure-area
  screen. It reports the app lifecycle and every touch to the controller. The enrollment screens are the first-run explanation, not the secure area.
- Strong biometric only: `lib/security/biometric_policy.dart` over the channel `io.biatec.authenticator/biometric`. Android
  (`BiometricChannel.kt`): `BiometricPrompt` with `BIOMETRIC_STRONG` and no `DEVICE_CREDENTIAL`; iOS (`BiometricChannel.swift`): the policy
  `deviceOwnerAuthenticationWithBiometrics` with the fallback button hidden. `local_auth` is not used (on Android its biometric-only mode also accepts
  weak biometrics). `test/lock/biometric_policy_test.dart` greps that no weaker policy appears.
- When it locks: at start, after the background delay (immediately, 30 seconds, 1 minute or 5 minutes; default 30 seconds; no "never"; stored
  locally; changed in Settings after a fresh biometric), when the screen locks (native event), and after 2 minutes without a touch. Locking runs the
  `addLockListener` hooks so decrypted seeds and codes leave memory (T-224 registers its own).
- A fresh biometric for each action goes through `LockBiometricGate` (approvals) and `SettingsController.apply` (every security setting, tightening
  too). The biometric requirement is no longer a switch in Settings.
- A tapped notification while locked is queued by id in `ShellController` (memory only); the card opens after the unlock.
- `markBiometricsChanged()` (for the vault and key code to call when a key is invalidated, T-223) and `markCompromised()` (T-228) put the app on a
  screen that says what happened; nothing opens from there.
- Not run on a device: the Kotlin and Swift code (CI builds Android).

## Codes tab (T-224)

- `lib/codes/codes_screen.dart` is the first tab: the list (issuer, account name, the code in groups of three, a countdown ring with the seconds in text, the next code in the last 5 seconds, tap to copy, a button for counter-based accounts), search, reorder (drag handle, or Move up and Move down in the menu), rename, delete (a confirmation, then a fresh biometric), and an optional "hide codes until tapped" mode kept on this phone.
- `CodesController` reads the vault (`lib/totp/vault`) when the tab opens and holds the secrets in memory only while the screen exists. The screen exists only while the app is unlocked, and the controller also wipes on the lock listener. One `CodeTicker` drives every countdown; it ticks on the whole second of the clock, and runs only while the tab shows, the app is in front and the list is loaded.
- Adding (`lib/codes/add/`): QR scanner (`mobile_scanner`; the camera permission is asked when the scanner screen opens, no picture is kept), a pasted `otpauth://` link, or a typed Base32 key. All three end in the same `OtpAccount`; an entry that is refused shows the engine's own message; the account is shown before it is saved; a copy of an account in the list is refused.
- Copy goes through `io.biatec.authenticator/clipboard` (`ClipboardChannel.kt`: `EXTRA_IS_SENSITIVE`; `ClipboardChannel.swift`: local only, expiring) and is cleared after 30 seconds only if the clipboard still holds that code.
- Clock: `ServerClock` reads the `Date` header of the calls to Biatec OIDC (the pinned client reports to it) and the tab warns above 5 seconds. A time earlier than the latest time shown (`OtpGenerator.clockIsPlausible`) hides time-based codes; a saved time more than 30 days ahead of the clock is forgotten, so a corrected clock is trusted again.
- Vault key window: the vault's secret key accepts a strong biometric for 30 seconds (Android `setUserAuthenticationParameters`, iOS `touchIDAuthenticationAllowableReuseDuration`), so the unlock that opened the app also opens every secret instead of one prompt per account. After the window each secret read prompts again.
- Not run on a device: the scanner, the clipboard channels and the vault window (Kotlin, Swift).

## Device integrity (T-228)

- `lib/integrity/`: `IntegrityDetector`s that are pure functions of an `IntegrityEnvironment` (files, writable folders, `/proc`, properties, debugger, loaded classes and libraries, signing certificate), so each is tested against a fake phone in `test/integrity/`. Android: root (su and manager files, open system folders, test-keys, debuggable or insecure builds), debugger and tracer, hooking (Frida, Substrate, Xposed), emulator, signing certificate. iOS: jailbreak files and an open sandbox, debugger (`P_TRACED`), injected libraries, simulator.
- `IntegrityGuard` keeps the answer for 30 seconds; the lock asks again (forced) on resume and before every approval (`reauthenticate`). A detector or checker that fails counts as a hit.
- Policy in `LockController`: `failClosed` (default true; `main.dart` passes `kReleaseMode`). Closed: the phone never gets the fingerprint prompt, the memory is cleared, and `CompromisedScreen` shows. That screen says that a safety check was not passed and names no detector or group; "Check again" runs the check anew and the normal unlock follows if it passes. Open (debug builds): the app opens with a warning on the lock screen.
- Release signing digest: `--dart-define=RELEASE_CERT_SHA256=<sha-256 of the release certificate>`. On Android a release build without it is not trusted (an unconfigured digest is a compromised result), so set it in the release build step.
- Attestation hook: `AttestationProvider` over `io.biatec.authenticator/attestation` (see "Platform attestation" below).
- Not run on a device: the Kotlin and Swift fact readers and App Attest.

## Security documentation and checks (T-230)

- `docs/AUTHENTICATOR-SECURITY.md` is the OWASP MASVS v2.0 Level 2 conformance matrix: every control, a status (met, partly, open, not applicable) and the evidence. The authenticator section of `docs/threat-model.md` lists the abuse cases; `docs/AUTHENTICATOR-PENTEST-BRIEF.md` is the brief for the independent test; `docs/AUTHENTICATOR-RELEASE-CHECKLIST.md` is the signed-release checklist.
- `dart run tool/matrix_check.dart` fails when a control is missing, a status is invalid, a `met` row has no evidence, a link points nowhere, or an `open` row names no task or owner. `dart run tool/gates.dart` fails on `print(` and `debugPrint(` in `lib/` and on secret-like strings in the source. Both are tested against seeded violations in `test/tool/`, and run in CI (job `authenticator-security`, which also scans `pubspec.lock` with OSV, checks that `pub get` leaves the lockfile alone, and publishes a CycloneDX SBOM).

## Minimum version and update enforcement (T-232)

- Platform floors: Android 9 (`minSdk = 28`, StrongBox keys, `setUnlockedDeviceRequired`, the signing-certificate API) and iOS 15 (App Attest, current Secure Enclave and biometric behaviour). Reasons are in `android/app/build.gradle.kts`; `test/update` checks both floors.
- `lib/update/update_guard.dart`: `MinimumBuildMonitor` reads `X-Biatec-Min-App-Build` from every answer of the pinned client and keeps the highest value; `UpdateGuard` blocks a build older than it, or past `--dart-define=BUILD_EXPIRES=<date>` (UTC; the fallback while Biatec OIDC does not send the header). `LockController` (`updates:`) then clears memory and shows `UpdateRequiredScreen`, at start, on resume, before an approval, and the moment an answer arrives while the app is open.
- The build passes its number with `--dart-define=APP_BUILD=<n>` (the number after the plus sign of `version`; a test keeps the default equal to `pubspec.yaml`). The screen does not link to a store (no `url_launcher`); it names the store.
- The mock sends the header (`MOCK_MIN_APP_BUILD`, default 1). The API shape is row 24 of `docs/required-changes-biatec-oidc.md`.

## Privacy and erase (T-233)

- `lib/privacy/storage_inventory.dart` lists, in words for the user, what the app stores, what it sends to Biatec OIDC and the push service, and what it never collects. `PrivacyScreen` (Settings > About > Privacy) shows it. A test fails when a `'biatec.*'` storage key in `lib/` is not named in the inventory, or a listed key is not used.
- `PhoneEraser` (`lib/privacy/phone_eraser.dart`) is "Erase everything on this phone": a confirmation that says what is lost, a fresh biometric, then the vault file, the vault keys, the device key, the secure storage and finally the enrollment (which moves the app to the enrollment screen). Every step runs even if an earlier one fails, has a time limit, and a failure is named on the screen. It removes data on the phone only; Biatec OIDC keeps its record of the device until it is cancelled from the account.
- The answers for the Play Data safety form and the Apple App Privacy labels are in `docs/AUTHENTICATOR-STORE-PRIVACY.md`.

## Platform attestation at enrollment (T-234)

- `EnrollmentController` asks the platform whether it can attest (`AttestationProvider.supported`), gets a single-use nonce from Biatec OIDC (`POST /devices/challenge` with the login), asks the platform for a token bound to it, and sends `attestation_challenge` and `platform_attestation` with `POST /devices`. If the platform cannot attest, gives no token, Biatec OIDC offers no challenge or anything throws, the enrollment goes **without** one: nothing is made up.
- iOS: App Attest (`IntegrityChannel.swift`, entitlement in `Runner.entitlements`; the App Attest capability must be on the App ID). Android: Play Integrity (`AttestationChannel.kt`, `com.google.android.play:integrity`), which needs the release's Google Cloud project number: `-PplayIntegrityProject=<number>` or `gradle.properties`; without it Android is not supported and enrolls without an attestation.
- When Biatec OIDC returns `attestation_refresh_after`, the record keeps it and the next refresh after that date sends a fresh attestation (`PUT /devices/attestation`), quietly. The API shape and the fallback are row 25 of `docs/required-changes-biatec-oidc.md`; the mock implements it.
- Not run on a device: both platform implementations, and the real token verification (Biatec OIDC's side).
