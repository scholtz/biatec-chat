# Biatec Consent Protocol, version 1

Status: draft. This document is the integrator-facing specification. `PRODUCT-DESCRIPTION.md` ("Biatec Authenticator And The Biatec Consent Protocol") is the product source of truth and wins on any conflict.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Overview

The Biatec Consent Protocol lets a user approve or deny one precisely described action on a trusted, device-bound surface (the Biatec Authenticator) while the action is requested from somewhere else (the Biatec Chat widget, a bank app, a website). It is a profile over existing standards, not a new protocol:

| Need | Standard |
| --- | --- |
| Push an approval to a device that did not start the flow | OpenID Connect CIBA (push and poll modes) |
| Describe exactly what is approved | OAuth 2.0 Rich Authorization Requests, RFC 9396 (`authorization_details`) |
| Bind approval to amount and payee | PSD2 dynamic linking, carried by `authorization_details`; CIBA `binding_message` for an optional purpose text |
| Step up only when needed | OAuth 2.0 Step-up Authentication Challenge, RFC 9470 |
| Hardening | FAPI 2.0 Security Profile, FAPI-CIBA: PKCE, exact redirect URIs, short lifetimes, `requested_expiry` default 300 s |
| Canonical signed bytes | JSON Canonicalization Scheme, RFC 8785 |
| Device keys | Hardware-backed P-256 keys (Secure Enclave, StrongBox), attested at enrollment |
| Client identity | RFC 7591 Dynamic Client Registration and OpenID Federation 1.0 trust chains |
| Consent record | Kantara Consent Receipt field layout |

Roles:

- **Client**: the requesting application (Biatec Chat backend, a bank, a fintech).
- **Biatec OIDC**: the authorization server. It decodes the transaction group, values it, opens the request, generates the binding code, stores the request and verifies and consumes receipts.
- **Authenticator**: the mobile app holding the device key.
- **User**: sees the card on the authenticator and the binding code on the requesting surface.

Machine-readable definitions live in `schemas/` (JSON Schema 2020-12) and signed examples in `vectors/`. Everything in this document that is normative about a wire object is expressed by a schema.

## 2. The request model

A consent request at Biatec OIDC is always the same object, whichever entry point opened it (`schemas/consent-request.schema.json`):

- `authorization_details`: exactly one typed object, decoded by Biatec OIDC (section 3).
- A **binding code** generated by Biatec OIDC, returned only to the client (section 7).
- An optional client-supplied `binding_message`.
- The client identity (`client.entity_id`, verified flag).
- `requested_expiry` (default and maximum 300 seconds) and the derived `expiry`.
- The **bound hash** (`group_hash` or `request_hash`) the consent is tied to.
- The reporting `origin` and the pairwise `sub`.

Client-supplied amounts or payees are never accepted as the thing being consented to; the group (or canonical limits body) is.

## 3. Authorization details types

`authorization_details` is an array of exactly one object (`schemas/authorization-details.schema.json`), of one of the two types below.

### 3.1 `biatec_transaction`

Describes one signing call (`schemas/authorization-details-transaction.schema.json`): `network`, `group_hash`, `sender`, optional `receiver` or `application_id`, `asset`, `amount` and `fiat_value`. Biatec OIDC decodes every field from the unsigned group itself. Amounts are decimal strings, never JSON numbers, so canonicalization loses no precision. The `group_hash` is the Algorand group ID recomputed from the handed transactions (base32, 52 characters), or for Bitcoin the SHA-256 intent hash derived from a PSBT carrying prevout data (lowercase hex). The signing endpoint MUST refuse a request whose recomputed hash differs from the consented one.

### 3.2 `biatec_limits_change`

Describes a change of spending limits (`schemas/authorization-details-limits-change.schema.json`): `current_limits`, `requested_limits` and `request_hash`, the lowercase hex SHA-256 of the RFC 8785 canonical request body of `PUT /wallet/limits`. The vectors include a worked example: the body `{"per_day_eur":"5000","per_transaction_eur":"2000"}` hashes to the `request_hash` in `vectors/receipts.json`.

## 4. Step-up entry

The client calls a wallet endpoint (`POST /wallet/{network}/{address}/sign` or `PUT /wallet/limits`) with an ordinary token. The CIBA request inherits that token's scopes and audience, so the elevated token carries the same `sign` or `manage-limits` scope and resource and can be presented straight back to the wallet endpoint. Biatec OIDC decides consent is needed (value above threshold, cooling-off or first use, the client sent `requireConsent: true`, or the user set "always ask" for this client), opens the request itself and answers with an RFC 9470 challenge:

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="biatec:consent"
Content-Type: application/json
```

```json schema=stepup-challenge
{
  "error": "insufficient_user_authentication",
  "error_description": "Phone approval is required for this group.",
  "acr_values": "biatec:consent",
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "expires_in": 300,
  "interval": 2,
  "binding_code": "483920"
}
```

The client shows the binding code on its surface, polls the token endpoint (or receives the push-mode callback), then retries the wallet endpoint with the elevated token and the same unsigned group:

```http
POST /token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:openid:params:grant-type:ciba&auth_req_id=ciba_8257c10231dd9b46e2f877484cf0b2a3&resource=https%3A%2F%2Fapi.biatec.io
```

The token response carries the access token (`acr` = `biatec:consent`, bound to the group hash, 300 seconds) and the signed receipt in `consent_receipt` (`schemas/token-response.schema.json`). A step-up receipt signs an empty `binding_message`, because no client text exists.

## 5. Direct entry

A client that already built the group and wants the consent in hand before calling the wallet endpoint (for example to drive its own progress UI) calls the CIBA backchannel authentication endpoint with the exact unsigned group (or the canonical limits request body) plus an optional `binding_message`. Biatec OIDC decodes the group and builds `authorization_details` exactly as in the step-up entry. A request that carries `authorization_details` is invalid.

```http
POST /connect/ciba
Content-Type: application/json
```

```json schema=backchannel-authentication-request
{
  "scope": "sign",
  "resource": "https://api.biatec.io",
  "login_hint": "user@example.com",
  "network": "algorand-mainnet",
  "address": "YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE",
  "unsigned_group": ["gqNzaWfEQ...base64 unsigned transaction..."],
  "binding_message": "Invoice 2026-0042",
  "requested_expiry": 300,
  "origin": "https://bank.example"
}
```

```json schema=backchannel-authentication-response
{
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "expires_in": 300,
  "interval": 2,
  "binding_code": "120934"
}
```

(The wire encoding of the endpoint follows CIBA, form-encoded; JSON is shown for readability and is what the schema validates.) The client then displays the binding code, obtains the token as in section 4 and presents it to the wallet endpoint, which checks the hash as usual.

`binding_message` is rendered on the card, under the decoded facts and visibly attributed to the client, only for clients whose entity statement chains to a recognized trust anchor. For unverified clients it is not rendered and therefore signed as the empty string; the raw text is kept only in the unsigned request log. An unverified client therefore has no free-text channel to the trusted surface.

### 5.1 One model, two entries

Both entries produce the same request object, the same receipt schema, the same canonical form and the same signing rules. Receipts differ only in field values (`binding_message`, `client_entity_id`, the detail fields). In `vectors/receipts.json`, `stepup-*` and `direct-*` vectors validate against identical schemas.

The client retrieves the receipt in the CIBA token response (`consent_receipt`) and again at `GET /consent/receipts/{auth_req_id}`, only as the client the request belongs to: the one that opened it (direct entry) or the one whose token was challenged (step-up entry).

## 6. The authenticator's request object

The authenticator learns of a request from a push notification that carries only the `auth_req_id`. It then fetches the request over an authenticated channel using its device key. The response is the consent request object (`schemas/consent-request.schema.json`) and never contains the binding code:

```json schema=consent-request
{
  "auth_req_id": "ciba_8257c10231dd9b46e2f877484cf0b2a3",
  "entry": "step-up",
  "authorization_details": [
    {
      "type": "biatec_transaction",
      "network": "algorand-mainnet",
      "group_hash": "BJPMYYUBSMQWYXMEBZT2ZHFZTWCIJAFAIMUZEGOJZKJPRBKU5KNA",
      "sender": "YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE",
      "receiver": "WSNJGAWN52IJMHAEFZIOPCS3IXSHS4C46QDNSKWDEWQ3E6M4HUNLYTHJXE",
      "asset": { "id": "31566704", "symbol": "USDC", "decimals": 6 },
      "amount": "5000.000000",
      "fiat_value": { "amount": "4612.50", "currency": "EUR" }
    }
  ],
  "client": {
    "entity_id": "https://chat.biatec.io",
    "verified": true,
    "display_name": "Biatec Chat",
    "domain": "chat.biatec.io"
  },
  "binding_message": "",
  "requested_expiry": 300,
  "expiry": 1792425900,
  "bound_hash": "BJPMYYUBSMQWYXMEBZT2ZHFZTWCIJAFAIMUZEGOJZKJPRBKU5KNA",
  "origin": "https://app.biatec.io",
  "sub": "pw_7c1f0a52e9b34d68"
}
```

For an unverified client, `client` carries only `entity_id`, `verified: false` and a short `fingerprint`; `display_name`, `logo_uri` and `domain` MUST be absent.

## 7. The binding code

Biatec OIDC generates a six digit binding code (`schemas/binding-code.schema.json`) and returns it only to the client. The authenticator does not display it; the user types the code shown on the requesting surface into the authenticator to approve. The user has three attempts in total within the request's validity. The third wrong code produces a denial recorded as `code_failed`; an explicit Deny produces a denial recorded as `deny`. Only explicit denies count toward the denial counter of section 11. The code the user entered is part of the signed receipt.

## 8. The signed receipt

The device signs the RFC 8785 canonical form of exactly this object (`schemas/consent-receipt-signed.schema.json`):

```
{ authorization_details, auth_req_id, client_entity_id, binding_code, decision, expiry, sub, binding_message }
```

- `client_entity_id` is the OpenID Federation entity identifier, or the `client_id` when the client has none.
- `decision` is `approve`, `deny` or `code_failed`.
- `expiry` is Unix time in seconds.
- `binding_message` is the text as rendered, or the empty string if none was rendered.
- `auth_req_id` is the single-use nonce.

Signing procedure:

1. Build the object above from the request fetched in section 6 and the code the user typed.
2. Canonicalize it with RFC 8785. All amounts are strings; integers MUST be at most 2^53 - 1.
3. Sign the UTF-8 bytes with ES256 (ECDSA P-256, SHA-256). The signature is the 64-byte IEEE P1363 `r || s` form, base64url without padding; verifiers MUST reject non-canonical encodings.

The receipt envelope (`schemas/consent-receipt.schema.json`) adds `version`, `alg`, `signature`, `issued_at` (informational, unsigned) and `device`: the key ID, the device public key as a JWK, and the **attestation**, a compact ES256 JWS signed by a Biatec OIDC JWKS key whose payload binds `sub`, `device_kid` and `device_jwk_thumbprint` (RFC 7638 thumbprint of the device public key).

Worked example, the first vector in `vectors/receipts.json` (canonical bytes, one line):

```
{"auth_req_id":"ciba_8257c10231dd9b46e2f877484cf0b2a3","authorization_details":[{"amount":"5000.000000","asset":{"decimals":6,"id":"31566704","symbol":"USDC"},"fiat_value":{"amount":"4612.50","currency":"EUR"},"group_hash":"BJPMYYUBSMQWYXMEBZT2ZHFZTWCIJAFAIMUZEGOJZKJPRBKU5KNA","network":"algorand-mainnet","receiver":"WSNJGAWN52IJMHAEFZIOPCS3IXSHS4C46QDNSKWDEWQ3E6M4HUNLYTHJXE","sender":"YKBLPFVKZFZFGOVHQK6L63YX67B76YBZCSYYGU4WD7QC3PRRP4U7Q2DCWE","type":"biatec_transaction"}],"binding_code":"483920","binding_message":"","client_entity_id":"https://chat.biatec.io","decision":"approve","expiry":1792425900,"sub":"pw_7c1f0a52e9b34d68"}
```

### 8.1 Offline verification

Anyone with the Biatec OIDC JWKS verifies a receipt without further lookups:

1. Validate the receipt against the schema.
2. Verify the attestation JWS with the JWKS key named by its `kid`.
3. Check that the attestation header `typ` is `biatec-device-attestation+jwt`, that its signing key is an EC P-256 signature key of the Biatec OIDC JWKS, that its `iss` is the expected issuer, that its `exp` is in the future (verifiers fail closed on a missing clock input), and that its `sub` equals `signed.sub`, `device_kid` equals `device.kid` and `device_jwk_thumbprint` equals the thumbprint of `device.public_key`.
4. Canonicalize `signed` (RFC 8785) and verify `signature` over its UTF-8 bytes with `device.public_key`.
5. For authorization, compare every signed member (`authorization_details`, `auth_req_id`, `client_entity_id`, `binding_message`, `expiry`, `sub`) and the bound hash with the stored request the verifier is waiting on, never with data the receipt supplies. Additionally require `decision` = `approve` and that `binding_code` equals, in constant time, the code Biatec OIDC issued for this `auth_req_id` (number matching, rule 2), compare the `signed.authorization_details` hash fields with the group or body presented, check `expiry`, and consume `auth_req_id` once. A verifier MUST NOT treat a `deny` or `code_failed` receipt, or an expired one, as consent. Verification helpers return a boolean and never throw on malformed input.

Reference implementations: `scripts/lib.mjs` (JavaScript; `verifyReceipt` covers steps 2-4 and `verifyApproval` step 5, which also matches the receipt against the stored request) and `backend/Biatec.Chat.Tests/Canonical/ConsentProtocolVectorTests.cs` (.NET, using the backend `JsonCanonicalizer`). Both verify every vector signature; the .NET test also verifies the attestation.

## 10. Third-party integration

1. Publish an OpenID Federation entity configuration and obtain a subordinate statement from a recognized trust anchor.
2. Self-register with RFC 7591 Dynamic Client Registration, declaring `backchannel_token_delivery_mode` and the `authorization_details_types` used. Capabilities needing the `manage-limits` scope stay reserved for operator-allowlisted clients.
3. Use the direct entry (section 5) or handle the step-up challenge (section 4). In both cases display the returned binding code, poll or receive the token, and present it to the wallet endpoint.

### 11.1 Requester identity and cooling-off

- **Rule 3.** The authenticator shows a client's display name, logo and domain only when the client's entity statement chains to a trust anchor. Unverified clients are shown as "Unverified application" with a short fingerprint of their `client_id` in a warning style and nothing else; the schema forbids the other fields for them. The user's policy may block unverified clients entirely. Biatec Chat's own tenant chains to Biatec's trust anchor.
- **Rule 4.** For a user with an active enrolled device, for the first 24 hours after a client registers, and for the first action the user ever performs through a client, every signing request requires phone approval regardless of value, as if the threshold were zero. A client chaining to a recognized trust anchor skips the 24-hour part but not the first-use part. An enrolled but still inactive device counts as no active device. For a user with no active device, Biatec OIDC instead applies a reduced per-client daily cap (default 100 EUR) during the client's first 24 hours and the user's first day with the client.

### 11.2 Validity and consumption

- **Rule 5.** A consent is valid for 300 seconds by default, bound to one group hash, and authorizes exactly one signing call. It is spent only when Biatec OIDC actually signs; a call failing the hash check, the spending limits or any other validation leaves it unspent. The signing endpoint signs for one sender address per call, so an action needing two senders is two groups, two signing calls and, if each needs it, two consents. A Bitcoin transaction in version 1 spends from one address; a transfer needing several addresses is split into one transaction per address, each with its own group hash. Biatec OIDC rejects a signing request whose group hash differs from the consented hash.

### 11.3 Device keys, enrollment and recovery

- **Rule 6.** The authenticator holds a hardware-backed key pair and an enrollment identifier, and no wallet keys, cloud-storage tokens or long-lived OAuth tokens. The key is generated in hardware and attested at enrollment (OAuth Attestation-Based Client Authentication with Apple App Attest and Google Play Integrity); attestation is presented again when receipts are posted.
- **Rule 7.** Enrollment starts with a fresh full Biatec OIDC login including the identity provider's multi-factor step. If an already-enrolled device approves, the new device is active immediately. Otherwise (first device or lost-device recovery) it is enrolled but inactive for 24 hours; every enrolled device and the user's email receive a cancel link, and during that period a user with no other active device cannot complete any action needing phone approval. A recovery code, generated and shown once only after a device has become active, activates a later device immediately.
- **Rule 8.** A user without an active enrolled device can use every below-threshold capability (subject to the reduced caps of rule 4) but cannot complete an action needing phone approval. The default threshold is not lowered for such users.

### 11.4 Denial, pending limits and pause

- **Rule 10.** A denial produces a signed denial receipt (`decision` = `deny`) and immediately cancels the pending action in the requesting surface. Denials never auto-block a client. Biatec OIDC allows at most three pending requests per client per user per origin (origin is reported by the client with each request), rate-limits new requests as an anti-spam measure only (default 60 per hour per client per user, no per-second burst limit), and after three explicit denials in a day the authenticator offers a one-tap "pause this client on this site for 24 hours", scoped to the reporting origin and liftable from the trusted-clients screen. `code_failed` denials do not count toward the three.

### 11.5 Limits

- **Rule 11.** Authenticator approval never bypasses spending limits; it is an additional requirement. Biatec OIDC's per-user limits cover the user's own addresses only; funds inside a Biatec Safe are governed by the safe's on-chain signer-group limits plus the consent threshold applied to each approval.

## 12. Threshold, loosening and tightening

The default policy is that any single action valued above 1000 EUR requires authenticator approval. Users can lower the threshold, enable approval for everything, or set per-client thresholds, but cannot raise it above a deployment-defined ceiling. Any change that loosens protection is itself a consent-elevated action (`biatec_limits_change` or a settings equivalent) approved on an active device; tightening applies immediately. The threshold and per-client settings are stored and enforced by Biatec OIDC at the signing endpoint. A client may ask for more consent (`requireConsent: true`) but never less.
