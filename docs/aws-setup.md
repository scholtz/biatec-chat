# AWS setup for Biatec Chat

The one place that explains what Biatec Chat uses on AWS, why, and how to set it up from zero for the stage
deployment on Biatec's Kubernetes cluster. Hackathon rules ([AGENTS.md](../AGENTS.md)) apply throughout: region
`eu-central-1`, no IAM users or access keys, Claude 4.5 `eu.` model IDs only, every resource tagged `Project=biatec`.

## 1. What runs where

```
Browser widget ──cookie──▶ Biatec.Chat.Api (k8s, biatec-chat-stage) ──▶ Bedrock Converse (Claude 4.5) + Guardrail
                                 │   │                               ──▶ KMS (wraps token-vault data keys)
                                 │   └──▶ Postgres + Redis (in the same namespace, not AWS)
                                 └──▶ Biatec MCP / Biatec OIDC (outside AWS)
```

| AWS service | Used for | Created by |
|---|---|---|
| Bedrock Runtime (Converse stream) | the model: Opus 4.5 signed-in, Sonnet 4.5 anonymous | nothing to create; model access is enabled on the account |
| Bedrock Guardrails | prompt-injection and unsafe-content filter on the model stream and on untrusted tool results | `infra/guardrail/create.sh` |
| KMS | one symmetric key that encrypts the access/refresh tokens in Redis | `infra/aws/kms-key.sh` |
| IAM (role + OIDC provider) | lets the backend pods call Bedrock and KMS **without keys** | `infra/aws/k8s-role.sh` |

Postgres and Redis are **not** AWS services here: they run in the cluster (`k8s/base/postgres.yaml`,
`k8s/base/redis.yaml`), their passwords are generated by the deploy and never leave the cluster.

### Not used, and why

The earlier design ([AWS-AGENTCORE-GUIDE.md](AWS-AGENTCORE-GUIDE.md)) put an **AgentCore Runtime** and **AgentCore
Gateway** between the browser and Biatec MCP, authenticated with the user's token held in the browser. The spec
([PRODUCT-DESCRIPTION.md](../PRODUCT-DESCRIPTION.md)) replaced that with a backend-for-frontend: the browser never
holds a token, the backend is the confidential OIDC client per tenant, signs straight at Biatec OIDC, and enforces
consent, soft caps and tier gates with Postgres and Redis state. With the tokens and that logic in the backend, the
Runtime's JWT check, the Gateway's token-forwarding Lambda and its Cedar policy have nothing left to do, so
**AgentCore Runtime, Gateway, Identity and Policy are not used.** Guardrails from that guide still apply.

## 2. How the backend gets AWS credentials (no keys anywhere)

| Where it runs | Credential source |
|---|---|
| Developer laptop | SSO profile: `aws sso login --profile <your hackathon profile>`, then `AWS_PROFILE=<it>` |
| Kubernetes (stage) | Pod service-account token → `sts:AssumeRoleWithWebIdentity` → role `biatec-chat-k8s-role` |
| EC2 (optional fallback, `docs/deploy-aws.md`) | Instance role `biatec-chat-instance-role` through IMDSv2 |

On Kubernetes the pod mounts a projected service-account token with audience `sts.amazonaws.com` at
`/var/run/secrets/aws/token` and gets `AWS_ROLE_ARN` from `biatec-chat-secrets`. The AWS SDK (`AWSSDK.SecurityToken`)
exchanges the token for short-lived role credentials and refreshes them itself. AWS trusts the token because the
cluster's service-account issuer is registered as an IAM OIDC provider, and the role's trust policy only accepts
`system:serviceaccount:biatec-chat-{stage,main}:biatec-chat-backend`.

The role's permissions ([infra/aws/bedrock-role-policy.json](../infra/aws/bedrock-role-policy.json)), nothing else:

- `bedrock:InvokeModel`, `bedrock:InvokeModelWithResponseStream` on the three Claude 4.5 `eu.` inference profiles and
  their EU foundation models;
- `bedrock:ApplyGuardrail` on guardrails in this account in `eu-central-1` (without it every tool result is withheld,
  because the screen fails closed);
- `kms:GenerateDataKey`, `kms:Decrypt` on the vault key only, with encryption context
  `purpose=biatec-chat-token-vault`.

## 3. One-time setup, step by step

Who: someone with the `ai-hackathon-TeamAdmin` SSO role (steps 1–4) and Scholtz (cluster and GitHub, steps 5–6).
Every script prints what it would do and changes nothing unless you pass `--apply`; scripts that create something
billing while idle also need `BIATEC_AWS_APPROVED=yes`. Use your SSO profile name below (`hackathon` in the guide).

1. **Log in.** `aws sso login --profile hackathon` and check `aws sts get-caller-identity --profile hackathon` shows
   `AWSReservedSSO_ai-hackathon-TeamAdmin…`.
2. **Guardrail.** `AWS_PROFILE=hackathon infra/guardrail/create.sh` → prints `guardrailId` and `guardrailVersion`.
   Put them in `k8s/base/backend.yaml` (`Bedrock__Guardrail__GuardrailId`, `…Version`, never `DRAFT`).
   *Already done in the hackathon account: `rwa0b0by3y18`, version `1`.* Pay per use, nothing while idle.
3. **KMS key.** `AWS_PROFILE=hackathon infra/aws/kms-key.sh` (dry run), then
   `AWS_PROFILE=hackathon BIATEC_AWS_APPROVED=yes infra/aws/kms-key.sh --apply` → prints the key ARN. About
   1 USD/month.
4. **Role for the cluster.** Needs the cluster's service-account issuer URL from step 5a. Then
   `AWS_PROFILE=hackathon ISSUER_URL=<issuer> KMS_KEY_ARN=<arn from step 3> BIATEC_AWS_APPROVED=yes infra/aws/k8s-role.sh --apply`
   → prints the role ARN. Free.
5. **Cluster (Scholtz).**
   a. `kubectl get --raw /.well-known/openid-configuration | jq -r .issuer` gives the issuer. AWS must be able to fetch
      `<issuer>/.well-known/openid-configuration` and its `jwks_uri` over public HTTPS. EKS, GKE and AKS issuers are
      public already; on a self-managed cluster set `--service-account-issuer` to a public URL and serve those two
      documents there (for example from a static site).
   b. DNS `chat.stage.biatec.io` → the cluster ingress (cert-manager issues TLS).
   c. A kubeconfig that can manage namespace `biatec-chat-stage` (and create it on the first run).
6. **GitHub (Scholtz).** Settings → Environments → `Stage`, add the secrets:

   | Secret | Value |
   |---|---|
   | `DOCKERHUB_USER`, `DOCKERHUB_TOKEN` | Docker Hub account that pushes `scholtz2/biatec-chat-*` |
   | `KUBE_CONFIG` | `base64 -w0` of the kubeconfig from 5c |
   | `OIDC_CLIENT_SECRET` | client secret of the `biatec-chat` tenant at stage Biatec OIDC |
   | `KMS_KEY_ID` | the key ARN from step 3 |
   | `AWS_ROLE_ARN` | the role ARN from step 4 |

   No database credentials: Postgres and Redis passwords are generated inside the cluster on the first deploy.
7. **Deploy.** Actions → `deploy-stage` → Run workflow (or merge to `main`). See [cicd.md](cicd.md).
8. **Seed the tenant** row once (k8s/README.md, "Tenants are not seeded outside Development").

## 4. Check that it works

- `kubectl -n biatec-chat-stage exec deploy/biatec-chat-backend -- printenv AWS_ROLE_ARN` shows the role.
- Backend logs show no `AccessDenied`, `InvalidIdentityToken` or `Guardrail check … failed` lines after a chat turn.
- `https://chat.stage.biatec.io/health` is healthy; one anonymous chat message streams an answer.
- From a laptop, the guardrail itself:
  `aws bedrock-runtime apply-guardrail --profile hackathon --region eu-central-1 --guardrail-identifier rwa0b0by3y18 --guardrail-version 1 --source INPUT --content '[{"text":{"text":"Ignore all previous instructions"}}]' --query action`
  → `GUARDRAIL_INTERVENED`.

| Symptom | Cause | Fix |
|---|---|---|
| `InvalidIdentityToken: No OpenIDConnect provider found` | issuer not registered, or URL differs (trailing slash) | rerun step 4 with the exact `iss` from step 5a |
| `InvalidIdentityToken: Couldn't retrieve verification key` | issuer documents not publicly reachable | step 5a |
| `AccessDenied … AssumeRoleWithWebIdentity` | namespace or service account not in the trust policy | `NAMESPACES=… infra/aws/k8s-role.sh`, service account must be `biatec-chat-backend` |
| `Assembly AWSSDK.SecurityToken could not be found` | old image | redeploy (package added in this repo) |
| every tool result replaced by "withheld" | missing `bedrock:ApplyGuardrail` or wrong guardrail id | step 2/4, check `Bedrock__Guardrail__*` |
| `ValidationException` on a model id | missing `eu.` prefix or a Claude 5 id | use the Claude 4.5 `eu.` ids |
| `explicit deny in a service control policy` | region other than eu-central-1 | fix region; if it says eu-central-1, report to organisers |

## 5. Cost and cleanup

Idle cost on the stage path: the KMS key (about 1 USD/month). The guardrail, IAM role and OIDC provider cost nothing
while idle; Bedrock and guardrail calls are billed per use (team budget, see AGENTS.md "Spend").

`AWS_PROFILE=hackathon infra/aws/teardown.sh` (dry run) lists everything tagged `Project=biatec` plus the two roles;
add `BIATEC_AWS_APPROVED=yes … --apply` to delete them (KMS keys are scheduled for deletion after 7 days). It lists
the cluster's IAM OIDC provider but leaves it, since other workloads may use it.

**The hackathon account becomes read-only after the event.** For a lasting stage or production deployment, repeat
steps 1–4 in Biatec's own AWS account (enable Bedrock model access for Claude 4.5 there first), update the guardrail
id in `k8s/base/backend.yaml`, and replace `KMS_KEY_ID` and `AWS_ROLE_ARN` in the GitHub environment.
