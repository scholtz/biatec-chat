# biatec_authenticator

Biatec Authenticator (Flutter): device enrollment with a hardware key, consent approvals with signed receipts, push
notifications, and device, trusted-client and security settings screens. It runs against the mock Biatec OIDC
(`packages/consent-protocol/mock-oidc`); real Biatec OIDC has no consent or device APIs yet
([docs/required-changes-biatec-oidc.md](../../docs/required-changes-biatec-oidc.md)).

## Platform folders

`android/` and `ios/` are committed (generated by `flutter create --platforms=android,ios --project-name biatec_authenticator --org io.biatec .`,
then hardened; BCHAT-008). The application id and bundle identifier are `io.biatec.authenticator`. What is set, and kept by
`test/platform_hardening_test.dart`:

- **Android:** no backup or device transfer (`allowBackup="false"`, `data_extraction_rules.xml`), no cleartext traffic (the debug manifest alone allows
  it, for the local mock), `MainActivity` (the launcher) is the only exported component and the only activity; the one service (`StayConnectedService`) and the
  boot receiver are not exported (T-244); the window is `FLAG_SECURE`, `KeystorePlugin` is registered in `MainActivity` (and in the service's engine), release builds are
  minified and signed with your own key (below). Libraries add receivers and services when the manifests merge (the notifications plugin's, and the AndroidX profile
  installer, protected by `android.permission.DUMP`); review the merged manifest (`build/app/intermediates/merged_manifests/release/`) on each release.
- **iOS:** App Transport Security at its default (no exceptions), no URL schemes, a Face ID usage string, `KeystorePlugin` (Secure Enclave) registered in
  `AppDelegate`, and `ScreenCover` hides the content from the app switcher and while the screen is recorded or mirrored.
- **Push on iOS is optional and off:** there is no push entitlement in the committed project; the optional Apple wake and its entitlements file are described under "Device channel and
  notifications (T-244)". The deployment target is iOS 15.
- **Not verified:** the Kotlin plugin compiles (`flutter build apk --debug` and `--release` were run), but nothing was run on a device or an emulator.
  The Swift files (`KeystorePlugin.swift`, `ScreenCover.swift`, `AppDelegate.swift`) and the Xcode project edits were written without Xcode: build them
  on a Mac before the first iOS release.

### Release build

The release build never uses the debug key. Create a keystore once, keep it out of the repository, and describe it in `android/key.properties`
(git-ignored):

    storeFile=/absolute/path/to/upload-keystore.jks   (or relative to android/)
    storePassword=...
    keyAlias=...
    keyPassword=...

    flutter build apk --release --dart-define=OIDC_BASE_URL=https://oidc.example

Without `key.properties` the release build fails with `SigningConfig "release" is missing required property "storeFile"`. A release build also
needs `OIDC_BASE_URL` (https only; there is no mock default).

The `windows/` folder is checked in. Build it with `flutter build windows` (needs Visual Studio with the "Desktop
development with C++" workload and Windows Developer Mode for plugin symlinks). `windows/CMakeLists.txt` defines
`_SILENCE_EXPERIMENTAL_COROUTINE_DEPRECATION_WARNINGS` because `local_auth_windows` fails on MSVC 14.51+ without it.

A Windows build without `OIDC_BASE_URL` (a bare `flutter build windows`) defaults to `https://stage.oidc.biatec.io`;
`./build-windows.ps1` passes the same URL explicitly via `--dart-define-from-file=config/local.json`. Put `nuget.exe` on `PATH` to silence the
`Nuget.exe not found` message from `local_auth_windows`.

### Platform hardening (T-227)

What the committed project files enforce, each with a test in `test/platform_hardening_test.dart` that fails on a regression:

| Setting | Android | iOS |
| --- | --- | --- |
| No backup or transfer | `allowBackup=false`, `fullBackupContent=false`, data extraction rules exclude every domain | app folders marked excluded from backup at launch; keychain items `_this_device` |
| No screenshots or recording | `FLAG_SECURE` set before the first view; recents screenshot off (Android 13+) | cover view when the app is inactive (so the app switcher shows no content) and while the screen is recorded or mirrored. iOS has no way to block a screenshot of the app in front, so a screenshot there is not prevented |
| Overlay and tapjacking | other apps' overlay windows hidden (Android 12+, `HIDE_OVERLAY_WINDOWS`); on Android 11 and older a touch through another app's overlay is dropped, which also disables a full-screen filter app's taps while it runs; on Android 10 and 11 a touch that was only partly covered is checked on the approve action alone (`lib/security/touch_guard.dart`) | - |
| No custom keyboard | - | `shouldAllowExtensionPointIdentifier` refuses keyboard extensions |
| Release build | not debuggable, R8 minify and shrink, every `android.util.Log` call removed (and none in the app's own Kotlin) | - |
| Privacy | cleartext off (pinned network config: T-229) | `PrivacyInfo.xcprivacy`: no tracking; push token declared |

CI builds the release APK with `--obfuscate --split-debug-info=build/symbols`, signed with a throwaway key that exists only for that job, runs the hardening test against the merged release manifest, and keeps the symbols of that build for 7 days as the `authenticator-debug-symbols` artifact. The repository and its artifacts are public, so the artifact is `symbols.tar.gz.gpg`, encrypted (OpenPGP, AES-256) with the `AUTHENTICATOR_SYMBOLS_PASSPHRASE` repository secret (decrypt with `gpg -d symbols.tar.gz.gpg | tar -xz`). Without that secret (a fork, or before it is set) no symbols are published. Those symbols fit only that CI build: a shipped release is built with its own `--obfuscate --split-debug-info=<dir>`, and that directory must be archived privately with the release to read its crash traces.

To check by hand on a device: open the app and try a screenshot (it must fail or show a black image), look at the recents list (blank), `adb backup -f x.ab io.biatec.authenticator` (must produce an empty archive), and `adb shell run-as io.biatec.authenticator ls` (must be refused on a release build).

Not verified on a device: none of this has been run on a phone; the Swift changes were written without Xcode.

### Backup and restore (T-226)

The Codes tab has a backup action (and the "fingerprints changed" screen a restore action). A backup is one file, `biatec-authenticator-backup-YYYYMMDD.biatecbackup`, offered through the system share sheet and read through the system file picker; nothing goes to a server. Both directions first ask for a fresh biometric.

File layout (`lib/totp/backup/backup_format.dart`): `"BTBK"`, version, KDF id, Argon2id memory (KiB), iterations, lanes, a 16-byte random salt, a 12-byte random nonce, then AES-256-GCM of the accounts as JSON padded to a multiple of 4 KiB (the size hides the account count). The header is the associated data, so any changed byte fails authentication. The key is Argon2id (RFC 9106, `pointycastle`) of the passphrase. The floor is 64 MiB, 3 passes, 4 lanes; a file made below it is refused as a downgrade, and one above the ceilings (256 MiB, 12 passes, 16 lanes) or the size and count limits (4 MiB, 1000 accounts) is refused without running the derivation. Every failure (wrong passphrase, damaged or foreign file) gives the same message, and a refused file still costs one derivation at the floor, so a quick refusal is not an oracle (a file that is accepted but fails authentication can take longer; the passphrase is the only secret, and this does not reveal it). Each account in a file goes through the same validation as a scanned QR code.

The passphrase needs at least 12 characters and an estimated 50 bits, is typed twice, and is never stored, logged or kept after use. It cannot be recovered: the screen says so. Restoring adds the accounts that are not already there (duplicates are counted and skipped) after showing them. After the phone's biometrics changed the old vault cannot be opened; restoring then replaces it with a new vault holding the file's accounts and returns to the lock screen. `test/codes/backup_screen_test.dart` also checks that only the vault and the backup code read a saved seed.

### Identity, motion and haptics (T-231)

The mark (a shield with a check, blue `#1B5E8C`) is drawn once as a vector in `lib/ui/brand_mark.dart` and once in `tool/make_brand_assets.py`, which writes the iOS icons (light, dark and tinted), the iOS launch image, the legacy Android launcher icons, and the Android vector drawables (adaptive icon with a monochrome layer, splash mark); run `python tool/make_brand_assets.py` after changing the mark (Pillow). Android 12 and newer use the system splash with the mark; older versions and iOS show the mark on the system background colour, light or dark.

`lib/ui/motion.dart` is the one answer to "may anything move": the system's reduce-motion setting (`disableAnimations`) turns off the page transitions and the gliding countdown ring. `Haptics` (`lib/ui/haptics.dart`) is the only code that calls the platform feedback (copy, approve, deny, error), and plays nothing under reduce-motion. The lock screen has no animation. Codes and the countdown use tabular figures. None of this has run on a device.

## Config

The Biatec OIDC base URL comes from `--dart-define=OIDC_BASE_URL=...` and defaults to the mock OIDC
(`http://10.0.2.2:5080/mock-oidc`, the host machine as seen from the Android emulator).

    flutter run --dart-define=OIDC_BASE_URL=https://oidc.example

The default does not match where the mock actually listens: `pnpm --filter mock-oidc start` serves
`http://127.0.0.1:8089` (`PORT`, `HOST` override it) with no `/mock-oidc` path. From the Android emulator pass
`--dart-define=OIDC_BASE_URL=http://10.0.2.2:8089` (with `adb reverse tcp:8089 tcp:8089` you can instead pass `http://127.0.0.1:8089` and keep the mock on loopback; `HOST=0.0.0.0` exposes it on every interface, and with `MOCK_TEST_HELPERS=1` anyone who reaches it can approve consent as a seeded user). An explicit URL that is not the
default counts as a real Biatec OIDC, so the settings screens are off unless `--dart-define=CONSENT_SETTINGS_API=true`
(see T-084 below).

**URL rules (BCHAT-029).** The URL must be `https`. Plain `http` is accepted only for the built-in mock URL (debug builds) and, in a debug build (not release, not profile), for `localhost`, `127.0.0.1`, `::1` and `10.0.2.2`; credentials, a query or a fragment in the URL are refused. A URL that breaks a rule stops the app at launch with a `ConfigException` that says which. Certificate pinning is not done.

## Enrollment and device key (T-051)

- `lib/keys/device_key_store.dart`: `DeviceKeyStore` is the two hardware keys (no export method, only signing; see "Two device keys" below).
  `PlatformDeviceKeyStore` calls the method channel `io.biatec.authenticator/keystore` (`generateKeys`, `load`, `keysState`, `signPresence`,
  `signApproval`, `deleteKeys`, `delete` for the single key of an old install; a key is `{x, y, securityLevel, authBound}`, P-256 base64url). The native side is in
  `android/app/src/main/kotlin/io/biatec/authenticator/KeystorePlugin.kt` (Android Keystore, StrongBox with fallback to the TEE; registered in
  `MainActivity.configureFlutterEngine`) and `ios/Runner/KeystorePlugin.swift` (Secure Enclave, `kSecAttrTokenIDSecureEnclave`; registered in
  `AppDelegate`).
- Key security level (BCHAT-032): `generate` and `load` also return `securityLevel`: `strongbox`, `tee`, `hardware` (Android below API 31, where the platform
  only says "inside secure hardware"), `secure_enclave` (iOS, read from the key's token attribute), `software` or `unknown`. The Android plugin deletes a key that
  ended up in software and answers `insecure_key`; `EnrollmentController.enroll` refuses `software` and `unknown` too (fail closed, also for an older plugin that
  says nothing), and the enrollment screen shows "Key protection: ...". The Kotlin side is compiled, the Swift side is not.
- `lib/enrollment/`: `EnrollmentController` state machine (`notEnrolled`, `generatingKey`, `enrolling`, `inactive`,
  `activeRecoveryPending`, `active`, `failed`), `OidcEnrollmentClient` (`POST /devices`), secure-storage record, and
  the enrollment and recovery-code screen. The platform attestation (Play Integrity, App Attest, T-234) is sent when the platform can make one.
- The mock `POST /devices` takes a `login-*` bearer token (`login-alice` is prefilled against the mock) and
  returns `active_at` in epoch seconds. The kids are derived from the keys (`biatec-approve-<32 characters of the RFC 7638 thumbprint>` and
  `biatec-presence-<...>`), so they are unique per key, stable and need no storage; the keystore aliases are fixed. The server rejects a kid it has already seen.
- Recovery code (rule 7): never part of the enrollment response and never stored on the device. Once the device is
  active the app calls `POST /devices/recovery-code` (`Authorization: Device <token>`, refused with 403 while
  inactive), holds the code in memory while it is shown, and confirms with `POST /devices/recovery-code/ack`. These
  two calls are a fallback implemented in the mock; the needed change is in
  `docs/required-changes-biatec-oidc.md` section 4.
- Known gap: the Kotlin plugin has been compiled (Android debug and release builds) but, like the Swift one, NOT run
  on a device or emulator. "Key is non-exportable on device" and the emulator enrollment run are therefore
  unverified and the task is partial until someone runs them (the iOS simulator has no Secure Enclave; use a device).
- Contract test against the real mock: start `MOCK_TEST_HELPERS=1 pnpm --filter mock-oidc start` (the `/mock/*` helpers and the seeded device tokens exist only with that flag), then
  `flutter test --dart-define=MOCK_OIDC_URL=http://127.0.0.1:8089 test/enrollment/mock_oidc_contract_test.dart`
  (skipped otherwise).

## In-app login and activation of a new device (T-242, audit finding BCHAT-033)

A device is enrolled only by a person who just logged in inside the app, and becomes active at once only when an existing device's user confirmed the same pairing code on both phones, or a recovery code was entered.

- **Login** (`lib/enrollment/auth_client.dart`): `flutter_appauth`, authorization code with PKCE in the system browser (Custom Tabs on Android, `ASWebAuthenticationSession` on iOS, never an embedded web view; the iOS session is ephemeral). Client `--dart-define=OIDC_CLIENT_ID=...` (default `biatec-authenticator`), scope `openid enroll-device`, `prompt=login`, `max_age=0`, no refresh token. The access token is held in a local variable for `POST /devices/challenge` and `POST /devices` and then dropped: nothing from the login is stored (`test/enrollment/in_app_login_test.dart` checks that no value written to the secure storage holds it). Biatec OIDC enforces `auth_time` as well: `401 insufficient_user_authentication` with `max_age` restarts the login once ("Sign in again").
- **Redirect:** a release build returns through an app link (`https://oidc.biatec.io/app/authenticator/callback`, or `--dart-define=OIDC_REDIRECT_URI=https://...`; a custom scheme is refused in a release build); a debug build uses `io.biatec.authenticator:/oauth2redirect`, which only the debug Android manifest declares. The app links need `assetlinks.json` and `apple-app-site-association` on Biatec OIDC's hosts (`docs/required-changes-biatec-oidc.md`, section 26); until they exist a release build cannot finish the login.
- **Minimum iOS for the release redirect:** the https callback of `ASWebAuthenticationSession` (the release redirect, an app link) needs **iOS 17.4 or later**. The project's deployment target is 15.0 (`ios/Podfile`, `IPHONEOS_DEPLOYMENT_TARGET`), so it does NOT already satisfy that. Chosen fallback: no custom scheme in a release build (any app can register one, and PKCE alone is then all that protects the code); `AppAuthClient` instead refuses to start the login on an iOS older than 17.4 with "Signing in from this app needs iOS 17.4 or later" (`httpsCallbackSupported`, tested), so the phone is not left hanging in the browser; such a phone is enrolled with a recovery code from another device or after updating. The debug custom scheme (`io.biatec.authenticator:/oauth2redirect`) works on every iOS version, since `ASWebAuthenticationSession` takes a custom scheme callback without any Info.plist entry. Raising the deployment target to 17.4 is the alternative if older phones are not needed. Android has no such minimum.
- **Release redirect host:** `https://<host of OIDC_BASE_URL>/app/authenticator/callback`; only `oidc.biatec.io` and `stage.oidc.biatec.io` (the hosts in the manifest and the entitlements) are valid, any other host with the in-app login on in a release build stops the app at launch with a `ConfigException`.
- **Switch:** `--dart-define=IN_APP_LOGIN=true|false`, on for the mock and off for any other URL, like `TWO_KEY_DEVICE` and `DEVICE_CHANNEL`. Off: no sign-in button, no activation, the enrollment is what it was. Activation by another device needs `TWO_KEY_DEVICE` too (`AppConfig.activationByDevice`).
- **The paste field** for a login token exists only in a debug build (`AppConfig.pasteLoginToken` is `!release && (isMock || !inAppLogin)`, and `release` is `!kDebugMode`, so a release build has no such field; `test/enrollment/pairing_and_flags_test.dart` checks the flag and the screen). A release build against a Biatec OIDC without the login therefore says "Sign-in is not available yet" and enrolls nothing.
- **A device cancelled elsewhere** (the email link, another phone): a `401`, `403` or `404` on the waiting device's poll or on its own cancel, or its absence from `GET /devices`, removes its record and keys, signs it out and shows "This device was cancelled".
- **A new device waits** (`lib/enrollment/enrollment_screen.dart`): it shows the six digit pairing code (`lib/enrollment/pairing_code.dart`, spec 8.3, worked example in `test/enrollment/pairing_and_flags_test.dart`), computed from its OWN two keys and the enrollment nonce; says it becomes active after 24 hours if nobody activates it and that an email with a cancel link was sent; asks `GET /devices` every 5 seconds while the screen is open; and has "Cancel this device" (`POST /devices/{kid}/cancel`, then the keys and record go).
- **An active device activates** (`lib/devices/devices_screen.dart`, `SettingsController.activateDevice`): the Devices screen shows "Activate <name>?" with the pairing code the app works out from the thumbprints and nonce `GET /devices` lists (refused, and not offered, when the server's own code differs). The user compares the two phones and confirms; the approval key signs `biatec_device_approval` (one biometric prompt, `signApproval`) and the app calls `POST /devices/{new_kid}/activate`. The `device_enrolled` event of the device channel refreshes the list. Mismatch or doubt: "Cancel this device".
- **Recovery code:** a field on the sign-in step, checked locally (`XXXX-XXXX-XXXX`, spaces and dashes forgiven) before the browser opens, so a typo costs nothing; a code Biatec OIDC refuses means signing in again (the login is `max_age=0` and its token was dropped after the one enrollment attempt), and wrong codes count toward the lockout; the code goes in `POST /devices` as `activation: { kind: "recovery_code", code }`. A wrong code and the lockout (`429`) have their own texts.
- **Strings:** English and Slovak, by the phone's language (`lib/enrollment/enrollment_strings.dart`; the test checks both have every key).
- **Android:** `AndroidManifest.xml` declares AppAuth's `RedirectUriReceiverActivity` (exported, because the browser starts it) with verified https filters only; the debug manifest adds the custom scheme; `test/platform_hardening_test.dart` checks both and that the merged release manifest has no custom scheme. **iOS:** the `applinks:` domains are in `Runner-AppLinks.entitlements`, which only the Release and Profile configurations use (`CODE_SIGN_ENTITLEMENTS` in the project); Debug keeps `Runner.entitlements`, because code signing a debug build fails without the Associated Domains capability. `Runner-APNs.entitlements` (the optional Apple wake build) includes the domains too. The Info.plist needs no URL scheme.

### Manual checklist for two phones (NOT run: no phone was available when this was written; the browser, the app link return and the native keystore have never run on a device)

Two phones with a fingerprint or face enrolled, the mock reachable from both (`HOST=0.0.0.0` on a network you trust, `MOCK_TWO_KEYS=1`; the first phone is called A, the second B; use `--dart-define=OIDC_BASE_URL=http://<host>:8089` on both, which makes them mock builds only if the URL is the default, so for this check run them as debug builds against the mock URL with the test helpers off):

1. A, first device: open the app, "Get started", "Sign in with Biatec". The system browser opens (not an embedded view), A returns to the app by itself. The step says the device is inactive for 24 hours, shows a pairing code, says an email with a cancel link was sent, and offers "Cancel this device". (With the mock, skip the 24 hours with `POST /mock/devices/<kid>/activate`, which needs `MOCK_TEST_HELPERS=1`.) A shows the recovery code once: save it.
2. B, a second device of the same account: sign in again (the browser asks for the credentials even though it has a session: `prompt=login`). B shows a six digit pairing code.
3. A: open Devices. A card "Activate <name>?" shows a code; it is the same six digits as on B. Tap "Activate", then "The codes match": the OS asks for the fingerprint once. B turns active within about 5 seconds and shows its own recovery code step.
4. B again, from the start (erase it in Privacy and erase first): sign in, and on A compare. This time doubt the code and tap "Cancel this device" on B (or "Cancel this device" on the card on A): B goes back to the start and A's list no longer has it.
5. Recovery code: erase B, sign in again, enter A's recovery code in the field before signing in: B is active at once with no waiting. Repeat with a wrong code: "Recovery code not accepted"; after five wrong codes: "Too many attempts".
6. Stale login: leave the browser login open for more than five minutes before finishing (or use `login-alice-stale` through a debug build): the app says "Sign in again" and restarts the login once.
7. Cancel the browser (close the Custom Tab): "Sign-in was cancelled. Nothing was enrolled."
8. Release build against a real URL with `IN_APP_LOGIN=true`, after the app links are hosted: the browser returns through the https link. Without the hosting it stays in the browser (expected: the prerequisite in `docs/required-changes-biatec-oidc.md`).

## Approvals and receipts (T-052)

- `lib/approvals/`: `ApprovalClient` (`GET /devices/requests`, `GET /consent/requests/{id}`,
  `POST /consent/requests/{id}/receipt`, all `Authorization: Device <token>`), `ApprovalController` (one request),
  the card, the pending list (polls every 5 s, and refreshes at once on a push) and the local history (secure storage, last
  100 decisions with their full receipts).
- The card is rendered only from the fetched consent request. The receipt signs `authorization_details` exactly as
  fetched, canonicalized with `jcs.dart` (RFC 8785, checked against `packages/consent-protocol/vectors`), with ES256
  by the device key, and carries the enrollment attestation (now kept in the enrollment record; a record saved before
  this change has none and must re-enroll).
- Approve: six-digit binding code, then a fresh fetch of the request. If that fetch fails the device is offline and
  nothing is signed; if the request differs from the card, the new one is shown and nothing is signed. Then the approval key signs, and the
  operating system's own biometric prompt (one operation with the signature, see "Two device keys") is the only check: there is no separate Dart
  biometric gate for it. A dismissed prompt leaves the request pending and uses no code attempt. Biatec OIDC counts the three attempts; after the third wrong
  code the app signs (presence key) and posts a `code_failed` receipt.
- Deny is signed too (presence key, no prompt), needs no code, and signs the last typed code or the empty string.
- Unverified clients: warning banner with fingerprint only; their `binding_message` is never rendered or signed.
- `local_auth` is not used anywhere (T-222; `test/lock/biometric_policy_test.dart` checks it). The Android approval prompt (`BiometricPrompt`) needs
  `FlutterFragmentActivity` as `MainActivity` (it is) and the iOS prompt needs `NSFaceIDUsageDescription` in `Info.plist` (it is there).
- Contract test against the real mock (it verifies signature and attestation with its JWKS): start the mock, then
  `flutter test --dart-define=MOCK_OIDC_URL=http://127.0.0.1:8089 test/approvals/mock_oidc_approval_contract_test.dart`.
  On Node older than 22.18 start it with `node --experimental-strip-types src/server.ts`.

## Two device keys (T-241, audit finding BCHAT-007)

Protocol 1.1 splits the device key in two. Both are P-256, generated in hardware, never exportable, and each has its own `kid` and its own attestation
(`biatec_key_use` is `approve` or `presence`).

| | Approval key | Presence key |
| --- | --- | --- |
| Signs | `approve` receipts, `biatec_settings_change`, `biatec_device_approval` (T-242), the approval half of the enrollment proof | device proofs (`X-Device-Proof`, every HTTP call), `deny` and `code_failed` receipts, the presence half of the enrollment proof |
| Prompt | the OS asks for a strong biometric for EVERY signature | none |
| Android | `setUserAuthenticationRequired(true)`, `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)` (per use, no PIN), `setInvalidatedByBiometricEnrollment(true)`, `setUnlockedDeviceRequired(true)`, StrongBox when present. Signing is `BiometricPrompt` with a `CryptoObject` that wraps the `Signature`: the prompt and the signature are one operation | `setUnlockedDeviceRequired(true)`, no user authentication |
| iOS | Secure Enclave, access control `.privateKeyUsage` + `.biometryCurrentSet` (`kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`), signed with an `LAContext` (fixed prompt text, no passcode fallback button) | Secure Enclave, `.privateKeyUsage`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` |

- Channel API (`lib/keys/device_key_store.dart`): `generateKeys()`, `signPresence(bytes)`, `signApproval(bytes, promptTitle, promptSubtitle)` (the only call that
  prompts; throws `KeyPromptCancelled`, `ApprovalKeyInvalidated` or `KeyPromptFailed`), `keysState()` (`ok`, `approvalKeyInvalidated`, `missing`, no prompt).
  There is no fallback to a software key or to the device credential for the approval key.
- After the approval key is created the plugin reads `KeyInfo` back (hardware, user authentication required, per use, invalidated by biometric enrollment) and
  refuses to enroll otherwise ("This phone cannot protect approvals"); the Dart side refuses it too (`DeviceKey.authBound`). A phone with no enrolled strong
  biometric cannot make the key: the app says to set one up first.
- Enrollment (`lib/enrollment/enrollment_proof.dart`) asks for the server's nonce (`POST /devices/challenge`; no nonce, no enrollment), signs the enrollment proof with the
  approval key (this is the one biometric prompt of an enrollment) and a `presence_proof` over the same payload with the presence key, and sends
  `presence_kid`, `presence_public_key`, `approval_proof` and `presence_proof` in `POST /devices`. The record keeps both attestations.
- Approvals: the prompt title is fixed ("Approve this action"); the subtitle names the client and the total from the request that was just fetched.
- Invalidation: adding or removing a fingerprint or face invalidates the approval key (`KeyPermanentlyInvalidatedException`, or the iOS key disappearing). The state becomes
  `approvalKeyInvalidated`: Approve and signed settings changes are off with an explanation, Deny still works (presence key), and "Enroll this device again"
  clears this install's enrollment and keys so the enrollment flow starts. Biatec OIDC keeps the old device record until it is cancelled from the account.
- An install from before the two keys (a record without `presence_kid`) is treated as having no keys: it is shown the enrollment flow with a notice, and its old key is deleted when
  the new enrollment starts. No silent migration.
- `keysState` on Android is cached for 5 minutes: probing the approval key with `initSign` leaves a keymaster operation open, so the probe runs at most once per 5 minutes, `signApproval`'s own `initSign` (the only long-lived operation) updates the cache, and the approval card reads the state once when it loads. In single-key mode (`AppConfig.twoKeys` off) the one key is made without `setUnlockedDeviceRequired`, so it works while the phone is locked as before.
- Known trade-off: the presence key needs an unlocked phone (`setUnlockedDeviceRequired`), so while the phone is locked the foreground service cannot sign the ticket request
  of a new device channel connection. A connection that was made while unlocked is not affected, and a reconnect waits until the phone is unlocked.
- Tests: `test/keys/device_key_store_test.dart` (channel), `test/approvals/approval_test.dart` group "two keys" (a fake keystore: approve signs with the approval
  key exactly once and nothing else prompts; deny, `code_failed` and proofs use the presence key; a cancelled prompt leaves the request pending and uses no attempt; an invalidated
  key turns Approve off and keeps Deny), `test/settings/settings_controller_test.dart`, and the contract tests against the mock with `MOCK_TWO_KEYS=1`
  (the mock verifies receipts, attestations, enrollment proofs and device proofs with `packages/consent-protocol/scripts/lib.mjs`; it refuses an approve signed by the presence key and a proof signed by the approval key).
- Android instrumented test: `android/app/src/androidTest/kotlin/io/biatec/authenticator/ApprovalKeyInstrumentedTest.kt` (`cd android && ./gradlew :app:connectedDebugAndroidTest`, needs
  a phone or emulator with a fingerprint enrolled). It checks `authBound`, hardware backing, that the approval key cannot sign outside a `BiometricPrompt`
  (`UserNotAuthenticatedException`) and that the presence key signs without a prompt. NOT run yet.

### Certificate pinning (T-229)

Every call to Biatec OIDC goes through `PinnedHttp` (`lib/security/pinning/`): the leaf certificate's public key must be one of the host's pins (`pins.dart`, a backup key is mandatory); the system's list of trusted certificate authorities is not used; there is no revocation check, so a compromised key is replaced by an app update.

## Device channel and notifications (T-244)

There is no Firebase and no Google push code in this app (changelog: T-244 removed `firebase_core`, `firebase_messaging` and the FCM transport). The app learns about
a request at once while it is connected, over a SignalR hub hosted inside Biatec OIDC. Nothing we host can wake an app that is not running; that limit is stated
here instead of being hidden.

### What the code is

- `lib/channel/device_channel.dart` (`DeviceChannel`, a `DeviceEventSource`): a minimal SignalR JSON hub-protocol client over `web_socket_channel`, server to
  client only, no SignalR package. For every connection it fetches a fresh single-use ticket with `POST /devices/hub-ticket` (signed with the device token and the
  device proof, like every device call), connects `wss://<oidc>/hubs/device?access_token=<ticket>` through the pinned TLS client (`PinnedHttp.webSocketClient`),
  sends the handshake, and handles invocations (type 1), pings (type 6, answered and sent every 15 s) and close (type 7: reconnect unless `allowReconnect` is
  `false`). Unknown message types and targets are ignored and an invocation is never sent. It reconnects after 1, 2, 5, 10, then 30 seconds plus up to 20 percent
  jitter, starting again at 1 second after a connection that lived 60 seconds, makes no attempt while there is no network or the device is not enrolled, and never
  logs the URL (it holds the ticket).
- `lib/push/device_event.dart`, `device_event_controller.dart` (`DeviceEventController`): the four events (`consent_request`, `consent_closed`, `device_enrolled`,
  `settings_changed`) carry ids only, validated by charset and length before use. A request refreshes the pending list and, when the app is not in front, fetches
  the pending requests and shows a local notification with fixed text ("Approval requested" / "Open Biatec Authenticator to review"; nothing from the payload is
  in it). A closed request drops its card and notification, an enrolled device refreshes the device list and notifies (fixed text), changed settings reload. The
  Approvals screen still polls every 5 seconds while it is open, and the list is fetched on resume, so a missed event only delays a request.
- The app keeps its channel open while it is in front and closes it when it goes to the background. Texts are in `lib/settings/channel_strings.dart`
  (English and Slovak, chosen by the phone's language).

### What wakes the phone, and what does not

| Situation | A new request is seen |
| --- | --- |
| App open | At once (the channel), and the list polls every 5 seconds as well |
| Android, app in the background or closed, "Stay connected for approvals" **on** | At once: the foreground service keeps the process and the channel alive, and a notification is shown |
| Android, app in the background or closed, setting **off** (the default) | Not until the app is opened: nothing can wake it |
| Android, after a reboot, setting on | The service is restarted after boot (and after an app update) only when the setting is on and the device is enrolled |
| iPhone, app in front | At once (the channel) |
| iPhone, app in the background or closed | Not until the app is opened, unless the optional Apple wake is built in (below) |
| Any phone, no network | When the network returns and the app is open or connected; the channel makes no attempts without a network |

A swiped-away app, "force stop", aggressive battery managers of some phone makers and a device that is switched off all stop the channel. The service's
battery cost is why the setting is off by default and says so.

### Stay connected on Android

- Settings, group Notifications: **Stay connected for approvals** (Android only, default off, English and Slovak). It says what happens when it is off ("you will see
  requests when you open the app") and that it keeps the app running with a permanent notification, which uses battery. Turning it on asks for the notification
  permission (Android 13+), saves the choice, and starts `StayConnectedService`; the choice and whether the service should run are kept in the app's private
  `SharedPreferences` (`StayConnectedPrefs`) because the boot receiver needs them without Dart. The battery optimisation exemption is offered once, after the first
  time it is turned on, through the system's battery optimisation list (`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`, no special permission).
- `StayConnectedService` is a small Kotlin service rather than `flutter_foreground_task`: it has to host the channel in its own headless Flutter engine and register
  `KeystorePlugin` on that engine, so that the ticket request is signed with the device key exactly as in the app (the device proof is not skipped or weakened; without
  the keystore plugin nothing would connect). Its Dart entry point is `stayConnectedMain` in `lib/channel/background_main.dart`; it uses the same pinned client, secure
  storage and `KeystoreDeviceProofSigner`. A request that arrives while the window is in front is left to the app (`UiState`).
- The service is not exported, runs with `android:foregroundServiceType="specialUse"` and a `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`; `BootReceiver` (not exported) restarts it after
  `BOOT_COMPLETED` or `MY_PACKAGE_REPLACED` only when the setting is on and the device is enrolled. It is stopped when the setting is turned off or the device is unenrolled
  (the app watches the enrollment; the service also stops itself when it finds none).
- **Play Console declaration.** `specialUse` is the type Android's documentation prescribes for a long-running foreground service that fits none of the other types
  (there is no "remote notification channel" type; `dataSync` is for transfers and is time-limited on Android 15). The permission `FOREGROUND_SERVICE_SPECIAL_USE` requires, in
  Play Console under App content, "Foreground service permissions": choose **Special use**, describe the use as in the manifest property (keeps a connection to the user's
  Biatec OIDC server so that a request to approve a high-value action reaches the phone at once, turned on by the user in Settings), explain that there is no alternative
  that wakes an app without a third-party push service, and attach a short video that shows the setting being turned on and the permanent notification. Without the declaration Play will not
  accept a release that has the permission. (This was written from memory of the current Android and Play documentation and was not checked against the live pages: check them
  before the first release.)

### The optional Apple wake (iOS)

Off by default. With `--dart-define=APNS_ENABLED=true` the app asks for notification permission, registers for remote notifications through `ApplePushChannel.swift`
(a small Swift method channel; the token as hex) and calls `PUT /devices/push` with `{ "provider": "apns", "token": ... }`; Biatec OIDC may then wake the app with a push that
carries no content. With the flag off nothing runs: the Dart code never calls the channel, and the committed project has no push entitlement or `UIBackgroundModes`. For a build
with the flag, set `CODE_SIGN_ENTITLEMENTS` to `ios/Runner/Runner-APNs.entitlements` (it adds `aps-environment`), enable the Push Notifications capability on the App ID, and add
`UIBackgroundModes` `remote-notification` to `Info.plist` for that build. The server side (APNs key, `provider: apns`) is Biatec OIDC's, not this repository's.

## Biometric lock (T-222)

- `lib/lock/lock_controller.dart`: `LockController` (locked, unlocking, unlocked, noBiometric, biometricsChanged, compromised). The only way to
  `unlocked` is `unlock()` with a `BiometricOutcome.success`; there is no PIN, no fallback and no debug switch. A process start is a locked state.
- `lib/shell/app_lock_gate.dart`: builds the shell only while unlocked, so while locked the widget tree holds a lock screen and no secure-area
  screen. It reports the app lifecycle and every touch to the controller. The enrollment screens are the first-run explanation, not the secure area.
- Strong biometric only: `lib/security/biometric_policy.dart` over the channel `io.biatec.authenticator/biometric`. Android
  (`BiometricChannel.kt`): `BiometricPrompt` with `BIOMETRIC_STRONG` and no `DEVICE_CREDENTIAL`; iOS (`BiometricChannel.swift`): the policy
  `deviceOwnerAuthenticationWithBiometrics` with the fallback button hidden. `local_auth` is not used (on Android its biometric-only mode also accepts
  weak biometrics). `test/lock/biometric_policy_test.dart` greps that no weaker policy appears.
- When it locks: at start, after the background delay (immediately, 30 seconds, 1 minute or 5 minutes; default 30 seconds; no "never"; stored
  locally; changed in Settings after a fresh biometric), when the screen locks (native event), and after 2 minutes without a touch. Locking runs the
  `addLockListener` hooks so decrypted seeds and codes leave memory (T-224 registers its own).
- A fresh biometric for each action goes through `LockBiometricGate` (approvals) and `SettingsController.apply` (every security setting, tightening
  too). The biometric requirement is no longer a switch in Settings.
- A tapped notification while locked is queued by id in `ShellController` (memory only); the card opens after the unlock.
- `markBiometricsChanged()` (for the vault and key code to call when a key is invalidated, T-223) and `markCompromised()` (T-228) put the app on a
  screen that says what happened; nothing opens from there.
- Not run on a device: the Kotlin and Swift code (CI builds Android).

## Codes tab (T-224)

- `lib/codes/codes_screen.dart` is the first tab: the list (issuer, account name, the code in groups of three, a countdown ring with the seconds in text, the next code in the last 5 seconds, tap to copy, a button for counter-based accounts), search, reorder (drag handle, or Move up and Move down in the menu), rename, delete (a confirmation, then a fresh biometric), and an optional "hide codes until tapped" mode kept on this phone.
- `CodesController` reads the vault (`lib/totp/vault`) when the tab opens and holds the secrets in memory only while the screen exists. The screen exists only while the app is unlocked, and the controller also wipes on the lock listener. One `CodeTicker` drives every countdown; it ticks on the whole second of the clock, and runs only while the tab shows, the app is in front and the list is loaded.
- Adding (`lib/codes/add/`): QR scanner (`mobile_scanner`; the camera permission is asked when the scanner screen opens, no picture is kept), a pasted `otpauth://` link, or a typed Base32 key. All three end in the same `OtpAccount`; an entry that is refused shows the engine's own message; the account is shown before it is saved; a copy of an account in the list is refused.
- Copy goes through `io.biatec.authenticator/clipboard` (`ClipboardChannel.kt`: `EXTRA_IS_SENSITIVE`; `ClipboardChannel.swift`: local only, expiring) and is cleared after 30 seconds only if the clipboard still holds that code.
- Clock: `ServerClock` reads the `Date` header of the calls to Biatec OIDC (the pinned client reports to it) and the tab warns above 5 seconds. A time earlier than the latest time shown (`OtpGenerator.clockIsPlausible`) hides time-based codes; a saved time more than 30 days ahead of the clock is forgotten, so a corrected clock is trusted again.
- Vault key window: the vault's secret key accepts a strong biometric for 30 seconds (Android `setUserAuthenticationParameters`, iOS `touchIDAuthenticationAllowableReuseDuration`), so the unlock that opened the app also opens every secret instead of one prompt per account. After the window each secret read prompts again.
- Not run on a device: the scanner, the clipboard channels and the vault window (Kotlin, Swift).

## Device integrity (T-228)

- `lib/integrity/`: `IntegrityDetector`s that are pure functions of an `IntegrityEnvironment` (files, writable folders, `/proc`, properties, debugger, loaded classes and libraries, signing certificate), so each is tested against a fake phone in `test/integrity/`. Android: root (su and manager files, open system folders, test-keys, debuggable or insecure builds), debugger and tracer, hooking (Frida, Substrate, Xposed), emulator, signing certificate. iOS: jailbreak files and an open sandbox, debugger (`P_TRACED`), injected libraries, simulator.
- `IntegrityGuard` keeps the answer for 30 seconds; the lock asks again (forced) on resume and before every approval (`reauthenticate`). A detector or checker that fails counts as a hit.
- Policy in `LockController`: `failClosed` (default true; `main.dart` passes `kReleaseMode`). Closed: the phone never gets the fingerprint prompt, the memory is cleared, and `CompromisedScreen` shows. That screen says that a safety check was not passed and names no detector or group; "Check again" runs the check anew and the normal unlock follows if it passes. Open (debug builds): the app opens with a warning on the lock screen.
- Release signing digest: `--dart-define=RELEASE_CERT_SHA256=<sha-256 of the release certificate>`. On Android a release build without it is not trusted (an unconfigured digest is a compromised result), so set it in the release build step.
- Attestation hook: `AttestationProvider` over `io.biatec.authenticator/attestation` (see "Platform attestation" below).
- Not run on a device: the Kotlin and Swift fact readers and App Attest.

## Platform attestation at enrollment (T-234)

- `EnrollmentController` asks the platform whether it can attest (`AttestationProvider.supported`), gets a single-use nonce from Biatec OIDC (`POST /devices/challenge` with the login), asks the platform for a token bound to it, and sends `attestation_challenge` and `platform_attestation` with `POST /devices`. If the platform cannot attest, gives no token, Biatec OIDC offers no challenge or anything throws, the enrollment goes **without** one: nothing is made up.
- iOS: App Attest (`IntegrityChannel.swift`, entitlement in `Runner.entitlements`; the App Attest capability must be on the App ID). Android: Play Integrity (`AttestationChannel.kt`, `com.google.android.play:integrity`), which needs the release's Google Cloud project number: `-PplayIntegrityProject=<number>` or `gradle.properties`; without it Android is not supported and enrolls without an attestation.
- When Biatec OIDC returns `attestation_refresh_after`, the record keeps it and the next refresh after that date sends a fresh attestation (`PUT /devices/attestation`), quietly. The API shape and the fallback are row 25 of `docs/required-changes-biatec-oidc.md`; the mock implements it.
- Not run on a device: both platform implementations, and the real token verification (Biatec OIDC's side).

## Link a service and approve its payments, logins and actions (T-247, protocol 1.2)

With this a bank's customer adds the bank to Biatec Authenticator and confirms the bank's payments and logins on the phone. Protocol: `packages/consent-protocol/spec/biatec-consent-protocol.md`, chapters 3.3 to 3.6, 8.4, 8.5, 14 and 15 (T-246).

**Configuration (a repository rule).** Real Biatec OIDC has no relying-party protocol yet (`docs/required-changes-biatec-oidc.md`), so everything here is **off** against a real URL: `AppConfig.relyingParties` is on for the mock only until `--dart-define=RELYING_PARTIES=true` says otherwise, and it counts only together with `TWO_KEY_DEVICE` (an approval is signed by the approval key) and `TRUST_SETTINGS` (Linked services is one of those screens): `AppConfig.relyingPartiesEnabled`. Off: no "Link a service", a `biatec-authenticator://link` link is dropped with a neutral message (no screen, no call), and a payment, login or action request is shown as "This request cannot be shown; update the app" and cannot be approved or denied.

- **Link entry** (`lib/links/`): Settings, Linked services, "Link a service" opens the scanner (`mobile_scanner`, the same camera view as the Codes tab), with "Paste a link code" for a phone without a camera. A link code is parsed strictly (`link_code.dart`): the scheme `biatec-authenticator`, the host `link`, exactly the parameters `iss`, `id` and `s` once each, no path, port, user name or fragment, and the shape of each value. `iss` must be the origin of the Biatec OIDC this app is enrolled with, exactly (`originOf(OIDC_BASE_URL)`); another one is "This code is for a different authenticator service" and **nothing is sent anywhere**, so the link secret never leaves the phone for another server. Against the mock, or any plain `http` server (only a debug build accepts one, for the developer's own machine), the mock's fixed issuer `https://oidc.biatec.test` is accepted as well, because the mock is not served from that name; a build against an `https` server has no such exception.
- **Deep link.** The Android intent filter (exactly one VIEW filter on `MainActivity`, which was exported already) and the iOS URL scheme (the only one) let another app, for example the camera app that read the QR code, open the app with the link code. It is only text: it waits in `LinkIntake` until the signed-in app can show the link screen, is parsed exactly like a scanned code, and never links anything without that screen. `test/platform_hardening_test.dart` checks both native declarations. A custom scheme cannot be verified like an app link, so another app could register it too; that only lets it receive a link code the user meant for this app. The link secret in the code is short-lived (5 minutes) and single use, and the code is useless without the six digits the service shows beside its QR code and the user's biometric. With linking switched off (see the configuration above) a link is dropped with the neutral message "This build cannot link services."
- **Link screen** (`link_screen.dart`, `link_controller.dart`): `GET /consent/links/{id}` with `X-Link-Secret`; the service-identity widget (proven domain, or "Unproven application" and the fingerprint), "The service calls you: (label)" in the area headed "Written by the service", what linking means, the countdown and the six-digit code the user types (never submitted by itself). **Link** signs `biatec_link` with the **approval key** (one biometric prompt); **Don't link** signs a deny with the **presence key** (no prompt). A service without a proven domain needs a second confirmation ("This service has not proven who it is"). A wrong code shows the server's remaining attempts; the third closes the link; a link that is gone, expired or used is one neutral message.
- **Cards** (`lib/approvals/cards/`): `biatec_payment` (amount and currency in the largest type; the payee, the account, an IBAN in groups of four or another identifier with its scheme, and the reference, in the bordered area "Written by the service"; the execution date), `biatec_login` ("Sign in to" the domain or the fingerprint, the context under "Reported by the service" in a quieter style) and `biatec_action` (the title and the labelled lines inside "Written by the service"). Every card shows the service identity and the origin when there is one; the approval screen adds the countdown and the code field. An unknown type, a schema failure or a text-rule violation is "This request cannot be shown; update the app", not approvable and not deniable (no valid receipt exists for it); it is kept out of the badge and can be dismissed locally (hidden until the app restarts or it expires, nothing is sent). In the pending list and in the prompt of the operating system, text a service wrote never appears in the app's own style: the list quotes it in a quiet line "From <service>:", and the prompt shows only the service identity, and for a payment the amount and currency.
- **Display safety** (`lib/links/text_rules.dart`): a Dart port of the relying-party text profile (spec chapter 15), tested against `vectors/text-rules.json`. A violation is refused, never stripped. Dart has no Unicode normaliser, so NFC is approximated by refusing a combining mark after a Latin, Greek or Cyrillic letter; the server and every verifier check NFC itself. Text is drawn as plain text, never as markup or a link.
- **What is signed.** The app computes `details_hash` itself (`computeDetailsHash`: RFC 8785 with `jcs.dart`, SHA-256, base64url) from the object it renders and refuses a request whose own `bound_hash` differs. The receipt is version `"1.2"`: the eight members of 1.1 without `remember` plus `details_hash`, an empty `binding_message`, `device.key_use`. The device block carries the device's own attestation as for every receipt (the spec binds nothing for a 1.2 receipt; the mock replaces it with one minted for the pairwise subject when it stores the receipt). History keeps links and the new request types (type, service, amount for a payment, decision, time), never the code.

### Manual checklist on a real phone (NOT run: no phone was available when this was written; the camera scan, the deep link from another app and the biometric prompt have never run on a device)

Needs an Android phone (USB debugging) with a debug build against the mock, enrolled with it, and a computer with Node 20 or newer. A custom `OIDC_BASE_URL` counts as a real Biatec OIDC, so switch the features on: `adb reverse tcp:8089 tcp:8089`, then `flutter run --dart-define=OIDC_BASE_URL=http://127.0.0.1:8089 --dart-define=CONSENT_SETTINGS_API=true --dart-define=TWO_KEY_DEVICE=true --dart-define=TRUST_SETTINGS=true --dart-define=RELYING_PARTIES=true --dart-define=IN_APP_LOGIN=true` (see "Config" and "In-app login"). Run the mock WITHOUT `MOCK_TEST_HELPERS`, so the demo waits for the real phone instead of scripting one (and nobody who reaches the mock can approve as a seeded user).

1. On the computer, from `packages/consent-protocol/mock-oidc`: `MOCK_TWO_KEYS=1 node src/server.ts` (port 8089, loopback; the phone reaches it through `adb reverse`).
2. From `packages/consent-protocol`: `node scripts/rp-demo.mjs --server http://127.0.0.1:8089 --manual`. It registers a relying party, prints the QR payload (`biatec-authenticator://link?iss=https%3A%2F%2Foidc.biatec.test&id=...&s=...`) and a six-digit code, and waits.
3. **Scan.** Turn the QR payload into a QR code (any generator) and, in the app, Settings, Linked services, "Link a service": scan it. The link screen shows "Unproven application" and a fingerprint (the demo published no well-known file), the text "The service calls you: Demo User (account ending 4421)" in the area "Written by the service", and what linking means. Also try "Paste a link code" with the payload and, with the app closed, open the payload from outside the app (`adb shell am start -a android.intent.action.VIEW -d '<payload>'`): the link screen must appear, and nothing may happen until you act.
4. **Link.** Type the six-digit code and press Link: because the domain is not proven a second confirmation appears ("This service has not proven who it is"); confirm. One fingerprint or face prompt. The demo prints that it linked, verified your signed statement and pinned two keys; the service is now in Linked services.
5. **Approve a payment.** The demo then sends a 12.50 EUR payment and prints the code to show inside the bank's own session. In Approvals, open it: the amount in the largest type, the payee, the IBAN in groups of four and the reference under "Written by the service", the origin, the countdown. Type the code, Approve, one prompt. The demo prints `verifyReceiptPinned: true` and "approved by the user".

Press Deny: no prompt, and the demo reports a `deny` and executes nothing.
7. **Refusals.** A code from a different server (change `iss`) is "This code is for a different authenticator service" and the mock sees no request for the link; a code with an extra parameter is "This is not a code for linking a service"; a third wrong code closes the link; a code used twice is "This link is not available".
